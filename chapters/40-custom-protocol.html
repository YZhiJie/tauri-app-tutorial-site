第 40 章 · 自定义协议与 IPC 底层 ​

钳钳：「IPC 是函数调用，协议是 URL 请求——浏览器能直接用的，才是协议。」

本章学习目标 ​

  • 分清 IPC 命令与自定义 URI 两种通信方式的能力边界
  • 用 register_asynchronous_uri_scheme_protocol 注册协议并异步响应
  • 处理 macOS/Linux 与 Windows 之间协议 Origin 的差异
  • 把 URL 路径解析成安全的资源 id，杜绝路径穿越
  • 正确设置 Content-Type、缓存与 nosniff 响应头
  • 在 CSP 中放行协议，并理解「能通过 URL 访问 = 能被页面脚本访问」的安全含义

40.1 协议在架构中的位置 ​

第 3 章起我们一直用 invoke 调命令：前端发起、Rust 分发、结果序列化回传。这条链路叫 IPC，它解决「函数调用」。

但有些场景天然是 URL 请求：

  • <img src="...">、<video src="...">、CSS url(...)；
  • 右键「图片另存为」、打印、下载；
  • 浏览器缓存、ETag、Content-Type 协商。

这些能力 IPC 都提供不了，因为 <img> 只认 URL。自定义协议就是让 WebView 把某个 scheme 的请求交给你处理：

text
<img src="note-card://localhost/abc.svg">
  -> WebView 发起请求
  -> wry 拦截 note-card scheme
  -> 调用 Rust handler
  -> 返回 HTTP Response
  -> WebView 渲染 SVG

它与第 36 章的深链 aninotes:// 是两件事：深链是操作系统把 URL 交给应用；本章的协议是应用内 WebView 把 URL 交给 Rust。名字可以相同，但作用层完全不同。

40.2 IPC 与自定义协议对比 ​

维度IPC 命令自定义协议
触发方前端 JS 主动 invokeWebView 发起资源请求（img / fetch / link）
数据方向双向，可传结构化对象本质是 HTTP 请求 / 响应
二进制需要序列化（base64 / ArrayBuffer）直接返回字节流
缓存无可被 WebView 按响应头缓存
权限系统受 capabilities 约束不受 capabilities 约束
典型用途业务动作、查询、写库图片、字体、媒体、导出文件、页面

警告：自定义协议不经过 Tauri 的权限系统。请求只要到达 handler 就会被执行，因此 handler 必须自己做鉴权与输入校验。能被页面脚本构造的 URL，就等于一个公开接口。

40.3 注册协议 ​

在 main.rs 里，于 run 之前注册：

rust
builder = builder.register_asynchronous_uri_scheme_protocol(
    note_card::SCHEME,
    |ctx, request, responder| {
        let app = ctx.app_handle().clone();
        tauri::async_runtime::spawn(async move {
            responder.respond(note_card::respond(&app, &request).await);
        });
    },
);

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L121-L133)。

为什么选异步版本：

  1. handler 里要查 SQLite，db.get 是 async；
  2. 同步 handler 会在 WebView 的协议线程上阻塞，图片一多就拖慢页面；
  3. responder 可以在任意线程调用，把结果交回 WebView 即可。

同步版本 register_uri_scheme_protocol 适合「读一个内存常量」这类零成本响应。两者签名差异只在于多一个 responder 参数。

40.4 平台差异：同一个协议，两种 Origin ​

这是最容易踩的坑。wry 在各平台的实现不同：

平台协议 URL 形式
macOS / iOS / Linuxnote-card://localhost/<path>
Windows / Androidhttp://note-card.localhost/<path>

所以前端不能写死 note-card://，否则 Windows 用户会得到裂图。项目里用一个函数集中处理：

ts
export function noteCardUrl(id: string, version: number): string {
  if (!isTauri()) return "";
  const origin = isWindowsWebview()
    ? "http://note-card.localhost"
    : "note-card://localhost";
  return `${origin}/${id}.svg?v=${version}`;
}

见 [noteCard.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/noteCard.ts#L24-L31)。

isWindowsWebview() 检测的是 WebView 所在系统，不是编译目标。移动端沿用 http://<scheme>.localhost，与 Windows 同形。

40.5 URL 解析与路径安全 ​

协议 handler 拿到的 request.uri().path() 是攻击面。最危险的是路径穿越：/../../etc/passwd。本章只暴露笔记卡片，因此把「合法路径」收窄成「一个 id + 固定后缀」：

rust
pub fn parse_note_id(path: &str) -> Option<String> {
    let name = path.trim_start_matches('/');
    let id = name.strip_suffix(".svg")?;
    if id.is_empty() || id.len() > 64 {
        return None;
    }
    if !id.chars().all(|c| c.is_ascii_alphanumeric() || c == '-' || c == '_') {
        return None;
    }
    Some(id.to_owned())
}

见 [note_card.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/note_card.rs#L31-L44)。

三条原则：

  1. 白名单字符，而不是黑名单过滤 ..。黑名单永远漏；
  2. 固定后缀，handler 只做一种资源，不做通用文件服务器；
  3. 先解析再取数据，非法 id 在碰数据库之前就被拒绝。

40.6 从数据库取数据 ​

rust
let Some(db) = app.try_state::<NotesDb>() else {
    return text_response(StatusCode::SERVICE_UNAVAILABLE, "数据库尚未就绪");
};

match db.get(&id).await {
    Ok(Some(note)) => svg_response(render_svg(&note)),
    Ok(None) => text_response(StatusCode::NOT_FOUND, "笔记不存在"),
    Err(err) => {
        tracing::warn!(%err, "生成笔记卡片失败");
        text_response(StatusCode::INTERNAL_SERVER_ERROR, "读取笔记失败")
    }
}

见 [note_card.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/note_card.rs#L129-L149)。

要点：

  • 用 try_state：协议可能在 setup 完成前被请求（例如页面首屏就渲染了 <img>），此时数据库还没托管，返回 503 比 panic 好；
  • 三种结果映射到三种状态码，前端与 DevTools 一眼能分清「参数错 / 不存在 / 服务端错」；
  • 日志只记错误，不记正文——第 30 章的红线同样适用于这里。

40.7 响应头：让 WebView 正确理解你的字节 ​

rust
Response::builder()
    .status(StatusCode::OK)
    .header(header::CONTENT_TYPE, "image/svg+xml; charset=utf-8")
    .header(header::CACHE_CONTROL, "no-store")
    .header(header::X_CONTENT_TYPE_OPTIONS, "nosniff")
    .body(svg.into_bytes())

见 [note_card.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/note_card.rs#L114-L125)。

三个头的理由：

响应头作用不设置的后果
Content-Type告诉 WebView 如何解析可能被当成 HTML / 文本，SVG 不渲染
Cache-Control: no-store内容随笔记变化改了笔记仍显示旧卡片
X-Content-Type-Options: nosniff禁止 MIME 嗅探恶意内容可能被当成脚本执行

前端还会在 URL 上追加 ?v=<version>，双保险：即使某层缓存忽略了 no-store，URL 变化也会迫使重新请求。

40.8 内容安全：转义与 CSP ​

笔记标题和正文是用户输入。直接拼进 SVG，就等于把用户内容当标签解析：

rust
fn escape_xml(raw: &str) -> String {
    raw.replace('&', "&amp;")
        .replace('<', "&lt;")
        .replace('>', "&gt;")
        .replace('"', "&quot;")
        .replace('\'', "&apos;")
}

见 [note_card.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/note_card.rs#L47-L53)。

顺序必须先替换 &：否则 &lt; 里的 & 会被二次转义成 &amp;lt;，显示反而出错。

另一个必改的地方是 CSP。默认 CSP 的 img-src 只允许 'self' 与 asset:，新协议会被拦下：

json
"img-src 'self' asset: http://asset.localhost note-card: http://note-card.localhost"

见 [tauri.conf.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/tauri.conf.json#L30)。

提示：CSP 同时写上两种 Origin 形式，是因为同一份配置要覆盖 macOS 与 Windows。少写一个，另一半平台的图片会被静默拦截——DevTools 控制台里才有 CSP violation 日志。

40.9 前端接入 ​

笔记编辑器里直接用一个 <img>：

vue
<img
  v-if="cardUrl"
  class="card-preview"
  :src="cardUrl"
  alt="笔记卡片预览"
/>

见 [NoteEditor.vue](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/notes/NoteEditor.vue#L91-L96)。

cardUrl 是 computed，浏览器 mock 返回空串，模板自动隐藏：

ts
const cardUrl = computed(() =>
  props.note ? noteCardUrl(props.note.id, props.note.version ?? 0) : "",
);

见 [NoteEditor.vue](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/notes/NoteEditor.vue#L34-L37)。

这里体现了协议相对 IPC 的最大优势：零 JS 代码。不需要 invoke、不需要把字节转成 Blob、不需要手动管理 URL 生命周期，浏览器该有的图片能力全部可用。

40.10 底层链路：请求是怎么走到 handler 的 ​

把一次 <img> 加载拆开看：

  1. WebView 解析 src，发现 scheme 不是 http(s)；
  2. wry 在创建 WebView 时为注册过的 scheme 挂上自定义协议回调；
  3. 平台层把请求打包成 http::Request<Vec<u8>>，交给 Tauri 的协议分发器；
  4. 分发器按 scheme 找到你的 handler；
  5. handler 返回 http::Response<Vec<u8>>；
  6. wry 把响应交回 WebView，后者按 Content-Type 渲染。

与 IPC 的链路对比：

阶段IPC自定义协议
发起window.__TAURI_INTERNALS__.invokeWebView 网络栈
传输自定义 IPC 消息（macOS 走 WKWebView message handler）平台自定义协议回调
分发collect_commands! 生成的分发表scheme → handler 映射
权限capability 校验无，handler 自己负责
返回JSON 序列化HTTP 响应字节流

所以「协议更快」或「IPC 更安全」都是过度简化：协议胜在浏览器原生能力，IPC 胜在结构化数据与权限系统。

40.11 什么时候用协议，什么时候用 IPC ​

需求选择原因
读取 / 写入笔记IPC结构化参数、需要权限与错误语义
列表刷新、搜索IPC返回 JSON 数组
生成缩略图、封面协议<img> 直接加载
导出 PDF / 下载文件协议浏览器下载与另存为
加载本地字体协议CSS url() 只能走 URL
播放本地视频协议<video> 需要 URL + Range 支持

一个经验法则：如果前端最终要把它塞进 src / href / url()，就用协议；如果前端要拿它做逻辑判断，就用 IPC。

40.12 常见报错速查 ​

报错 / 现象原因处理
图片裂开，控制台报 CSP violationimg-src 没放行协议在 CSP 中加入 note-card: 与 http://note-card.localhost
macOS 正常、Windows 裂图URL 写死成 note-card://localhostWindows 用 http://note-card.localhost
所有请求都 404scheme 注册名与 URL 不一致统一引用同一个 SCHEME 常量
handler 里 panic 导致白屏用了 state 而不是 try_state协议可能早于 setup，必须容忍状态缺失
图片加载很慢、页面卡顿同步 handler 里查数据库改用异步注册 + spawn
SVG 显示成源码文本没设 Content-Type设 image/svg+xml; charset=utf-8
用户标题把卡片撑破没做长度截断按字符截断，并在 SVG 中固定行高
笔记改了但卡片不变缓存或 URL 未变no-store + ?v=<version>

40.13 小结 ​

本章补上了 IPC 之外的另一种通信方式：

  • 自定义协议让 WebView 用 URL 访问 Rust 资源，天然支持 <img>、下载、缓存与二进制；
  • 注册时优先选异步响应器，把数据库 / 文件 I/O 移出协议线程；
  • 协议 URL 的 Origin 随平台变化，必须集中构造，不能写死；
  • handler 是公开攻击面：白名单 id、固定后缀、try_state、正确的状态码与响应头缺一不可；
  • 用户内容拼进 SVG 前必须做 XML 转义，CSP 必须显式放行新协议；
  • 选择标准：进 src / href 的走协议，做逻辑判断的走 IPC。

课后练习 ​

  1. 给协议增加 HEAD 请求支持（只返回响应头，不返回 body），并解释它对缓存与下载工具的意义。
  2. 把卡片渲染改成 PNG（提示：需要引入图像编码库），对比 SVG 与位图在体积、清晰度与生成成本上的差异。
  3. 为协议增加一个 ?theme=dark|light 参数，在 handler 里解析查询串并切换配色，观察 CSP 与缓存策略是否需要调整。
