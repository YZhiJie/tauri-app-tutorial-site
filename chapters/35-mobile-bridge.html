第 35 章 · 移动端构建与原生桥接 ​

小塔：「桌面应用搬进手机，不是把窗口缩小，而是换一套生命周期和权限规则。」

本章学习目标 ​

  • 理解桌面与移动端在窗口、生命周期、系统能力上的差异
  • 用 crate-type = ["staticlib", "cdylib", "rlib"] 让库目标同时服务三端
  • 用 cfg(desktop) / cfg(mobile) 裁掉移动端不存在的 API
  • 用命令、插件、JNI/Swift 三种方式完成原生桥接
  • 用 Rust 侧编译期探测替代前端 userAgent 猜测
  • 按平台拆分 capability，做到「移动端拿不到的权限不声明」

35.1 移动端不是缩小版桌面 ​

把同一份 Tauri 应用编到 Android / iOS，最先撞上的不是 UI 适配，而是能力模型：

能力桌面移动
多窗口任意创建系统托管单一 WebView
系统托盘有无
全局快捷键有无
窗口装饰可定制标题栏由系统控制
生命周期关闭窗口即退出切后台可能被挂起/回收
文件系统任意路径沙箱目录 + 分享面板

因此移动端适配的第一原则：先让代码在移动端编译通过，再谈体验。编译都过不了，说明还有桌面专属 API 散落在业务路径里。

35.2 库目标：移动打包器的硬性要求 ​

移动端不链接可执行文件，而是把 Rust 编译成静态库/动态库，再由 Android 的 JNI 或 iOS 的 Swift 壳加载：

toml
[lib]
name = "aninotes"
crate-type = ["staticlib", "cdylib", "rlib"]

见 [Cargo.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/Cargo.toml#L18-L22)。

三个产物各司其职：

crate-type给谁用说明
staticlibiOSXcode 链接 .a
cdylibAndroidJNI 加载 .so
rlib桌面二进制 / 测试普通 Rust 链接

提示：rlib 不能省。少了它，cargo test 找不到可链接的库，桌面构建也会失败。三端共存不是「多此一举」，而是同一份 Cargo 配置必须同时满足三种链接方式。

35.3 条件编译：把桌面 API 关在门外 ​

main.rs 里最容易让移动端编译失败的，是托盘、菜单、全局快捷键与多窗口。第 35 章把 Builder 拆成两段：

rust
let mut builder = tauri::Builder::default()
    .plugin(tauri_plugin_dialog::init())
    /* 跨平台插件与状态 */;

#[cfg(desktop)]
{
    builder = builder.plugin(global_shortcut_plugin);
}

builder
    .invoke_handler(specta.invoke_handler())
    .setup(move |app| { /* ... */ })

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L72-L105)。

setup 里的托盘整段也收进 #[cfg(desktop)] 块：

rust
#[cfg(desktop)]
{
    let show_item = MenuItem::with_id(app, "tray-show", "显示主窗口", true, None::<&str>)?;
    /* 菜单 + TrayIconBuilder */
}

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L142-L183)。

同样的处理还用在多窗口函数上：

rust
#[cfg(desktop)]
fn open_quick_capture(app: &tauri::AppHandle) { /* ... */ }

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L272)。

这些 cfg(desktop) / cfg(mobile) 是 Tauri 构建脚本注入的别名，不需要自己定义。判断规则：

  • API 在某个平台不存在 → 必须 cfg；
  • API 存在但语义不同（如窗口尺寸）→ 运行时判断，不要 cfg；
  • 业务逻辑本身跨平台 → 保持共享，避免复制两份。

警告：不要在 cfg 块里写「差不多就行」的替代实现。移动端缺失的托盘就用「不提供」，不要硬造一个假托盘；用户不会因为少了托盘而困惑，却会因为一个点不动的假图标而困惑。

35.4 原生桥接的三种方式 ​

移动端的「原生」是相对 WebView 而言的。按侵入程度从低到高：

方式写法适用
命令#[tauri::command] + invoke纯 Rust 逻辑，无平台 SDK
插件官方/社区插件相机、蓝牙、生物识别等标准能力
JNI / SwiftKotlin / Swift 壳 + FFI只有原生 SDK 才能做的事

本章用的是第一种：平台探测完全在 Rust 完成，前端只消费结果。它没有引入任何 Android/iOS 工程文件，却已经满足「移动端能编译」的前提。

第二种是绝大多数场景的正解。选插件时看两个信号：是否声明支持 android / ios，以及权限是否通过 Tauri 的 capability 暴露。不要直接抄一段 JNI 代码进业务模块——那会绕开 capability，让权限模型形同虚设。

第三种只在插件缺位时使用。桥接边界要满足三条：

  1. 单向：原生层不做业务决策，只做能力调用；
  2. 可失败：所有原生调用返回 Result，不允许「失败就静默」；
  3. 最小面：暴露的函数数量控制在个位数，其余封装在原生层内部。

35.5 平台探测：编译期事实，而不是 UA 猜测 ​

前端需要知道「我是不是移动端」，用来隐藏托盘入口、调整间距。最可靠的信息来自 Rust：

rust
const fn is_mobile() -> bool {
    cfg!(any(target_os = "android", target_os = "ios"))
}

pub fn current() -> RuntimePlatform {
    RuntimePlatform {
        kind: if is_mobile() { PlatformKind::Mobile } else { PlatformKind::Desktop },
        os: std::env::consts::OS.to_string(),
        arch: std::env::consts::ARCH.to_string(),
    }
}

见 [platform.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/platform.rs#L35-L46)。

命令本身只是 current() 的薄包装：

rust
#[tauri::command]
#[specta::specta]
pub fn runtime_platform() -> RuntimePlatform {
    current()
}

见 [platform.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/platform.rs#L55-L57)，注册位置见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L209)。

前端只做两件事：优先走 IPC，失败才退回 UA：

ts
export async function detectPlatform(): Promise<RuntimePlatform> {
  if (!isTauri()) return fallbackPlatform();
  try {
    return await commands.runtimePlatform();
  } catch {
    return fallbackPlatform();
  }
}

见 [platform.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/platform.ts#L28-L36)。

为什么要保留 UA 回退？因为 pnpm dev 的浏览器预览没有 Rust 进程。回退只用于开发期展示，不参与权限判断——UA 可以伪造，编译期 cfg 不能。

「关于」弹窗把它展示出来，方便真机联调时第一时间确认形态：

html
<li v-if="runtime">
  <span>运行时形态</span>
  <b>{{ runtime.kind === "mobile" ? "移动端" : "桌面端" }} · {{ runtime.arch }}</b>
</li>

见 [AboutDialog.vue](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/system/AboutDialog.vue#L99-L105)。

35.6 权限按平台拆分 ​

第 27 章讲过 capability 是最小权限的落点。到了移动端，还要多一层「平台维度」：桌面 capability 里的 updater、global-shortcut 在手机上根本不存在。

桌面主窗口显式限定平台：

json
{
  "identifier": "main-window",
  "platforms": ["macOS", "windows", "linux"],
  "windows": ["main"]
}

见 [main.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/capabilities/main.json#L2-L6)。

移动端单独一份，只保留真正可用的能力：

json
{
  "identifier": "main-window-mobile",
  "platforms": ["android", "iOS"],
  "windows": ["main"],
  "permissions": ["core:default", "dialog:default", "notification:default", "os:default", "note-stats:default"]
}

见 [mobile.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/capabilities/mobile.json#L1-L12)。

拆分的好处不只是「能编译」：

  • 移动端即使误调 updater，也会被权限系统拒绝，而不是抛一个平台不支持的错误；
  • 安全审计时能一眼看出「哪些能力只存在于桌面」；
  • 未来接入商店审核，权限清单可以直接对应隐私声明。

提示：quick-capture.json 同样限定为桌面。移动端没有第二个窗口，保留这份 capability 只会让权限表无端变长。

35.7 初始化与开发工作流 ​

移动端工程文件（gen/android、gen/ios）由 CLI 生成，不手写：

bash
# 首次准备（需要 Android Studio / SDK 与 Xcode）
pnpm tauri android init
pnpm tauri ios init

# 开发：真机或模拟器热更新
pnpm tauri android dev
pnpm tauri ios dev

# 构建：产出 apk / aab 或 ipa
pnpm tauri android build
pnpm tauri ios build

gen/ 目录建议纳入版本控制（官方模板默认如此），因为商店签名、Manifest 权限、Info.plist 往往需要人工微调；把它当生成物忽略掉，下一次 init 会覆盖你的修改。

本章没有在本机执行 android init：移动构建需要 Android SDK / NDK 与 Xcode，属于环境前置条件，无法在纯 Rust 桌面环境里完成。代码侧的准备（库目标、cfg 隔离、capability 拆分、平台探测）已全部落地，装好 SDK 后即可直接初始化。

环境检查清单：

目标必需项验证命令
AndroidJDK 17、Android SDK、NDKpnpm tauri info
iOSXcode、Command Line Toolsxcodebuild -version
通用Rust 移动目标rustup target list --installed

35.8 移动端 UX 与生命周期 ​

编译通过只是起点。移动端有三件事必须提前设计：

  1. 安全区：刘海与手势条会吃掉上下 20~40px，CSS 用 env(safe-area-inset-*) 留白；
  2. 软键盘：键盘弹起会压缩可视区域，编辑器要监听 resize 或使用 visualViewport；
  3. 后台回收：应用切后台后可能被系统杀掉，未落盘的编辑内容必须实时持久化（本项目笔记本来就是输入即保存，天然满足）。

生命周期上，桌面习惯「关窗即退出」，移动端对应的是：

  • RunEvent::Resumed：从后台回到前台，适合刷新数据、重连；
  • RunEvent::Suspended：进入后台，适合 flush 缓冲、暂停轮询；
  • 不要在这两个事件里做耗时操作，系统给的时间窗口很短。

警告：移动端不要依赖「进程一直活着」。定时器、长连接、内存缓存都要假设随时会断，恢复时从持久化状态重建，而不是从内存变量续上。

现象原因解决

35.10 小结与课后练习 ​

本章你已完成：为库目标补齐移动端所需的 staticlib / cdylib；用 cfg(desktop) 隔离托盘、全局快捷键与多窗口；新增 runtime_platform 命令与前端探测层；把 capability 按平台拆成桌面与移动两份；梳理了移动端初始化、开发与构建命令。应用升级到 v0.34.0。

课后练习：

  1. 在 platform.rs 里增加 safeAreaTop 字段（移动端返回估算值，桌面返回 0），并说明为什么这个值不该由前端自己猜。
  2. 把 AboutDialog 的「数据目录」「重启」「退出」三个按钮在移动端隐藏，写出判断条件与测试。
  3. 设计一个「相机扫码导入笔记」的插件方案：列出需要的 capability、权限文案与失败分支。
  4. 解释为什么 cfg(mobile) 更适合控制「编译是否存在」，而 runtime_platform 更适合控制「界面是否展示」。
  5. 读 Tauri 的 RunEvent 文档，写出应用从后台恢复时重建数据库连接的最小步骤。
