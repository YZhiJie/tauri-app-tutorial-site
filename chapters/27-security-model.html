第 27 章 · 安全威胁模型与最小权限 ​

钳钳：「安全的起点不是加一个锁，而是先想清楚：谁想进来、门在哪、里面有什么值得偷。」

本章学习目标 ​

  • 用「资产 / 对手 / 入口 / 缓解」四要素写出一个能落地的威胁模型
  • 理解 Tauri 的信任边界：WebView 不可信，Rust 核心才是防线
  • 把「一个 default 权限集」拆成按窗口的最小权限
  • 逐条读懂 CSP，知道每条指令挡住什么
  • 建立输入校验三层防线，并做一次发布前安全检查

27.1 威胁模型不是安全公司的专利 ​

很多人一听到「威胁模型」就想到大企业的合规文档。实际上它只需要回答四个问题：

要素问题AniNotes 的答案
资产什么值得保护？笔记正文、数据库文件、更新签名公钥
对手谁会尝试攻击？恶意网页内容、被篡改的更新包、本地其他程序
入口从哪里能进来？WebView 渲染、IPC 命令、文件导入、深链、更新器
缓解每道门怎么挡？CSP、capability、输入校验、签名校验

写下来之后，安全措施才有优先级：没有威胁模型的「加固」很容易把成本花在没人攻击的地方。

27.2 AniNotes 的资产清单 ​

按「泄露 / 篡改后的后果」排序：

资产位置后果当前保护
笔记正文aninotes.db隐私泄露、内容丢失用户目录权限 + 应用内校验
数据库完整性SQLite 文件静默篡改、索引损坏单写入点、事务、迁移版本闸门
更新包网络下载被替换成恶意程序updater 内置公钥验签
更新私钥CI Secret可签发任意更新不入库、只放 CI Secret
文件系统路径导入导出参数读写任意文件文件名白名单、用户显式选择
全局快捷键系统注册被其他应用抢占失败降级、不阻塞启动

注意最后一项也属于安全资产：一个被抢占后反复弹窗报错的快捷键，会训练用户忽略应用提示。

27.3 信任边界：谁不可信 ​

text
┌──────────────────────────────────────────────┐
│ WebView（不可信）                              │
│  HTML / CSS / JS / 第三方脚本                  │
│  能力：只能通过 IPC 调用 Rust 暴露的命令        │
└───────────────────────┬──────────────────────┘
                        │ IPC（唯一的门）
┌───────────────────────▼──────────────────────┐
│ Rust 核心（可信）                              │
│  命令参数校验 / 路径白名单 / SQL / 签名校验     │
└───────────────────────┬──────────────────────┘
                        │ 系统 API
┌───────────────────────▼──────────────────────┐
│ 操作系统（边界外）                             │
│  文件系统 / 网络 / 进程 / 钥匙串               │
└──────────────────────────────────────────────┘

三条推论：

  1. 前端校验只是 UX，不是安全。用户可以在 DevTools 里直接 invoke，命令层必须重新校验。
  2. Rust 核心不能假设前端只传合法参数。batch_size = 0、path = "../../.ssh/id_rsa" 都要在命令层挡掉。
  3. 系统能力要按窗口授权。能给主窗口的权限，不该自动给一个只有输入框的小窗。

27.4 从「一个 default」到「按窗口最小权限」 ​

第 24 章为了快速记录窗口，把 quick-capture 加进了同一个 default.json：

json
{
  "identifier": "default",
  "windows": ["main", "quick-capture"],
  "permissions": ["core:default", "dialog:default", "updater:default", "..."]
}

问题在于：快速记录窗口只需要 create_note 和关闭自己，却同时拿到了文件对话框、通知、更新器、系统信息。一旦这个窗口被 XSS 或恶意依赖控制，攻击面被无谓放大。

本章把它拆成两个文件：

[capabilities/main.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/capabilities/main.json)：

json
{
  "identifier": "main-window",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "dialog:default",
    "notification:default",
    "opener:default",
    "os:default",
    "process:default",
    "updater:default",
    "global-shortcut:default",
    "note-stats:default"
  ]
}

[capabilities/quick-capture.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/capabilities/quick-capture.json)：

json
{
  "identifier": "quick-capture-window",
  "windows": ["quick-capture"],
  "permissions": [
    "core:default",
    "core:window:allow-close",
    "core:window:allow-set-focus"
  ]
}

权限矩阵因此变成：

能力mainquick-capture理由
自定义命令（笔记 CRUD）是是快速记录必须能保存
文件对话框是否小窗不导入导出
通知是否保存后不需要系统通知
更新器是否更新只由主窗口触发
系统信息（os）是否小窗不展示硬件信息
关闭 / 聚焦自身窗口是是关闭是基本交互

一个容易踩的坑：自定义命令不受 capability 限制。invoke("create_note") 在 quick-capture 里能用，不是因为它被列进了 JSON，而是因为应用自己注册的命令默认允许。capability 管的是插件与核心 API，不是你的业务命令。

27.5 CSP：WebView 的「只准做这些事」 ​

[tauri.conf.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/tauri.conf.json#L29-L31) 现在的 CSP：

json
"csp": "default-src 'self'; connect-src ipc: http://ipc.localhost; img-src 'self' asset: http://asset.localhost; style-src 'self' 'unsafe-inline'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'"

逐条解释：

指令作用为什么这样写
default-src 'self'未单独声明的资源默认只允许应用自身兜底最严格
connect-src ipc: http://ipc.localhost允许 IPC 通信少了它，某些平台的 invoke 会被 CSP 拦
img-src 'self' asset:...允许本地图片与 asset 协议教程插图走 asset
style-src 'self' 'unsafe-inline'允许内联样式Vue 的 scoped style 需要；风险可接受
script-src 'self'脚本只能来自打包产物挡住内联脚本与 eval
object-src 'none'禁止 Flash/插件类对象历史攻击面，直接关死
base-uri 'self'禁止 <base> 改基准地址防相对路径被劫持
frame-ancestors 'none'禁止被嵌入 iframe防点击劫持

不要为了省事加 'unsafe-eval'。如果某个依赖要求它，先确认依赖是否真的需要，再考虑隔离到独立窗口。

27.6 输入校验的三层防线 ​

层做什么例子
前端即时反馈，减少无效请求标题长度提示、禁用空提交
命令层强制约束，防绕过batch_size.clamp(1, 1000)、空标题拒绝
数据/文件层最后一道，防注入与越界SQL 参数绑定、文件名白名单

以文件名为例。导出功能接受用户输入的文件名，如果直接拼接路径：

rust
let path = dir.join(user_input); // 危险：../../.ssh/id_rsa

[text.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/text.rs) 的 safe_file_name 做了三件事：拒绝路径分隔符、拒绝 ..、过滤平台非法字符，最后截断长度。命令层再把它和用户选定的目录拼起来，永远不让用户输入决定最终目录。

SQL 侧同理：全项目使用 ?1 参数绑定，没有一处 format! 拼 SQL。FTS5 搜索还会把用户输入包成短语 "{kw}"，避免 AND、列名前缀被当成查询语法。

27.7 日志与错误消息：别把秘密写进文件 ​

第 16 章的日志会落盘。以下内容永远不该进日志：

  • 笔记正文（可能含隐私）——只记 id、长度、操作类型；
  • 完整文件路径（可能含用户名）——必要时只记文件名；
  • 更新私钥、token、密钥——根本不应出现在进程内存以外的任何地方；
  • 前端完整错误对象——只记 error.name 与脱敏后的 message。

当前代码的错误消息带「哪一步失败」的上下文，但不带正文，这是正确的粒度。第 28 章会把真正需要加密的内容单独放进 vault，而不是塞进 tracing。

27.8 发布前安全检查清单 ​

检查项通过标准
capability 拆分每个窗口只拿它真正需要的权限
CSP无 unsafe-eval，object-src 'none'
命令参数所有长度、范围、枚举都有后端校验
文件路径用户输入不参与目录选择
SQL全部参数绑定，无字符串拼接
日志不含正文、凭证、完整路径
更新公钥已配置，私钥只在 CI Secret
依赖cargo audit / pnpm audit 无高危（第 29 章）
调试能力发布版无 devtools、无测试后门命令

这张表建议放进发布 PR 模板，每一条都能用「看代码 / 跑命令」验证，而不是靠感觉。

27.9 常见报错速查 ​

现象原因解决
拆完 capability 后小窗调插件报 not allowed插件权限只给了 main确认小窗真的需要；需要才加最小权限
invoke 报 CSP 拦截connect-src 缺少 ipc:补上 ipc: http://ipc.localhost
页面样式全丢style-src 未允许内联保留 'unsafe-inline'（Vue scoped style 需要）
两个 capability 文件冲突identifier 重复每个文件用唯一 identifier
开发正常、打包后白屏CSP 在生产模式更严格用 tauri build 复现，检查控制台 CSP 报告
小窗关闭后进程不退关闭只是隐藏明确 close 与 hide 的语义

27.10 小结与课后练习 ​

本章你已完成：写出 AniNotes 的四要素威胁模型与资产清单；画出 WebView / Rust / OS 的信任边界；把单一 default 权限拆成按窗口最小权限；逐条解释 CSP；建立输入校验三层防线与日志脱敏规则；得到一份可执行的发布前检查清单。应用升级到 v0.26.0。

课后练习：
