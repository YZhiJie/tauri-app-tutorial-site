第 37 章 · 本地优先：迁移、备份与冲突解决 ​

小塔：「本地优先不是拒绝云，而是先把数据放在用户手里，再谈同步。」

本章学习目标 ​

  • 理解「本地优先」对数据主权、离线可用与一致性的要求
  • 用 PRAGMA user_version 组织只向前、可重跑的迁移步骤
  • 在升级前用 VACUUM INTO 生成一致性备份，并做保留份数轮转
  • 用版本号 + compare-and-swap 保存，避免多窗口「后写覆盖先写」
  • 设计冲突后的处理策略：另存副本、保留远端、用户手动合并
  • 为未来的多设备同步预留变更日志与墓碑字段

37.1 本地优先到底优先什么 ​

很多笔记应用把「云同步」当成第一功能，本地只是缓存。本地优先（local-first） 反过来：

原则含义工程后果
数据主权用户的数据首先属于用户设备默认落本地库，导出/备份是一等能力
离线可用断网时读写照常所有写操作先写本地，同步是后台行为
可恢复升级、崩溃、误删都能回退迁移前备份、软删除、版本历史
最终一致多端数据迟到汇合需要版本号、冲突检测与合并策略

本章不实现网络同步，但把同步必需的三块地基打好：可演进的模式迁移、可恢复的备份、可判定的冲突。真正接云端时，你会发现协议层只是在这三块之上加一层传输。

37.2 模式迁移：版本号是唯一真相 ​

SQLite 自带一个整型字段 PRAGMA user_version，默认 0。它跟着数据库文件走，不需要额外的元表，因此最适合当「模式版本」：

rust
const SCHEMA_VERSION: i64 = 2;

async fn migrate(&self, app: &AppHandle) -> Result<(), AppError> {
    let current = self.schema_version().await?;
    if current >= SCHEMA_VERSION {
        return Ok(());
    }

    if current > 0 {
        let path = self.backup(app).await?;
        tracing::info!(from = current, to = SCHEMA_VERSION, path = %path.display(), "数据库升级前已备份");
    }

    if current < 1 {
        self.migrate_to_v1(app).await?;
    }
    if current < 2 {
        self.migrate_to_v2().await?;
    }
    Ok(())
}

见 [db.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/db.rs#L158-L183)。

三条硬规则：

  1. 只向前：迁移函数只处理 current..SCHEMA_VERSION 的缺口，已执行的步骤永不重跑。否则「用户删掉的种子笔记」会在每次启动时复活。
  2. 每步幂等：CREATE TABLE IF NOT EXISTS、CREATE INDEX IF NOT EXISTS 让「执行到一半崩溃」后可以安全重试。
  3. 一步一版本：v1 负责 JSON 迁移与种子，v2 只加索引。不要把多个变更塞进同一步，否则回滚粒度太粗。

提示：不要把业务逻辑（比如「给旧笔记补标签」）写成 SQL 字符串数组。把它写成带测试的 Rust 函数，失败时能打印具体是哪条记录、哪个字段。

v2 加的是列表查询的复合索引：

rust
sqlx::query(
    "CREATE INDEX IF NOT EXISTS idx_notes_updated_at
     ON notes(updated_at DESC, id ASC)",
)

见 [db.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/db.rs#L231-L241)。列表与分页都按这两个键排序，数据量上来后没有索引就是全表扫描加临时排序。

37.3 迁移前备份：别用 fs::copy ​

最危险的发布事故之一是「升级迁移写坏了库，用户原数据也没了」。备份必须在迁移之前完成。

rust
let escaped = target.to_string_lossy().replace('\'', "''");
sqlx::query(&format!("VACUUM INTO '{escaped}'"))
    .execute(&self.pool)
    .await
    .map_err(|e| AppError::db("备份数据库失败", e))?;

见 [db.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/db.rs#L247-L268)。

为什么是 VACUUM INTO 而不是直接复制文件：

方式风险
fs::copy复制瞬间可能正有写入，拿到页级不一致的副本；WAL 模式下还会漏掉未合并的日志
VACUUM INTO在数据库连接内做一致性快照，输出一个可独立打开的单文件库

备份文件名带时间戳（aninotes-backup-20261102-233900.db），字典序即时间序，清理时不需要解析时间：

rust
files.sort();
let extra = files.len().saturating_sub(keep);
for path in files.into_iter().take(extra) { ... }

见 [db.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/db.rs#L525-L545)。

只保留最近三份：够回退到「刚才那次升级」，又不会让磁盘无限增长。清理时按前缀 aninotes-backup- 精确匹配，aninotes.db 等业务文件绝不误删——单元测试里专门放了一个无关文件来守住这条边界。

警告：VACUUM INTO 的目标文件必须不存在。若同一秒内触发两次备份会撞名失败。生产代码可加随机后缀，或先检查存在性；本章保留「秒级时间戳 + 报错」的简单策略，因为手动备份几乎不可能同秒连点。

37.4 冲突从哪里来 ​

单窗口 + 单机时，SQLite 单一写入点已经消灭了大部分冲突。但以下场景仍会发生：

场景冲突表现
两个窗口同时编辑同一笔记后保存者覆盖先保存者
快速记录窗与主窗并存（第 24 章）主窗的旧草稿覆盖小窗刚写入的内容
从文件导入同名笔记语义相同的两份内容各自成条
未来多设备同步同一版本号在不同设备上演化出两条历史

本章解决第一类与第二类的数据覆盖问题，第三类交给用户显式选择，第四类为后续同步协议留好版本字段。

核心观察：冲突不是错误，而是一种需要业务决策的正常结果。把它当 Err("冲突") 抛给前端，前端只能弹个红字；把它当结构化返回值，前端才能选择「另存副本」。

37.5 CAS 保存：一条 SQL 消灭竞态 ​

「先 SELECT 查版本，再 UPDATE 写入」中间存在竞态窗口。正确做法是把比较和写入压成一条原子语句：

sql
UPDATE notes
SET title = ?1, content = ?2, updated_at = ?3, version = version + 1
WHERE id = ?4 AND version = ?5
  • 影响行数为 1：版本一致，写入成功，version 自增；
  • 影响行数为 0：要么 id 不存在，要么版本已变。再查一次当前值即可区分。
rust
if result.rows_affected() == 1 {
    let saved = self.get(id).await?.ok_or_else(|| AppError::NotFound(id.to_string()))?;
    return Ok(SaveOutcome::Saved(saved));
}

match self.get(id).await? {
    Some(current) => Ok(SaveOutcome::Conflict(current)),
    None => Err(AppError::NotFound(id.to_string())),
}

见 [db.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/db.rs#L436-L470)。

返回值用一个判别联合表达两种结果：

rust
#[derive(Debug, Clone, Serialize, specta::Type)]
#[serde(tag = "status", content = "data", rename_all = "camelCase")]
pub enum SaveOutcome {
    Saved(Note),
    Conflict(Note),
}

见 [model.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/model.rs#L49-L61)。前端拿到的是 { status: "saved" | "conflict", data: Note }，用判别联合窄化，不需要靠字符串消息猜。

命令层只在真正写入成功时广播 notes://changed：

rust
if let SaveOutcome::Saved(note) = &outcome {
    cache.invalidate();
    crate::broadcast_notes_changed!(app, note);
}

见 [commands.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/commands.rs#L107-L135)。冲突时若也广播，前端会刷新成远端内容，用户正在编辑的界面会「跳变」，反而掩盖了冲突。

37.6 冲突后的三种策略 ​

策略适用代价
另存副本（本章）两边都有价值，宁可多一条也不丢字列表会出现「标题（冲突副本）」
保留远端、放弃本地本地只是误触或试验用户可能丢改动
字段级合并标题与正文分别被改需要三方合并（base/local/remote），实现成本高

本章选「另存副本」，因为它满足两个工程目标：

  1. 不丢数据：本地改动第一时间落成新笔记，用户随后可对比、摘抄、删除；
  2. 实现简单：不需要 base 版本，也不需要 UI 做逐字段 diff。
ts
export function conflictCopyTitle(title: string): string {
  const base = title.trim() || "无标题笔记";
  return `${base}（冲突副本）`;
}

见 [sync.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/sync.ts#L59-L63)。

提示：副本标题是「可被用户识别的标记」，不是唯一性约束。同名副本会自然出现多条，这没问题——笔记应用允许重名，ID 才是主键。

37.7 前端接入：防抖里带上版本 ​

第 3 章的保存是 500ms 防抖 + 乐观更新。第 37 章只改一处：保存时把「这次编辑基于哪个版本」一起送出去。

ts
const snapshot = {
  id: note.id,
  title: note.title,
  content: note.content,
  expectedVersion: expectedVersionOf(note),
};

见 [useNotes.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/composables/useNotes.ts#L128-L163)。

保存成功要把本地版本跟上，否则下一次防抖保存还会用旧版本，立刻自造一次假冲突：

ts
if (outcome.status === "saved") {
  const local = notes.value.find((n) => n.id === snapshot.id);
  if (local) local.version = outcome.note.version;
  return;
}

冲突时先写副本，再让 notes://changed 驱动的刷新覆盖当前笔记：

ts
await invoke("create_note", {
  title: conflictCopyTitle(outcome.current.title),
  content: snapshot.content,
});
notifyError("笔记已被其他窗口修改，你的改动已保存为冲突副本");

注意顺序：先创建副本，再提示。如果先提示再异步创建，用户可能立刻关窗或切走，副本就丢了。

旧数据没有 version 字段时按 0 处理：

ts
export function expectedVersionOf(note: Note): number {
  return note.version ?? 0;
}

见 [sync.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/sync.ts#L68-L71)。0 与库里的 1 必然不等，因此会走一次冲突分支——换来的是「旧笔记第一次保存不会静默覆盖别人刚做的修改」。

37.8 把备份做成用户可点的动作 ​

迁移前备份是自动的，但用户仍需要一个「我现在就想存一份」的入口。关于弹窗里加一个按钮：

ts
async function backupData() {
  backupState.value = "正在备份…";
  try {
    const path = await backupDatabase();
    if (!path) {
      backupState.value = "浏览器模式没有数据库可备份";
      return;
    }
    backupState.value = `✅ 已备份到 ${path.split("/").pop()}`;
  } catch (err) {
    backupState.value = "备份失败，请检查磁盘空间";
    console.error(err);
  }
}

见 [AboutDialog.vue](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/system/AboutDialog.vue#L61-L75)。

前端封装只做两件事：Tauri 判定与错误解包。

ts
export async function backupDatabase(): Promise<string | null> {
  if (!isTauri()) return null;
  const result = await commands.backupNotes();
  if (result.status === "error") throw new Error(result.error);
  return result.data;
}

见 [sync.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/sync.ts#L48-L53)。

提示：备份文件默认放在应用数据目录，与主库同级。恢复时关闭应用，把备份重命名回 aninotes.db 即可；不要做「应用内一键恢复」初版，它需要处理连接池、WAL、前端缓存三者的一致性问题，风险远高于收益。

37.9 数据目录与恢复演练 ​

macOS / Linux / Windows 的数据目录由 app_data_dir() 决定，本项目里可以用「数据目录」按钮直接打开。一次完整的恢复演练：

  1. 关闭应用；
  2. 把 aninotes.db 改名为 aninotes.db.broken（保留现场）；
  3. 把 aninotes-backup-*.db 最新一份改名为 aninotes.db；
  4. 启动应用，确认列表、搜索、字数统计都正常；
  5. 确认无误后删除 aninotes.db.broken。

警告：恢复时不要在应用运行中替换数据库文件。连接池仍持有旧文件句柄，WAL 与共享内存文件（-wal / -shm）也会残留，轻则读到旧数据，重则打开失败。

37.10 为多设备同步预留的三样东西 ​

本章没有网络层，但同步协议需要的字段已经就位：

地基本章状态后续用途
全局唯一 IDgen_id() 生成 n-<nanos>多端合并时不会撞主键
内容版本号version 每次写入 +1判定「谁更新」与冲突检测
一致性快照VACUUM INTO 备份同步前基线、迁移回滚点

还缺的两块，留给第 38 章与后续练习：

  • 变更日志（op log）：只传增量，不传全量；
  • 墓碑（tombstone）：删除也要同步，否则另一台设备会把已删笔记「复活」。
text
notes(id, title, content, updated_at, version)
changes(id, note_id, op, payload, at)   -- 未来：增量同步的账本

设计顺序建议：先有稳定的版本号与 ID，再有变更日志，最后才谈「实时推送」。反过来做，通常会在第一次冲突时推倒重来。

37.11 常见报错速查 ​

现象原因处理
启动时提示「备份数据库失败」目标文件已存在 / 磁盘满VACUUM INTO 目标必须不存在；检查空间
备份文件很小但打不开误用 fs::copy 拷到半写状态改用 VACUUM INTO
升级后种子笔记复活迁移步骤重跑了校验 PRAGMA user_version 闸门
每次保存都提示冲突保存成功后未同步本地 version用返回值更新本地版本
冲突副本没出现先提示后创建、组件已卸载先 create_note，再提示
恢复备份后搜索失效只替换主库，漏了 WAL 文件关闭应用后替换，或同时清理 -wal/-shm
旧笔记首次保存就冲突旧数据 version 为 0符合预期；提示用户后保存副本
备份越积越多未做轮转按前缀排序，只保留最近 N 份

37.12 小结与课后练习 ​

本章你已完成：把迁移整理成「版本闸门 + 幂等步骤」；升级前用 VACUUM INTO 自动备份并轮转；用一条 CAS SQL 实现版本校验保存；在前端处理冲突并另存副本；给备份加了用户入口。应用升级到 v0.36.0。

课后练习：

  1. 给 backup() 增加毫秒或随机后缀，解决同一秒内重复备份撞名的问题，并补一条测试。
  2. 把 migrate_to_v2 换成「加一列 tags TEXT NOT NULL DEFAULT ''」，写出完整迁移、模型字段、导出格式与测试。
  3. 实现「保留远端」策略：冲突时让用户在原笔记与副本之间二选一，说明如何避免多次提示。
  4. 设计 changes 表的最小字段与写入时机，要求支持「按时间增量拉取」与「删除同步」。
  5. 写一份恢复演练脚本（可以是 shell），要求能在不启动 GUI 的情况下校验备份库的 PRAGMA user_version 与笔记条数。
