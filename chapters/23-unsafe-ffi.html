第 23 章 · unsafe 与 FFI：把 C 接口关进安全的盒子 ​

小塔：「unsafe 不是『危险模式』开关，而是一张欠条——你向编译器承诺『这里我人工检查过了』，就得写清楚凭什么。」

本章学习目标 ​

  • 理解 unsafe 的五个能力，以及它不能做什么
  • 每条 unsafe 都配 // SAFETY: 注释，写清成立条件
  • 通过 libc 调用 getpid / sysconf，并用 cfg 为非 Unix 平台提供安全回退
  • 用 target-specific dependency 只在需要的平台链接 libc
  • 设计「窄接口」：所有 unsafe 关在一个模块，对外只暴露安全函数

23.1 unsafe 的真实含义 ​

unsafe 允许你做五件事：

  1. 解引用裸指针（*const T / *mut T）；
  2. 调用 unsafe 函数（包括大多数 FFI）；
  3. 访问/修改 static mut；
  4. 实现 unsafe trait；
  5. 访问 union 字段。

它不会关闭借用检查、不会关闭类型检查、不会让数据竞争「合法」。换句话说：

unsafe 只是把「编译器无法验证的那一小部分」交给开发者，其余规则照旧。

本项目只在 [system/hardware.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/system/hardware.rs) 里出现 unsafe，且都包在最小函数内。

23.2 目标：进程 PID 与在线 CPU 数 ​

需求很小：在「关于」弹窗里显示 PID 和 CPU 核心数。

  • std::process::id() 能拿 PID（安全）；
  • std::thread::available_parallelism() 能拿并行度（安全）；
  • 但「在线 CPU 数」在 Unix 上最直接的来源是 sysconf(_SC_NPROCESSORS_ONLN)，属于 libc。

为了让这一章有真实的 FFI 素材，我们两条都走 libc，并通过 source 字段告诉前端「这次走的是 FFI 还是标准库回退」。

23.3 添加依赖：只在 Unix 链接 libc ​

toml
[target.'cfg(unix)'.dependencies]
libc = "0.2"

[target.'cfg(...)'.dependencies] 是 target-specific dependency：Windows 构建时根本不会编译/链接 libc，也就不会出现「找不到符号」。这比在代码里到处 #[cfg] 更干净。

23.4 两段 FFI，两条 SAFETY 注释 ​

rust
/// getpid(2)：返回当前进程 ID。
#[cfg(unix)]
fn process_id() -> u32 {
    // SAFETY: getpid 没有参数、不读写调用者内存、不会失败，
    // 在任何线程调用都安全。
    unsafe { libc::getpid() as u32 }
}
rust
/// sysconf(_SC_NPROCESSORS_ONLN)：查询「在线」CPU 数。
#[cfg(unix)]
fn cpu_count() -> usize {
    // SAFETY: _SC_NPROCESSORS_ONLN 是编译期常量，sysconf 只读系统配置；
    // 失败时返回 -1，我们做了显式检查后回退到标准库。
    let n = unsafe { libc::sysconf(libc::_SC_NPROCESSORS_ONLN) };
    if n > 0 { n as usize } else { fallback_cpu_count() }
}

SAFETY 注释不是形式主义，它要回答三个问题：

  1. 这个调用的前置条件是什么？（参数合法、指针有效、对齐……）
  2. 为什么当前上下文满足这些条件？
  3. 失败/边界情况怎么处理？

sysconf 的返回值 -1 就是边界情况：可能是「查询失败」，也可能是「配置无上限」。这里我们只关心 CPU 数，-1 一律回退。

23.5 非 Unix 的安全回退 ​

rust
#[cfg(not(unix))]
fn process_id() -> u32 { std::process::id() }

#[cfg(not(unix))]
fn cpu_count() -> usize { fallback_cpu_count() }

fn fallback_cpu_count() -> usize {
    std::thread::available_parallelism()
        .map(|n| n.get())
        .unwrap_or(1)
}

available_parallelism 返回 Result，因为某些沙箱环境可能拿不到；拿不到时保守返回 1——低估算不会造成并发 bug，只会慢一点。

source 字段让前端能看到实际路径：

rust
#[cfg(unix)]
fn source_name() -> &'static str { "libc (unsafe FFI)" }

#[cfg(not(unix))]
fn source_name() -> &'static str { "std (safe fallback)" }

23.6 对外只暴露安全函数 ​

rust
#[derive(Debug, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct HardwareInfo {
    pub pid: u32,
    pub cpu_count: usize,
    pub source: &'static str,
}

pub fn info() -> HardwareInfo {
    HardwareInfo { pid: process_id(), cpu_count: cpu_count(), source: source_name() }
}

命令层（system/mod.rs）：

rust
#[tauri::command]
pub fn system_hardware() -> hardware::HardwareInfo {
    hardware::info()
}

从 main.rs 注册后，前端「关于」弹窗多了一行：

ts
hardware.value = await invoke("system_hardware");
vue
<li v-if="hardware">
  <span>进程 / CPU</span>
  <b>PID {{ hardware.pid }} · {{ hardware.cpuCount }} 核</b>
</li>

unsafe 边界的工程含义：让不可审查的代码尽可能小、集中、可测试。业务层看到的只是普通结构体和普通函数。

23.7 FFI 检查清单 ​

接入任何 C 库前，按顺序确认：

检查项说明
头文件/ABI函数签名是否与 crate 声明一致（libc 已处理大部分）
参数合法性空指针、越界、非法枚举值
返回值语义-1 是错误还是合法值？errno 要不要读？
内存所有权谁分配、谁释放？跨 FFI 的 String/Vec 绝不能直接传
线程安全C 函数是否可重入？是否需要全局锁？
平台覆盖非目标平台是否 cfg 掉并提供回退？
测试至少一个 smoke test（本项目 info_is_sane）

23.8 什么时候真的需要 unsafe ​

  • 调用没有 Rust 绑定的系统 API / 硬件 SDK；
  • 极致性能的内联汇编或 SIMD（且已有充分基准）；
  • 实现底层数据结构（如自定义分配器）；
  • 与现有 C/C++ 代码库集成。

反过来，下面这些不需要 unsafe：

  • 读写文件、网络、JSON、数据库（标准库/crate 已封装）；
  • 共享状态（Arc<Mutex> / channel）；
  • 类型转换（as、TryFrom）；
  • 调用另一个 Rust crate。

经验法则：如果你的 unsafe 块超过 20 行，先想想能不能拆成更小的安全函数。

23.10 小结与课后练习 ​

本章你已完成：理解 unsafe 的边界与 SAFETY 注释规范；用 libc 调用 getpid / sysconf；用 target-specific dependency 与 cfg 提供跨平台回退；把 unsafe 收敛到一个可测试的安全模块，并通过命令暴露给前端。应用升级到 v0.22.0。

课后练习：

  1. 增加 memory_rss()：Unix 下读 /proc/self/statm（Linux）或 libc::getrusage，Windows 下用标准库回退；为它写 SAFETY 注释。
  2. 用 cargo clippy -- -W clippy::undocumented_unsafe_blocks 检查本项目，确认所有 unsafe 都有说明。
  3. 思考：为什么 libc::getpid() 可以标成「任何线程都安全」，而 libc::setenv() 不行？查一查 POSIX 的线程安全列表。
