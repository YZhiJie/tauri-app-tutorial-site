第 14 章 · 数据持久化进阶：SQLite 与全文搜索 ​

钳钳：「一个笔记一个 JSON 文件，就像把书散在地上——找起来全靠蹲着翻。本章我们把书搬进了带索引的图书馆：SQLite。」

本章学习目标 ​

  • 说清「JSON 文件存储」与「SQLite」各自的能力边界与选型时机
  • 用 sqlx 连接 SQLite，完成建表、CRUD 与异步命令改造
  • 用 FTS5 虚表 + 触发器实现中文可用的全文搜索
  • 用 PRAGMA user_version 实现「旧版 JSON 一次性迁移入库」
  • 理解「单一写入点」为什么让第 4 章的指纹冲突检测退役

14.1 为什么换存储引擎 ​

第 4 章的 JSON 方案很好教也很好懂，但有两个绕不开的天花板：

痛点JSON 文件方案SQLite 方案
搜索只能把全部笔记读进内存逐个 contains，数据量大就卡FTS5 倒排索引，毫秒级返回
并发安全靠指纹比对「事后发现冲突」再报错单一写入点 + 事务，冲突在机制上不存在
结构演进靠 #[serde(default)] 给老数据补字段PRAGMA user_version 版本闸门 + SQL 迁移

注意一个诚实的代价：SQLite 方案放弃了「用户可以直接用记事本改笔记」的开放性——数据库文件对普通用户是黑盒。笔记类应用这个代价几乎总是值得的。

🦀 钳钳的悄悄话

「单一写入点替代指纹检测」是本章最重要的架构观念：指纹比对是事后补救（改都改完了才发现被外部动过），数据库事务是事前预防（所有写入都经过同一个连接池排队执行）。能预防的问题，就不要留到事后检测。

14.2 引入 sqlx 并打开数据库 ​

Cargo.toml 加依赖：

toml
# 第 14 章：SQLite 持久化（sqlx 运行时查询；sqlite feature 自带 bundled 引擎，含 FTS5）
sqlx = { version = "0.8", default-features = false, features = ["runtime-tokio", "sqlite", "macros"] }

三个 feature 的分工：

  • runtime-tokio：异步运行时选 tokio（Tauri 内部也是 tokio，同一套线程池）；
  • sqlite：SQLite 驱动，自动编译内置 SQLite 引擎（bundled），用户机器上不需要装任何数据库；
  • macros：#[derive(FromRow)] 派生宏，把查询结果行自动装配成结构体。

新建 notes/db.rs，核心结构是一个持有连接池的托管状态：

rust
use sqlx::sqlite::{SqliteConnectOptions, SqlitePool};
use sqlx::FromRow;

/// 应用托管状态：一个连接池走天下
pub struct NotesDb {
    pool: SqlitePool,
}

impl NotesDb {
    /// 打开（必要时创建）数据库：建表建索引 -> 一次性迁移 -> 返回连接池
    pub async fn open(app: &AppHandle) -> Result<Self, AppError> {
        let dir = app.path().app_data_dir()
            .map_err(|e| AppError::disk("获取数据目录失败", e))?;
        fs::create_dir_all(&dir).map_err(|e| AppError::disk("创建数据目录失败", e))?;

        // create_if_missing：第一次运行时顺手建库文件，免去「先创建再连接」两步
        let options = SqliteConnectOptions::new()
            .filename(dir.join("aninotes.db"))
            .create_if_missing(true);
        let pool = SqlitePool::connect_with(options)
            .await
            .map_err(|e| AppError::db("连接数据库失败", e))?;

        let db = Self { pool };
        db.create_schema().await?;   // 幂等建表
        db.migrate_once(app).await?; // 旧 JSON 一次性迁移
        Ok(db)
    }
}

数据库文件放在 app_data_dir()/aninotes.db，与旧版 JSON 目录同根——迁移时好找邻居。

main.rs 的 setup 有个小障碍：setup 是同步闭包，而打开数据库是异步的。用 block_on 在启动时一次性跑完：

rust
.setup(|app| {
    // setup 是同步闭包，异步的数据库初始化用 block_on 一次性跑完
    let db = tauri::async_runtime::block_on(NotesDb::open(app.handle()))?;
    app.manage(db);
    // ...
})

14.3 建表：业务表 + FTS5 虚表 + 同步触发器 ​

schema 初始化全部用 IF NOT EXISTS，每次启动都跑一遍也安全（幂等）：

rust
sqlx::query(
    "CREATE TABLE IF NOT EXISTS notes (
        id         TEXT PRIMARY KEY,
        title      TEXT NOT NULL,
        content    TEXT NOT NULL,
        updated_at TEXT NOT NULL,
        version    INTEGER NOT NULL DEFAULT 1
    )",
)
.execute(&self.pool)
.await
.map_err(|e| AppError::db("创建 notes 表失败", e))?;

接下来是本章的主角——FTS5 全文索引：

rust
sqlx::query(
    "CREATE VIRTUAL TABLE IF NOT EXISTS notes_fts USING fts5(
        title,
        content,
        content = 'notes',
        content_rowid = 'rowid',
        tokenize = 'trigram'
    )",
)

三个关键选择，每个都有讲究：

  1. 外部内容模式（content = 'notes'）：正文只存在 notes 表一份，虚表只存倒排索引，不占双份空间；
  2. content_rowid = 'rowid'：虚表通过 SQLite 每张表自带的隐藏 rowid 与业务表对号入座；
  3. tokenize = 'trigram'：三元字符组分词。这是中文可搜的关键——默认的 unicode61 分词会把「今天天气不错」整段当成一个 token，搜「天气」永远搜不到；trigram 按 3 字符滑窗切分（「今天天」「天天天气」…），中英文都能子串匹配。

索引建好还不会自动更新，需要三个触发器保持同步：

rust
for stmt in [
    "CREATE TRIGGER IF NOT EXISTS notes_ai AFTER INSERT ON notes BEGIN
        INSERT INTO notes_fts(rowid, title, content)
        VALUES (new.rowid, new.title, new.content);
    END",
    "CREATE TRIGGER IF NOT EXISTS notes_ad AFTER DELETE ON notes BEGIN
        INSERT INTO notes_fts(notes_fts, rowid, title, content)
        VALUES ('delete', old.rowid, old.title, old.content);
    END",
    "CREATE TRIGGER IF NOT EXISTS notes_au AFTER UPDATE ON notes BEGIN
        INSERT INTO notes_fts(notes_fts, rowid, title, content)
        VALUES ('delete', old.rowid, old.title, old.content);
        INSERT INTO notes_fts(rowid, title, content)
        VALUES (new.rowid, new.title, new.content);
    END",
] {
    sqlx::query(stmt).execute(&self.pool).await
        .map_err(|e| AppError::db("创建同步触发器失败", e))?;
}

外部内容虚表的删除是 FTS5 的固定写法：往虚表 insert 一条第一列为 'delete' 的特殊记录。有了这个铁三角，业务代码只管 INSERT/UPDATE/DELETE notes 表，索引同步完全无感知。

14.4 一次性迁移：PRAGMA user_version ​

老用户升级后，数据还在 JSON 文件里。迁移要满足两条：只跑一次（重启不能把已删除的旧笔记复活）、可断点续传（中途失败下次还能再来）。SQLite 自带一个天然合适的工具：

rust
/// PRAGMA user_version 是 SQLite 自带的整型「模式版本」字段，默认为 0。
/// 0 -> 1：旧版 JSON 文件迁移入库，空库补种子数据。
async fn migrate_once(&self, app: &AppHandle) -> Result<(), AppError> {
    let (version,): (i64,) = sqlx::query_as("PRAGMA user_version")
        .fetch_one(&self.pool)
        .await
        .map_err(|e| AppError::db("读取数据库版本失败", e))?;
    if version >= 1 {
        return Ok(());
    }

    // ---- 旧版 JSON 迁移（没有旧数据时 load_all 返回空，天然跳过） ----
    if let Ok(storage) = NotesStorage::open(app) {
        for note in storage.load_all().unwrap_or_default() {
            self.insert_note(&note).await?;
        }
    }

    // ---- 空库补种子（首次安装的新用户） ----
    let (count,): (i64,) = sqlx::query_as("SELECT COUNT(*) FROM notes")
        .fetch_one(&self.pool).await
        .map_err(|e| AppError::db("统计笔记数量失败", e))?;
    if count == 0 {
        for note in default_seeds() {
            self.insert_note(&note).await?;
        }
    }

    sqlx::query("PRAGMA user_version = 1").execute(&self.pool).await
        .map_err(|e| AppError::db("写入数据库版本失败", e))?;
    Ok(())
}

storage.rs 随之瘦身成只读的迁移工具（只剩 open + load_all），store.rs（内存工作集 + 指纹比对）整个退役删除——数据源唯一了，内存缓存层没有必要存在。

14.5 CRUD 改造：从内存到 SQL ​

命令层全部改为 async fn，参数从 State<NotesStore> 换成 State<'_, NotesDb>，前端 invoke 调用方式一行都不用改（invoke 对同步/异步命令一视同仁）。以 update 为例：

rust
/// 更新笔记：version 由 SQL 原子自增；影响行数为 0 说明 id 不存在
pub async fn update(&self, id: &str, title: String, content: String) -> Result<Note, AppError> {
    let result = sqlx::query(
        "UPDATE notes SET title = ?1, content = ?2, updated_at = ?3, version = version + 1
         WHERE id = ?4",
    )
    .bind(&title)
    .bind(&content)
    .bind(js_now())
    .bind(id)
    .execute(&self.pool)
    .await
    .map_err(|e| AppError::db("更新笔记失败", e))?;

    if result.rows_affected() == 0 {
        return Err(AppError::NotFound(id.to_string()));
    }
    // 返回最新行（含自增后的 version），与旧内存模型的行为保持一致
    self.get(id).await?.ok_or_else(|| AppError::NotFound(id.to_string()))
}

两个细节：

  • ?1 ?2 参数绑定：sqlx 用位置参数，值走绑定通道而不是字符串拼接，SQL 注入在机制上不可能；
  • version = version + 1 在 SQL 里自增：原子操作，不依赖「先读出旧值再加一」的两步——这是把业务规则下沉到数据库的典型写法。

另一个变化在 error.rs：新增 Db 变体与 AppError::db() 构造器；Conflict 变体随指纹机制一起退役（单一写入点后这类冲突不可能再发生）。

14.6 全文搜索命令 ​

新命令 search_notes 里有一个诚实的产品决策：trigram 的最小匹配单元是 3 个字符，1~2 字符的短词必须回退 LIKE：

rust
/// 全文搜索：>= 3 字符走 FTS5，短词回退 LIKE
pub async fn search(&self, keyword: &str) -> Result<Vec<Note>, AppError> {
    let kw = keyword.trim();
    if kw.is_empty() {
        return self.list().await;
    }

    if kw.chars().count() < 3 {
        // 先转义 \ 再转义通配符 % 和 _，ESCAPE '\' 声明转义符，
        // 避免用户输入被 LIKE 当成通配语法
        let like = format!("%{}%",
            kw.replace('\\', "\\\\").replace('%', "\\%").replace('_', "\\_"));
        let rows = sqlx::query_as::<_, NoteRow>(
            "SELECT id, title, content, updated_at, version FROM notes
             WHERE title LIKE ?1 ESCAPE '\\' OR content LIKE ?1 ESCAPE '\\'
             ORDER BY updated_at DESC",
        ).bind(like).fetch_all(&self.pool).await
        .map_err(|e| AppError::db("搜索笔记失败", e))?;
        return Ok(rows.into_iter().map(Note::from).collect());
    }

    // 双引号把用户输入包成「短语」：引号、AND/OR、列名前缀等
    // 都不会被误当成 FTS5 查询语法，防「查询语法注入」
    let phrase = format!("\"{}\"", kw.replace('"', "\"\""));
    let rows = sqlx::query_as::<_, NoteRow>(
        "SELECT n.id, n.title, n.content, n.updated_at, n.version
         FROM notes_fts JOIN notes n ON n.rowid = notes_fts.rowid
         WHERE notes_fts MATCH ?1
         ORDER BY rank",
    ).bind(phrase).fetch_all(&self.pool).await
    .map_err(|e| AppError::db("搜索笔记失败", e))?;
    Ok(rows.into_iter().map(Note::from).collect())
}

两处「防注入」值得记住：

  1. LIKE 路径：用户输入的 %、_、\ 都要转义，否则 % 会变成通配符（搜 100% 会匹配所有含 100 的笔记）；
  2. FTS 路径：MATCH 有自己的查询语法（AND、OR、title:xxx），用户原样输入带这些字符的关键词会直接报错或语义错乱——用双引号包成短语，一切特殊字符失效。

ORDER BY rank：FTS5 内置的相关性评分，越匹配越靠前。

14.7 前端：搜索框与防抖编排 ​

前端改动很小——这正是「数据源换引擎，接口不变」的价值：

  • lib/core.ts 新增 searchNotes(keyword) 封装；
  • useNotes 新增搜索编排：300ms 防抖、searchResults 状态、visibleNotes 计算属性（搜索态显示结果，否则显示全量；浏览器 mock 本地过滤）；
  • NoteSidebar 加一个受控搜索框，输入事件上抛；
  • App.vue 把 :notes="visibleNotes" 和 @search="setKeyword" 接上线。

useNotes 里的核心片段：

ts
/** 搜索框输入：300ms 防抖，避免每个击键都打一次 IPC */
function setKeyword(kw: string) {
  keyword.value = kw;
  if (searchTimer) clearTimeout(searchTimer);
  searchTimer = setTimeout(() => void runSearch(), SEARCH_DEBOUNCE_MS);
}

/** 侧栏实际展示的列表：搜索态显示结果，否则显示全量 */
const visibleNotes = computed(() => {
  const kw = keyword.value.trim();
  if (!kw) return notes.value;
  if (isTauri()) return searchResults.value ?? [];
  const lower = kw.toLowerCase(); // 浏览器 mock：本地子串过滤
  return notes.value.filter(
    (n) => n.title.toLowerCase().includes(lower) || n.content.toLowerCase().includes(lower),
  );
});

还有一个小修正：refresh() 现在包 try/catch（list_notes 变成可失败的异步命令），并且搜索态下刷新会顺带重跑搜索——否则改完笔记，搜索结果列表里还是旧内容。

14.9 小结与课后练习 ​

本章你已完成：sqlx 接入与连接池托管；业务表 + FTS5 外部内容虚表 + 三个同步触发器；PRAGMA user_version 版本闸门实现 JSON → SQLite 一次性迁移；CRUD 全部 async 化；search_notes 命令与前端搜索框全链路。应用升级到 v0.13.0。

课后练习：

  1. 给搜索结果加高亮：FTS5 提供 highlight(notes_fts, 列号, '<mark>', '</mark>') 函数，让 search_notes 返回带 <mark> 标签的片段，前端用 v-html 渲染（注意：内容来自自己的数据库，没有 XSS 风险，但要想清楚为什么）。
  2. 笔记多了之后 list() 一次拉全量会变慢——给它加分页：SELECT ... ORDER BY updated_at DESC LIMIT ?1 OFFSET ?2，前端滚动到底自动加载下一页。
  3. 现在删除是「真删」。改成软删除：给 notes 表加 deleted_at TEXT 列（PRAGMA user_version 升到 2，迁移语句 ALTER TABLE notes ADD COLUMN deleted_at TEXT），删除变 UPDATE，列表查 WHERE deleted_at IS NULL。体会 user_version 递增迁移的完整流程。
