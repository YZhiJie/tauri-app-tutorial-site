第 38 章 · 运行时扩展：WASM 与插件沙箱 ​

钳钳：「插件能做什么，由宿主说了算；插件想做什么，不能由插件说了算。」

本章学习目标 ​

  • 比较 Rust 内置插件、WASM 模块、脚本语言三条扩展路线的取舍
  • 用 manifest 声明能力与资源预算，把「信任」变成可校验的结构
  • 在宿主侧实现清单校验与执行预算，拒绝未知能力与未知操作
  • 区分「字符预算」与「字节预算」，避免中文输入被误杀
  • 理解 WASM 接入时 fuel、epoch、内存上限与无 WASI 的意义
  • 为插件分发设计签名、版本与卸载边界

38.1 三条扩展路线 ​

路线代表隔离强度开发门槛典型场景
编译期 Rust 插件第 15 章的 note-stats无（同进程同权限）高官方维护的深度功能
WASM 模块wasmi / wasmtime强（线性内存 + 显式导入）中第三方算法、规则引擎
脚本语言JS/Lua/Rhai中（取决于解释器实现）低用户自定义小规则

三者不是互斥关系。成熟应用的常见组合是：核心功能用 Rust 插件，第三方扩展用 WASM，高级用户的自动化用脚本——但三者共用同一套「清单 + 能力 + 预算」契约。

本章先把契约与宿主校验写出来，执行器用纯文本操作占位；真正替换成 WASM 时，清单与 IPC 接口不用改。

38.2 信任模型：三句话 ​

  1. 能力是白名单：插件申请 fs.write，宿主不认识就拒绝，绝不「先授予再说」。
  2. 预算是双保险：插件自报上限，宿主再按硬上限收口。插件写 max_input_chars: 1000000 也没用。
  3. 接口无副作用：run 只接收字符串、只返回字符串。插件在类型层面就摸不到文件、网络与数据库。

警告：不要用「读取插件代码里有没有 std::fs」来判断安全性。字符串扫描永远可以被绕过；正确的边界是根本不把文件系统句柄交给插件。

38.3 清单即契约 ​

json

  "name": "大声插件",

38.4 宿主校验：先拒绝，再执行 ​

rust
fn validate_manifest(manifest: &PluginManifest) -> Result<(), AppError> {
    if !valid_plugin_id(&manifest.id) { /* 拒绝路径穿越式 id */ }
    if !valid_version(&manifest.version) { /* 只接受 major.minor.patch */ }
    if manifest.capabilities.is_empty() { /* 必须显式申请 */ }
    for capability in &manifest.capabilities {
        if capability != CAP_TEXT_TRANSFORM { /* 未知能力 */ }
    }
    // 操作数量、预算下限同样在这里检查
    Ok(())
}

见 [plugin_sandbox.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/plugin_sandbox.rs#L119-L158)。

校验顺序建议：结构 -> 身份 -> 能力 -> 规模 -> 内容。先把最便宜、最确定的检查做完，避免把恶意输入送进昂贵的分支。

id 的校验值得单独说：

rust
fn valid_plugin_id(id: &str) -> bool {
    let len = id.len();
    (3..=64).contains(&len)
        && id.chars().all(|c| c.is_ascii_lowercase() || c.is_ascii_digit() || c == '.' || c == '-')
        && !id.starts_with('.')
        && !id.starts_with('-')
}

见 [plugin_sandbox.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/plugin_sandbox.rs#L211-L219)。限制字符集的意义不只是「好看」：id 常被用作目录名、日志字段、配置键，允许 ../ 或空格会把这些下游假设全部打破。

38.5 执行与预算：字符不是字节 ​

中文用户最容易踩的坑：按 len()（字节数）限制输入，一个汉字占 3 字节，「最多 1000 字」瞬间变成 333 字。

rust
let input_chars = input.chars().count();
let input_limit = usize::min(HARD_MAX_INPUT_CHARS, manifest.budget.max_input_chars as usize);
if input_chars > input_limit {
    return Err(AppError::plugin(format!("输入过长：{input_chars} 字符，插件上限 {input_limit}")));
}

见 [plugin_sandbox.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/plugin_sandbox.rs#L84-L116)。

每一步操作后都重新检查输出预算：

rust
for op in &manifest.operations {
    output = apply_op(op, &output, output_limit)?;
    applied_ops.push(op.op.clone());
}

单个操作也要检查，因为一个 repeat 8 就能把 4KB 输入膨胀成 32KB。把检查放在「每次变换之后」而不是「全部做完之后」，才能在早期终止，避免中间结果先吃满内存。

硬上限做成常量：

rust
const HARD_MAX_INPUT_CHARS: usize = 16 * 1024;
const HARD_MAX_OUTPUT_CHARS: usize = 32 * 1024;
const HARD_MAX_OPERATIONS: usize = 16;

38.6 为什么 op 是字符串而不是枚举 ​

Rust 侧完全可以用 enum TextOp，但清单是跨版本、跨语言的产物。用字符串有两点好处：

设计旧宿主遇到新操作新宿主遇到旧清单
枚举（serde 反序列化）反序列化失败，错误信息含糊正常
字符串 + 宿主匹配明确报「未知操作：xxx」，可定位正常
rust
"repeat" => {
    let times = op.times.unwrap_or(1);
    if !(1..=8).contains(&times) {
        return Err(AppError::plugin(format!("repeat 次数超出范围：{times}")));
    }
    input.repeat(times as usize)
}
other => {
    return Err(AppError::plugin(format!("未知操作：{other}")));
}

见 [plugin_sandbox.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/plugin_sandbox.rs#L162-L194)。

未知操作必须报错而不是跳过。静默跳过会让插件作者以为功能生效了，排查成本远高于一次明确失败。

命令只做一层转发，参数是结构体：

rust

#[specta::specta]
pub fn run_plugin(manifest: PluginManifest, input: String) -> Result<PluginOutput, AppError> {

}

export async function runPlugin(manifest: PluginManifest, input: string): Promise<PluginOutput> {
  if (!isTauri()) return runPluginLocal(manifest, input);

  const result = await commands.runPlugin(manifest, input);
  if (result.status === "error") throw new Error(result.error);
  return result.data;
}

38.8 真正接入 WASM ​

把 apply_op 换成 WASM 调用，需要先回答四个问题：

问题推荐答案
运行时选谁追求小体积与易移植选 wasmi（纯 Rust 解释器）；追求极致性能选 wasmtime
允许导入什么什么都不导入。无 WASI，插件拿不到文件/网络/时钟
如何限制 CPUwasmi 用 fuel（指令预算）；wasmtime 用 fuel 或 epoch 中断
如何限制内存模块只暴露线性内存，宿主设置 memory.minimum/maximum

一个最小的 ABI 约定：

text
导入：无
导出：transform(input_ptr: i32, input_len: i32) -> i32
内存：插件自己的 linear memory，宿主读写前先校验边界

transform 返回一个指针，宿主按「指针 + 长度」读取结果，必须先校验 ptr + len <= memory.size，否则越界读取就是宿主替插件背锅。

rust
// 伪代码：宿主侧边界检查
let end = ptr as usize + len as usize;
if end > memory.data_size() {
    return Err(AppError::plugin("插件返回了越界指针"));
}

提示：不要给插件导入 host_log 之类的「方便函数」却忘了限流。日志同样可以撑爆磁盘，也能被用来做侧信道。导入的每一个函数都是新的攻击面。

清单结构可以原样复用，只把 operations 换成 module 字段：

json
{
  "id": "com.aninotes.ext.regex",
  "capabilities": ["text.transform"],
  "budget": { "maxInputChars": 4096, "fuel": 1000000, "maxMemoryPages": 16 },
  "module": { "path": "plugin.wasm", "sha256": "..." }
}

38.9 分发：签名、版本与卸载 ​

插件市场的底线要求：

  1. 签名：发布者用私钥签 manifest + wasm 的哈希，宿主用内置公钥验签（与第 8 章更新包的 minisign 思路一致）；
  2. 版本：清单里的版本只增不减，宿主记录「已安装版本」，拒绝降级；
  3. 权限变更提示：新版本申请了更多能力时，必须让用户重新确认，而不是静默升级；
  4. 可卸载：删除插件目录 + 清理其产生的数据。要求插件的数据必须落在宿主分配的命名空间里，不能写任意路径。
text
plugins/
  com.aninotes.ext.regex/
    manifest.json
    plugin.wasm
    data/            # 宿主分配，卸载时整体删除

警告：插件 id 是权限与数据的命名空间。一旦允许两个插件共用 id，卸载一个就会误删另一个的数据。注册时做全局唯一性检查。

38.10 常见报错速查 ​

现象原因处理
「未知能力」清单申请了白名单外的能力收敛 capabilities，或扩展宿主白名单
「插件 id 不合法」含大写、空格、/ 或 ..用小写 + 数字 + ./-，3~64 字符
「输入过长」但内容不多按字节而非字符统计用 chars().count()
「输出超限」某步操作膨胀过快降低 repeat 次数或输出预算
「操作步数超限」清单超过预算或硬上限合并操作，或申请更小范围的功能
插件执行后正文没变前端丢弃了返回值把 result.output 写回编辑状态
浏览器里能跑、桌面端被拒两套实现不一致以 Rust 校验为准，镜像只做演示
WASM 插件卡死界面没有 fuel/epoch 限制设指令预算，超限终止实例

38.11 小结与课后练习 ​

本章你已完成：用 manifest 声明插件能力与预算；实现宿主侧的清单校验与逐步预算检查；通过 IPC 暴露 run_plugin，让编辑器可以执行示例插件；梳理 WASM 运行时的选型、ABI、资源限制与分发要求。应用升级到 v0.37.0。

课后练习：

  1. 给 apply_op 增加 wrap { width }：按字符宽度折行，要求正确处理中英文混排，并补边界测试。
  2. 把 TextOp 改成 enum，比较「反序列化失败」与「未知操作」两种错误在用户体验上的差异。
  3. 用 wasmi 写一个最小 WASM 插件（输入反转字符串），接入 fuel 限制，并证明死循环会被终止。
  4. 设计插件签名的校验流程：签名覆盖哪些字节、公钥如何轮换、旧签名何时失效。
  5. 为插件数据设计命名空间与卸载清理逻辑，要求不触碰用户笔记与凭证库。
