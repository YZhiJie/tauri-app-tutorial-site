第 21 章 · 并发与异步：JoinSet、Semaphore 与原子计数 ​

小塔：「一条流水线不等于一个工人。让四只钳钳各搬各的，比一只钳钳来回跑快得多——前提是别让它们抢同一块地板。」

本章学习目标 ​

  • 理解 Tauri 的异步命令运行在什么运行时上，以及为什么文件 I/O 要 spawn_blocking
  • 用 JoinSet 管理一组动态并发任务，并处理任务 panic
  • 用 Semaphore 做有界并发，避免「100 个任务同时抢磁盘」
  • 用 AtomicUsize + 合适的 Ordering 统计完成数
  • 从多个并发任务向同一个 Channel 汇报进度，保证 UI 语义不变

21.1 从串行到并发：先算清瓶颈 ​

第 12 章的批量导出是一个 for 循环：

rust
for (i, note) in notes.iter().enumerate() {
    std::fs::write(path, body)?;
    on_progress.send(Progress { done: i + 1, title })?;
}

单条笔记的写入是毫秒级，但 1000 条就是秒级；而且这段循环跑在异步任务里，同步 std::fs::write 会阻塞 async worker——在导出期间，其他命令可能明显变慢。

两个优化方向：

  1. 把阻塞 I/O 移出异步线程：spawn_blocking；
  2. 并行写入：多条笔记的文件互不依赖，天然可并行。

但并行不能无脑开满：SSD 的随机写吞吐有上限，开 100 个线程只会互相拖慢，还吃掉内存。于是需要有界并发。

21.2 Tauri 的异步运行时与 spawn_blocking ​

Tauri v2 内部使用 tokio 运行时。async fn 命令会被扔到这个运行时上执行；sqlx 的查询本身是异步的，没有问题。但 std::fs 是同步 API，必须交给阻塞线程池：

rust
let total = tauri::async_runtime::spawn_blocking(move || {
    snapshot.iter().map(|n| count_words(&n.content)).sum()
})
.await?;

判断标准：调用栈里出现 std::fs / std::net（阻塞版）/ 长时间 CPU 计算，就 spawn_blocking。

21.3 JoinSet：管理「数量在运行期才知道」的任务 ​

tokio::task::JoinSet 是一组任务的集合：

rust
let mut set = tokio::task::JoinSet::new();
for note in notes {
    set.spawn_blocking(move || {
        // 写文件
        Ok::<String, AppError>(title)
    });
}

while let Some(joined) = set.join_next().await {
    let title = joined.map_err(|e| AppError::disk("导出任务异常终止", e))??;
    // 每完成一个就汇报一次
}

相比 Vec<JoinHandle>：

  • 不用手动保存句柄，任务完成即从集合移除；
  • join_next() 按完成顺序返回，而不是按 spawn 顺序——这正是进度条需要的语义；
  • JoinSet 被 drop 时会 abort 剩余任务：导出中途报错，不会留下后台线程继续写文件。

joined 的类型是 Result<Result<String, AppError>, JoinError>：

  • 外层 Err(JoinError)：任务 panic 或被取消；
  • 内层 Err(AppError)：业务失败（磁盘写不进去）。

两层都要处理，?? 正好展开。

21.4 Semaphore：有界并发的闸门 ​

如果只靠 JoinSet，上面那个循环会瞬间 spawn 1000 个阻塞任务。加一个信号量：

rust
const EXPORT_CONCURRENCY: usize = 4;

let gate = Arc::new(tokio::sync::Semaphore::new(EXPORT_CONCURRENCY));

for note in notes {
    // 先拿许可证；拿不到就在这里 await，形成天然背压
    let permit = gate.clone().acquire_owned().await
        .map_err(|e| AppError::disk("导出并发控制失败", e))?;

    set.spawn_blocking(move || {
        let _permit = permit; // 任务结束自动归还
        std::fs::write(&path, body)...
    });
}

关键点：

  • acquire_owned() 需要 Arc<Semaphore>，返回的 OwnedSemaphorePermit 可以移动进 'static 任务；
  • 许可证在任务闭包里被持有到结束，Drop 时自动 release；
  • 主循环在 acquire 处等待，等于「最多 4 个任务在飞，其余排队」。

🦀 钳钳的悄悄话

Semaphore 和 Mutex 的区别：Mutex 保护的是数据，同一时刻只能有一个访问者；Semaphore 限制的是并发度，允许 N 个任务同时做各自的事。别用 Mutex 去模拟并发限制——那会把并行退化成串行。

21.5 AtomicUsize：无锁计数 ​

进度计数只需要「加一」，没必要上锁：

rust
use std::sync::atomic::{AtomicUsize, Ordering};

let done = Arc::new(AtomicUsize::new(0));

// 每完成一个任务：
let n = done.fetch_add(1, Ordering::Relaxed) + 1;
on_progress.send(ExportProgress::Progress { done: n, title })?;

fetch_add 返回加之前的值，所以 +1 才是「当前完成数」。

Ordering 怎么选：

Ordering语义适用
Relaxed只保证原子性，不保证跨线程顺序单纯计数（本场景）
Acquire/Release建立同步关系发布数据、实现锁
SeqCst全局顺序不确定时的保守选择

进度数字不需要与其他内存操作建立 happens-before 关系，Relaxed 足够。不要因为「怕错」一律 SeqCst——那会白白损失性能，而且掩盖了对内存序的理解。

21.6 完整流程复盘 ​

text
list_notes
   │
   ▼
Started { total }
   │
   ├─ for note in notes
   │     ├─ acquire_owned()  ← 背压：最多 4 个在飞
   │     ├─ exporter.render(note)  ← 纯 CPU，小活
   │     └─ JoinSet::spawn_blocking(写文件 + 归还许可证)
   │
   ├─ join_next() 循环
   │     ├─ 取出完成的任务（完成顺序）
   │     ├─ fetch_add 计数
   │     └─ Channel.send(Progress { done, title })
   │
   ▼
Finished

前端完全不需要改：它依旧收到 started → progress × N → finished。并发是后端实现细节，IPC 契约保持稳定——这是分层设计带来的好处。

21.7 并发代码的测试策略 ​

并发正确性很难靠「跑一遍看看」验证。可落地的检查顺序：

  1. 单元测试测纯逻辑：exporter.render 的输入输出；
  2. 集成测试测结果：导出到临时目录，断言文件数量与内容（不关心顺序）；
  3. 压力测试：临时把 EXPORT_CONCURRENCY 调到 64、笔记数调到 5000，观察内存与耗时；
  4. 工具辅助：cargo miri（检测 UB）、loom（模型化并发）、tokio-console（看任务阻塞）。

本项目的 cargo test 目前覆盖前两层；压力测试留作课后练习。

21.9 小结与课后练习 ​

本章你已完成：把同步文件 I/O 移入 spawn_blocking；用 JoinSet 管理动态并发任务并按完成顺序汇报；用 Semaphore 实现有界并发；用 AtomicUsize::Relaxed 无锁计数；保持前端 IPC 契约不变。应用升级到 v0.20.0。

课后练习：

  1. 把并发度做成设置项（1/2/4/8），在「关于」弹窗里切换，比较不同笔记量下的耗时。
  2. 给导出加一个「取消」按钮：命令接收 CancellationToken（tokio-util），JoinSet drop 时自动 abort。
  3. 用 tokio::time::timeout 包住单个写文件任务，卡住超过 5 秒就记为失败并继续——思考「部分成功」的语义该怎么向用户表达。
