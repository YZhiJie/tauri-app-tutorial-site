第 31 章 · 类型安全 IPC 契约生成 ​

钳钳：「前后端最有默契的时候，不是开会，是编译。让 Rust 签名直接生成 TypeScript，吵不起来。」

本章学习目标 ​

  • 看清手写 invoke("命令名") 会在哪三处悄悄漂移
  • 把 Rust 命令签名当成 IPC 的唯一事实源
  • 接入 tauri-specta，让命令注册与类型导出共用同一份清单
  • 读懂生成的 ipc-bindings.ts：commands 对象、DTO 类型与 typedError
  • 避开 Specta 的 BigInt 禁区，把对外计数收窄为 u32
  • 用一条 git diff 把契约漂移挡在合并之前

31.1 手写 invoke 的三处漂移 ​

前 30 章里，前端调用后端一直长这样：

ts
await invoke("create_note", { title, content });
await invoke("stream_notes", { batchSize, onEvent: channel });

它能在浏览器里跑，也能收到结果，但契约是靠人记的。只要有一个人改 Rust 侧，就会出现三类漂移：

漂移点表现发现时机
命令名"create_note" 写成 "createNote"运行时「命令未找到」
参数名Rust batch_size，前端写 batchSize 或 batch_size运行时参数反序列化失败
返回类型后端把 Version 从 number 改成 string前端 .version + 1 静默变成字符串拼接

最麻烦的是第三类：它不报错，只是算错。等你发现「笔记版本号变成 011」时，已经发过两个版本了。

第 12 章我们讲过 IPC 的序列化边界，但那次只解决了「怎么传」；本章解决「传的东西怎么保证两边一致」。

31.2 单一事实源：谁说了算 ​

一个双向契约必须有唯一事实源。选 Rust，理由很实在：

text
Rust 命令签名（唯一事实源）
        │
        ├──► 运行时：invoke_handler 分发
        │
        └──► 编译期：导出 ipc-bindings.ts
                        │
                        ▼
            前端 commands.xxx() 调用

如果反过来以 TypeScript 为准，就得在 Rust 侧手写校验、手写反序列化，等于把 Tauri 已经做好的事重做一遍，还更容易漏。

原则：Rust 改签名是「改契约」，前端类型是产物，不是源码。

31.3 接入 tauri-specta ​

依赖不算多，但必须锁死版本：

toml
# 第 31 章：IPC 契约生成。用命令签名反射出 TypeScript 绑定，
# 前端不再手写命令名与参数名。specta 仍是 rc 版本，必须用 `=` 精确锁定，
# 否则 rc 之间的破坏性变更会让构建随机失败。
specta = { version = "=2.0.0-rc.26", features = ["derive"] }
specta-typescript = "0.0.13"
tauri-specta = { version = "=2.0.0-rc.26", features = ["derive", "typescript"] }

见 [Cargo.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/Cargo.toml#L74-L80)。

提示：2.0.0-rc.* 之间不是语义化兼容关系。今天 collect_commands! 支持宏路径，下个 rc 可能就要求换写法。教学项目可以跟最新 rc，但生产项目要把版本写进升级清单，每次升级都跑一遍契约测试。

31.4 标注命令与数据结构 ​

collect_commands! 只能看到被标注过的函数。于是两条规则：

  1. 每个命令加 #[specta::specta]（它必须和 #[tauri::command] 并列）；
  2. 每个出现在签名里的自定义类型加 #[derive(specta::Type)]。

以流式读取为例：

rust
#[derive(Debug, Clone, Serialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct NotesBatch {
    pub offset: u32,
    pub total: u32,
    pub notes: Vec<Note>,
}

#[tauri::command]
#[specta::specta]
pub async fn stream_notes(
    db: State<'_, NotesDb>,
    batch_size: Option<u32>,
    on_event: Channel<NotesBatch>,
) -> Result<u32, AppError> {
    // ...
}

见 [stream.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/stream.rs#L28-L51)。

注意 State / AppHandle / Channel 的处理：前两个由 Tauri 注入，不会出现在 TypeScript 参数表里；Channel<T> 会映射成 Channel<T> 类型，前端照样要自己 new Channel()。

错误类型也要交代清楚。AppError 本身是枚举，但前端从来只收到一条中文消息，所以手写一个「等价于 string」的 Type 实现：

rust
impl specta::Type for AppError {
    fn definition(types: &mut specta::Types) -> specta::datatype::DataType {
        <String as specta::Type>::definition(types)
    }
}

见 [error.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/error.rs#L73-L82)。

警告：不要为了「信息更全」把 AppError 直接导成枚举。#[derive(IpcError)] 的序列化行为就是 Display 文本；如果 Specta 导出的是枚举结构，前端类型会和运行时数据对不上，比没有绑定更危险。

31.5 唯一注册点：specta_builder ​

命令清单过去写在 generate_handler![...] 里，现在抽成一个函数：

rust
fn specta_builder() -> Builder<tauri::Wry> {
    Builder::<tauri::Wry>::new().commands(collect_commands![
        crash::diagnostics,
        crash::report_frontend_error,
        perf::perf_snapshot,
        perf::report_frontend_ready,
        vault::vault_unlock,
        // ... 共 23 个命令
        export_all_notes,
        close_quick_capture
    ])
}

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L174-L207)。

这个函数同时承担三件事：

用途调用点生效时机
运行时分发.invoke_handler(specta.invoke_handler())每次前端 invoke
事件挂载specta.mount_events(app)setup 中执行一次
类型导出specta.export(...)debug 启动 / 契约测试

为什么只留一个注册点：如果运行时用 generate_handler!、导出用另一份清单，两份清单迟早不同。让它们共享 specta_builder()，遗漏一个命令就会同时表现为「命令不可用」和「绑定缺失」，一眼能看出来。

原来的 generate_handler![...] 已经删除——加新命令时只需要改这一处。

31.6 生成物长什么样 ​

在 app 目录下执行一次导出，会得到 [ipc-bindings.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/ipc-bindings.ts)：

ts
export const commands = {
  greet: (name: string) => __TAURI_INVOKE<string>("greet", { name }),
  searchNotes: (keyword: string) =>
    typedError<Note_Serialize[], string>(
      __TAURI_INVOKE("search_notes", { keyword })
    ),
  streamNotes: (batchSize: number | null, onEvent: Channel<NotesBatch_Deserialize>) =>
    typedError<number, string>(
      __TAURI_INVOKE("stream_notes", { batchSize, onEvent })
    ),
};

三个细节值得逐条看：

  1. 命令名是 camelCase：Rust search_notes → TS searchNotes，但底层 invoke 仍传 "search_notes"。前端不用记两套命名。
  2. Option<u32> → number | null：Rust 的 None 到这里就是 null，不会再变成 undefined 让你写两种判断。
  3. Result<T, E> → typedError<T, E>：返回判别联合，而不是把错误抛成 any。

typedError 的实现是生成器附带的运行时小函数：

ts
async function typedError<T, E>(result: Promise<T>) {
  try {
    return { status: "ok", data: await result };
  } catch (e) {
    if (e instanceof Error) throw e;
    return { status: "error", error: e as any };
  }
}

于是调用端必须先窄化：

ts
const result = await commands.searchNotes(keyword);
if (result.status === "error") throw new Error(result.error);
return result.data;

result.error 的类型就是 AppError 导出成的 string，与第 11 章的错误消息链路完全一致。

31.7 前端怎么消费 ​

改造后的 [core.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/core.ts#L13-L40) 只多了一行 import，少了一堆字符串：

ts
import { isTauri } from "@tauri-apps/api/core";
import type { Note } from "../types";
import { commands } from "./ipc-bindings";

export async function greet(name: string): Promise<string> {
  if (!isTauri()) {
    await delay(150);
    return `你好，${name}！（浏览器 mock：装上 Tauri 后这里会收到 Rust 的回复）`;
  }
  return commands.greet(name);
}

export async function searchNotes(keyword: string): Promise<Note[]> {
  if (!isTauri()) return [];
  const result = await commands.searchNotes(keyword);
  if (result.status === "error") throw new Error(result.error);
  return result.data;
}

浏览器降级分支保留：commands 在非 Tauri 环境调用会直接失败，所以 isTauri() 判断仍要在最前面。

边界：生成的 commands 只覆盖命令，不覆盖事件。listen("notes-changed") 的事件名与 payload 仍是手写契约——第 22 章那个宏只统一了「怎么广播」，没统一「广播什么类型」。想连事件也纳入契约，需要用 tauri-specta 的 typed event（本章暂不引入，留给读者练习）。

31.8 BigInt 禁区：把 usize 收窄成 u32 ​

第一次导出绑定，大概率会撞上这条错误：

text
error: BigInt-style types (u64, i64, usize, ...) are not allowed in TypeScript

原因：JavaScript 的 number 只有 53 位安全整数，而 usize / u64 是 64 位。Specta 拒绝静默降精度，宁可让导出失败。

Rust 类型能否直接导出处理方式
u32 / i32 / f64可以直接用
usize / isize不可以收窄为 u32（计数、下标）
u64 / i64不可以收窄，或转成 String（时间戳、ID）
Option<T>看 TNone → null

本章的收窄清单：

rust
// 对外 DTO
pub struct NotesBatch { pub offset: u32, pub total: u32, ... }
pub struct VaultStatus { pub entries: u32, ... }
pub struct HardwareInfo { pub cpu_count: u32, ... }
pub enum ExportProgress {
    Started { total: u32 },
    Progress { done: u32, title: String },
}

// 命令返回值
pub async fn word_count(...) -> Result<u32, AppError> { ... }

内部计算仍用 usize（Rust 集合长度天然是 usize），只在「跨 IPC 边界」处 as u32。见 [commands.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/commands.rs#L110-L123) 与 [vault.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/vault.rs#L44-L49)。

提示：as u32 在超过 42 亿时会截断。笔记条数到不了这个量级，但「用户传给后端的 ID」别这么转——那种场景应该用 String，既保精度又避开 JS 大整数。

31.9 契约漂移门禁 ​

绑定文件是生成物，但它必须进仓库。否则 CI 没有基准可比，新克隆的仓库也要先跑一次程序才能编译前端。

于是加一个只做导出的测试：

rust
#[cfg(test)]
mod contract_tests {
    /// 契约快照测试：重新导出绑定，交给 CI 用 `git diff` 判断是否漂移。
    #[test]
    fn export_ipc_bindings() {
        let builder = super::specta_builder();
        builder
            .export(
                specta_typescript::Typescript::default(),
                "../src/lib/ipc-bindings.ts",
            )
            .expect("导出 IPC 契约失败");
    }
}

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L209-L225)。

CI 里紧接 cargo check 执行：

yaml
- name: 校验 IPC 契约未漂移
  run: |
    cargo test --bin aninotes export_ipc_bindings
    git diff --exit-code -- ../src/lib/ipc-bindings.ts

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L52-L58)。

这条门禁的语义是：

  • Rust 签名改了、绑定也重新生成并提交 → git diff 为空，通过；
  • Rust 签名改了、忘了提交绑定 → 测试把文件改回新内容，git diff 非空，失败；
  • 前端手改绑定文件 → 测试重新生成后覆盖，git diff 非空，失败。

不要给生成文件加 --no-verify 或把它放进 .gitignore：它不是缓存，是契约的版本快照。

31.10 渐进迁移与边界 ​

本章只迁移了 core.ts 的两条命令。剩下的调用点可以按这个顺序推进：

  1. 先迁「参数多、返回结构复杂」的命令（export_all_notes、stream_notes）——它们最容易漂移；
  2. 再迁「只有一个字符串参数」的命令（greet、delete_note）——收益小但顺手；
  3. 最后删掉 src/types.ts 里与生成类型重复的定义，改为 export type Note = Note_Serialize 之类的别名。

两个不要做：

  • 不要保留两套类型。手写 Note 与生成 Note_Serialize 并存，等于把漂移从命令层搬到了类型层。
  • 不要在前端重新拼命令名。有了 commands 还写 invoke("xxx")，等于门禁只管一半。

Channel 参数目前仍需前端显式构造，生成器只保证泛型类型对得上。这是下一层「事件契约」的入口，不属于本章范围。

31.11 常见报错速查 ​

现象原因解决
error: BigInt-style types ...签名里含 usize / i64 / u64收窄为 u32，或改 String
生成的 commands 里少了某个命令没加 #[specta::specta] / 没进 collect_commands!两处都补上
Type \X` does not implement specta::Type`DTO 缺 #[derive(specta::Type)]给结构体/枚举加派生
前端拿到 {status:"error"} 但 error 是对象错误类型导成了枚举手写 impl Type 映射为 String
参数在 Rust 里收不到前端按 snake_case 传了生成器用 camelCase，照签名传
CI 报 git diff 非空改了签名没提交绑定本地跑契约测试并提交 ipc-bindings.ts
debug 启动报「导出 IPC 契约失败」相对路径基于 src-tauri 工作目录从 app/src-tauri 启动，或用绝对路径

31.12 小结与课后练习 ​

本章你已完成：接入 tauri-specta；把 23 个命令收进唯一注册点；让 DTO 与错误类型进入 TypeScript 绑定；用 commands 替换手写 invoke；把 BigInt 禁区收窄为 u32；用契约测试 + git diff 建立漂移门禁。应用升级到 v0.30.0。

课后练习：

  1. 给 notes-changed 事件加类型：用 tauri-specta 的 typed event，让 listen 的 payload 也来自生成文件。
  2. 写一个脚本，在 pre-commit 里跑 cargo test --bin aninotes export_ipc_bindings，漂移时直接阻止提交。
  3. 把 src/types.ts 中的 Note 改为生成类型的别名，确认 vue-tsc 仍能通过，并记录哪些字段的可选性发生了变化。
