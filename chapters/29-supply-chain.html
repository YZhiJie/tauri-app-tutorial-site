第 29 章 · 供应链审计与签名公证 ​

钳钳：「你的应用有多少行代码不重要，重要的是你信任了多少别人的代码。」

本章学习目标 ​

  • 画出桌面应用的完整供应链：依赖、构建工具链、产物、分发渠道
  • 用 cargo audit / cargo deny / pnpm audit 建立依赖门禁
  • 理解许可证白名单与来源限制为什么也属于安全
  • 分清「代码签名」「公证」「更新包签名」三种不同的信任机制
  • 把签名密钥关进 CI Secret，并设计轮换与撤销流程

29.1 供应链不只是「依赖列表」 ​

一个安装包到达用户手中，中间经过了这些环节：

text
源码
 │  git / 依赖声明
 ▼
依赖树（crates.io + npm）──► 已知漏洞 / 恶意包 / 许可证冲突
 │  cargo / pnpm / vite
 ▼
构建工具链（rustc / node / tauri-cli）──► 被替换的编译器 / 缓存投毒
 │  打包 + 签名
 ▼
产物（.dmg / .msi / .AppImage）──► 未签名 / 证书过期 / 私钥泄露
 │  上传
 ▼
分发渠道（GitHub Releases / 商店）──► 更新包被换 / 下载源劫持

每一层都可能出错。本章只做两件事：把可自动化的检查放进 CI；把人工签名流程写清楚。

29.2 四个真实攻击面 ​

攻击面手法后果防线
依赖投毒typosquatting、维护者账号被盗恶意代码进入构建锁文件 + 审计 + 来源限制
构建脚本build.rs / postinstall 执行任意命令构建机被控评审新增依赖、最小权限 CI
签名证书证书泄露、过期、被吊销用户无法验证来源私钥只放 CI Secret、监控有效期
更新通道替换更新包 / 篡改清单任意代码执行更新包 minisign 验签

最常见也最容易被忽略的是第一项：一个从没听过的 crate，可能只是为了改一个字符串就被引入。

29.3 三个审计命令 ​

cargo audit ​

只读 Cargo.lock，对照 RustSec 漏洞数据库：

bash
cd app/src-tauri
cargo audit

输出会按 severity 分组。注意它不编译代码，所以很快，适合每次提交都跑。

cargo deny ​

[deny.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/deny.toml) 一次检查四个维度：

bash
cargo deny check
维度配置段作用
漏洞[advisories]有公告即失败；未维护仅警告
许可证[licenses]只允许白名单内的宽松许可证
依赖形态[bans]禁止通配符版本、提示重复版本
来源[sources]只允许 crates.io 与显式 git 源

为什么要管许可证：一个 GPL 依赖可能要求你开源整个应用；一个未知许可证的包可能根本没有授权。这是法律风险，也是供应链风险。

pnpm audit ​

bash
cd app
pnpm audit --audit-level high

前端依赖同样有漏洞。配合 pnpm install --frozen-lockfile，保证 CI 安装的版本与本地完全一致——锁文件被改动却没有提交，会直接失败。

29.4 CI 里的安全任务 ​

新增 [.github/workflows/security.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/security.yml)，与 ci.yml 并行存在：

yaml
on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: "0 3 * * 1"   # 每周一，漏洞库更新后主动跑

三个设计点：

  1. 定时任务：代码没变，但漏洞数据库每天更新。只靠 push 触发会漏掉「新披露的旧漏洞」。
  2. 只读权限：permissions: contents: read，安全扫描任务不需要写仓库。
  3. 失败即拦截：高危漏洞和许可证违规都让 PR 变红，而不是只发一条通知。

为什么不把安全扫描塞进 ci.yml：两者失败的含义不同。编译失败是「改坏了」，审计失败是「依赖世界变了」。分开的任务更容易判断该找谁。

29.5 代码签名、公证、更新签名：三件不同的事 ​

初学者最容易把这三件事混为一谈：

机制解决什么问题谁验证平台
代码签名安装包确实来自你，且未被修改操作系统macOS / Windows
公证（notarization）Apple 已扫描过这个包GatekeepermacOS
更新包签名更新内容确实由持有私钥的人签发应用自身全平台（minisign）

macOS：签名 + 公证 ​

Tauri 读取这些环境变量完成签名与公证：

bash
export APPLE_CERTIFICATE="<base64 的 .p12>"
export APPLE_CERTIFICATE_PASSWORD="<证书口令>"
export APPLE_SIGNING_IDENTITY="Developer ID Application: Your Name (TEAMID)"
export APPLE_ID="you@example.com"
export APPLE_PASSWORD="<App 专用密码>"
export APPLE_TEAM_ID="TEAMID"

然后：

bash
cd app
pnpm tauri build

产物会带上签名，并自动提交公证。证书口令与 App 专用密码只能放 CI Secret，永远不要写进仓库、脚本或文档。

Windows：Authenticode ​

需要代码签名证书（EV 证书可立即获得 SmartScreen 信誉）。Tauri 支持通过 certificateThumbprint / digestAlgorithm / timestampUrl 配置。时间戳服务很关键：证书过期后，带时间戳的旧签名仍然有效。

Linux：没有统一体系 ​

多数发行版靠仓库签名或 AppImage 自带校验。至少应发布 SHA-256 校验和，并在 Release 页面注明。

29.6 更新包签名：最后一道门 ​

第 8 章的 updater 已经配置了公钥：

json
"updater": {
  "pubkey": "dW50cnVzdGVkIGNvbW1lbnQ6...",
  "endpoints": ["https://github.com/.../{{target}}-{{arch}}.json"]
}

更新流程的信任链是：

text
CI 用私钥签名更新包
        │
        ▼
用户端下载 .tar.gz + .sig
        │
        ▼
应用用内置公钥验签 ──失败──► 拒绝安装
        │成功
        ▼
替换并重启

关键点：公钥可以公开，私钥必须离线或只存在 CI Secret。 私钥泄露等于任何人都能给你的用户推送任意程序，比代码签名泄露更危险——更新通道是持续性的。

29.7 密钥托管与轮换 ​

密钥存放轮换周期泄露后的动作
macOS 签名证书CI Secret（base64）按证书有效期吊销证书、重新签名发布
Windows 证书CI Secret / HSM1~3 年吊销、联系 CA
更新私钥CI Secret（最好离线备份）每年或人员变动换公钥需要发一次「带旧签名的过渡版本」
npm / crates tokenCI Secret90 天立即 revoke

更新公钥轮换是唯一麻烦的一项：客户端内置的是旧公钥，你无法用新私钥签一个它能接受的更新。实践做法是先用旧私钥发布一个内置新公钥的版本，等用户升级后，再切换到新私钥。

29.8 产物校验与 SBOM ​

除了签名，还应该让用户能核对「下载的东西没坏」：

bash
shasum -a 256 AniNotes_0.28.0_aarch64.dmg

把校验和写进 Release notes。更进一步可以生成 SBOM（软件物料清单）：

bash
cargo install cargo-cyclonedx
cargo cyclonedx --format json

SBOM 的价值在事后：当某个依赖爆出漏洞时，你能立刻回答「哪个版本的应用用了它」。

29.9 常见报错速查 ​

现象原因解决
cargo audit 报未维护 crate依赖长期不更新评估替换；急用时在 ignore 里写原因与期限
cargo deny 许可证失败新依赖是 GPL/未知协议换依赖，或在 allow 列表显式评审后加入
pnpm audit 失败但本地正常锁文件与安装不一致提交 pnpm-lock.yaml，CI 用 --frozen-lockfile
macOS 公证失败App 专用密码 / Team ID 错误重新生成专用密码；确认证书类型是 Developer ID
Windows 签名后仍被 SmartScreen 拦新证书没有信誉积累使用 EV 证书；保持稳定签名主体
更新验签失败公钥与私钥不匹配 / 包被改重新生成密钥对，走过渡版本流程

29.10 小结与课后练习 ​

本章你已完成：画出从源码到分发的供应链；添加 cargo-deny 配置；新增独立的安全扫描工作流（含每周定时）；区分代码签名、公证与更新签名；写下三类密钥的托管与轮换规则；补充校验和与 SBOM 的实践。应用升级到 v0.28.0。

课后练习：

  1. 在本地安装 cargo-audit 并跑一次，把输出里的 warning 按「可升级 / 需替换 / 可忽略」分类。
  2. 给 security.yml 增加一个「证书有效期检查」步骤（可用 openssl x509 -enddate 读取证书）。
  3. 写一份 200 字的更新私钥泄露应急流程：先做什么、后做什么、如何通知用户。
