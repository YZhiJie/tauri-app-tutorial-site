第 33 章 · 多平台 CI 矩阵与缓存 ​

钳钳：「『在我机器上能编译』不是证据。让三个操作系统同时点头，才算证据。」

本章学习目标 ​

  • 理解为什么桌面应用的 CI 必须覆盖真实操作系统，而不只是 Linux
  • 用 strategy.matrix 把同一套步骤铺到 macOS / Windows / Linux
  • 用 if 条件处理平台专属依赖，避免复制三份 workflow
  • 设计「OS + 工具链 + 锁文件」的缓存键，并理解 restore-keys 的作用
  • 用 concurrency、timeout-minutes、fail-fast 控制反馈速度与成本
  • 分清哪些步骤必须全平台跑，哪些只跑一次就够了

33.1 为什么不能只测 Linux ​

桌面应用的代码里到处是平台分支：

rust
#[cfg(unix)]
fn set_private_permissions(path: &Path) -> Result<(), AppError> { /* 0o600 */ }

#[cfg(not(unix))]
fn set_private_permissions(_path: &Path) -> Result<(), AppError> { /* ACL */ }

在 macOS 上写代码、在 Linux 上跑 CI，最典型的翻车方式是：

  • Windows 分支长期没人编译，cfg 里的类型错误攒了三个月；
  • 托盘、全局快捷键、文件关联的 API 在某个平台根本不存在；
  • 路径分隔符、大小写敏感、文件名保留字只在打包时才暴露。

这些都不是「写错了」，而是「另一个平台没编译过」。矩阵就是让每个平台都真实编译一次。

33.2 一个矩阵，三个操作系统 ​

yaml
rust:
  strategy:
    fail-fast: false
    matrix:
      os: [ubuntu-latest, windows-latest, macos-latest]
  runs-on: ${{ matrix.os }}
  timeout-minutes: 40

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L26-L40)。

三个参数值得解释：

配置作用本章取值
matrix.os生成三个并行 job三平台
fail-fast一个失败是否取消其他false，一次看全
timeout-minutes防止卡死烧满额度40 分钟

fail-fast: false 是刻意的：如果 Windows 挂了，你仍然想看到 macOS 是否也挂。修完一个再等一轮，反馈周期会翻倍。

提示：矩阵维度不要乱加。os × rust 版本 × feature 很快会变成 18 个 job。只把「真的会改变编译结果」的维度放进矩阵，其余用固定版本。

33.3 平台专属步骤：用 if，不要复制 job ​

Linux 需要 WebKitGTK 等系统库，Windows 与 macOS 不需要：

yaml
- name: 安装 Linux 系统依赖
  if: runner.os == 'Linux'
  run: |
    sudo apt-get update
    sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L47-L53)。

三种写法的成本对比：

写法维护成本适用场景
三个独立 job步骤改一次要同步三处平台步骤差异极大
一个 job + if一处维护90% 步骤相同（本章）
复合 Action需要额外仓库/目录跨仓库复用

runner.os 的取值是 Linux / Windows / macOS，注意大小写与 matrix.os 的 ubuntu-latest 不同。

33.4 哪些步骤只跑一次 ​

矩阵的代价是重复。把与平台无关的检查收敛到单个 runner：

yaml
# 绑定文件与平台无关，只在 Linux 上跑一次
- name: 校验 IPC 契约未漂移
  if: runner.os == 'Linux'
  run: |
    cargo test --bin aninotes export_ipc_bindings
    git diff --exit-code -- ../src/lib/ipc-bindings.ts

# clippy 规则基本一致，Linux 足够覆盖
- name: cargo clippy
  if: runner.os == 'Linux'
  run: cargo clippy --workspace -- -D warnings

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L71-L86)。

判断标准：这一步的输入是否依赖操作系统？

  • 生成 TypeScript 绑定：不依赖 → 跑一次；
  • cargo check / cargo test：依赖 → 全平台；
  • 打包 .dmg / .msi / .AppImage：强依赖 → 留给 release 矩阵。

33.5 缓存的三层结构 ​

一次冷启动的 Rust 构建，时间大致花在：

text
下载 crates         ██████
编译依赖（几百个）  ████████████████████████
编译本项目          ███

缓存要解决的正是中间那块。需要缓存三类目录：

目录内容变化频率
~/.cargo/registry下载的 crate 源码低（锁文件变化时）
~/.cargo/gitgit 依赖低
app/src-tauri/target编译产物高（源码变化）

Swatinem/rust-cache@v2 把这三类都接住了：

yaml
- uses: Swatinem/rust-cache@v2
  with:
    workspaces: app/src-tauri -> target
    cache-on-failure: true

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L55-L61)。

workspaces 的写法是「工作目录 -> target 目录」，多个 workspace 用换行分隔。

cache-on-failure: true 值得开：构建失败时，失败之前的依赖编译仍然有效。下一次修好代码，不必从零重编。

33.6 缓存键：精确命中与部分命中 ​

如果手写 actions/cache，键的设计决定了命中率：

yaml
key: ${{ runner.os }}-cargo-${{ hashFiles('app/src-tauri/Cargo.lock') }}
restore-keys: |
  ${{ runner.os }}-cargo-

两段式设计的含义：

  • 精确键：OS + 锁文件哈希。锁文件没变 → 完整命中，秒级恢复；
  • 前缀键：锁文件变了 → 退而求其次恢复旧缓存，再增量编译新增依赖。

Swatinem/rust-cache 在内部做了更细的拆分（按 rustc 版本、target、profile），并会自动跳过明显不该缓存的内容。

警告：不要用 key: cargo 这种常量键。缓存一旦写入就不会更新，依赖升级后你会一直用旧产物，出现「本地能编、CI 编不过」的幽灵问题。

33.7 并发、超时与成本 ​

三个并行 runner 的账单是单机的三倍。两个配置能把浪费压下来：

yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

同一分支连续推送时，旧一轮直接取消。对「推一版、改个错别字、再推一版」的日常操作，这能省掉一半机器时间。

timeout-minutes 则防止某个步骤卡在交互式提示或网络重试上：

  • 默认超时是 6 小时，足够烧掉当月额度；
  • Rust 项目冷构建通常 10~20 分钟，40 分钟是安全上限；
  • 前端与文档 job 可以设 15 分钟。

33.8 矩阵测试：让平台差异在测试里说话 ​

CI 矩阵只保证「能编译」。再补一条平台测试，把假设写进代码：

rust
#[test]
fn exactly_one_supported_platform() {
    let matched = [
        cfg!(target_os = "macos"),
        cfg!(target_os = "windows"),
        cfg!(target_os = "linux"),
    ]
    .into_iter()
    .filter(|hit| *hit)
    .count();
    assert_eq!(matched, 1, "只支持 macOS / Windows / Linux");
}

见 [platform_matrix.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/tests/platform_matrix.rs#L8-L19)。

它验证的是「当前编译目标在支持列表里」。如果以后有人在矩阵里加了 ubuntu-latest-arm，或误用了 cfg(target_arch)，这条断言会先提醒你。

同文件的 target_is_64_bit 与 unix_permissions_are_gated_by_cfg 分别锁住：

  • 指针宽度（FFI 布局的前提）；
  • 平台差异只允许出现在 cfg 分支，而不是运行时字符串判断。

33.9 本地复现 CI 的顺序 ​

CI 挂了，本地先按同样顺序跑一遍：

bash
# 1. 依赖与锁文件
cd app && pnpm install --frozen-lockfile

# 2. 前端（CI 的 frontend job）
pnpm build && pnpm test

# 3. Rust（CI 的 rust job，Linux 等价）
cd src-tauri && cargo check --workspace && cargo test --workspace

# 4. 文档（CI 的 docs job）
cd ../../docs && pnpm docs:build

如果本地全过、CI 挂，优先怀疑三件事：

  1. 平台差异：本地 macOS，CI Linux/Windows；
  2. 缓存污染：删掉 target 或换一个缓存键重跑；
  3. 环境差异：CI 的 rustc / node 版本与你本地不同。

33.10 常见报错速查 ​

现象原因解决
Windows job 找不到 libwebkit2gtk把 Linux 依赖步骤复制到了所有平台加 if: runner.os == 'Linux'
缓存从不命中键里含 github.run_id 等每次都变的值只用 OS + 锁文件/工具链版本
依赖升级后仍用旧产物常量缓存键 / 未更新锁文件用锁文件哈希，必要时手动清缓存
一个平台失败，另外两个被取消fail-fast 默认 true显式设 false
job 卡住 6 小时命令等待输入/网络挂起设 timeout-minutes + 命令加非交互参数
cargo test 在 macOS 过、Linux 挂测试依赖平台路径/大小写用 cfg 分支或临时目录
矩阵 job 数量暴涨维度组合过多只保留必要维度，固定工具链版本
缓存体积超过仓库上限target 目录过大只缓存依赖产物，或定期清理旧缓存

33.11 小结与课后练习 ​

本章你已完成：把 Rust job 铺到三平台矩阵；用 if 条件收敛平台专属步骤；用 Swatinem/rust-cache 接管三层缓存；加 concurrency、超时与 fail-fast；新增平台矩阵测试，让「支持哪些平台」成为可执行的断言。应用升级到 v0.32.0。

课后练习：

  1. 给 docs job 也加 timeout-minutes: 15，并解释为什么它比 Rust job 短。
  2. 在本地删掉 app/src-tauri/target，分别记录冷构建与热构建的耗时，估算缓存节省的比例。
  3. 故意在 #[cfg(windows)] 分支写一个类型错误，观察三个平台里哪个先失败、另外两个是否继续。
  4. 把 matrix.os 改成包含 windows-11-arm，判断当前代码是否真的支持 ARM64 Windows，并说明还需要补哪些配置。
