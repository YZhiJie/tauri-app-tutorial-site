第 3 章 · 事件系统与笔记核心 ​

钳钳：「命令是前端『主动发问』；事件是任何一方都能『主动开口』。本章把双向通道全部打通。」

本章学习目标 ​

  • 区分命令（拉模式）与事件（推模式）的使用场景
  • 用 Rust struct + 托管状态（State）重建笔记业务模型
  • 掌握四个方向的事件写法：Rust emit、前端 listen、前端 emit、Rust listen
  • 理解乐观更新与防抖保存的工程取舍

3.1 什么时候该用事件 ​

命令 invoke事件 event
方向前端 → Rust（一问一答）任意方向（广播）
语义「帮我做一件事，把结果给我」「发生了一件事，关心的人自己处理」
返回值必须有（Result）没有返回值概念
典型场景读数据、存文件、调系统能力进度推送、数据变更通知、跨窗口通信、菜单/快捷键触发

判断口诀：需要「等结果」用命令；需要「告诉大家」用事件。真实功能里两者经常配合——比如本章：命令负责改数据，改完用事件通知前端刷新。

3.2 Tauri v2 事件 API 地图 ​

v2 把事件方法收进了 trait，这是从 v1 升级最容易踩的坑：

方向APIv2 注意事项
前端 → 所有人emit(event, payload)@tauri-apps/api/event
前端订阅listen(event, cb) → 返回取消函数回调里载荷字段是 event.payload（v1 叫 data）
Rust → 前端app.emit(event, payload)必须 use tauri::Emitter;
Rust 订阅app.listen(event, cb)必须 use tauri::Listener;，闭包需持有 AppHandle 才能再发事件

3.3 把数据搬到 Rust：struct + State ​

定义与前端同构的 Rust struct ​

rust
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")] // updated_at <-> updatedAt
pub struct Note {
    pub id: String,
    pub title: String,
    pub content: String,
    pub updated_at: String,
}

#[serde(rename_all = "camelCase")] 是命名差异的标准答案：Rust 保持风格，JS 看到驼峰，两边都舒服。

托管状态 ​

rust
use std::sync::Mutex;

#[derive(Default)]
pub struct NotesStore {
    notes: Mutex<Vec<Note>>,
}

应用启动时注入：

rust
tauri::Builder::default()
    .manage(NotesStore::with_seeds()) // ← 任何命令都能注入取用

命令里通过参数声明即可拿到：

rust
#[tauri::command]
pub fn list_notes(store: State<NotesStore>) -> Vec<Note> {
    store.notes.lock().expect("笔记锁中毒").clone()
}

🦀 为什么用 std::sync::Mutex 而不是异步锁

所有命令都是同步的，临界区只是几条内存操作；改异步锁会波及每个命令的签名， 收益为零。锁的选型跟着调用栈走，而不是哪个「更先进」。

3.4 Rust 主动推送：命令里 emit ​

写操作完成后广播变更事件：

rust
use tauri::{AppHandle, Emitter, State};

pub const EVENT_NOTES_CHANGED: &str = "notes://changed";

#[tauri::command]
pub fn create_note(
    app: AppHandle,
    store: State<NotesStore>,
    title: String,
    content: String,
) -> Result<Note, String> {
    let note = store.insert(title, content);
    app.emit(EVENT_NOTES_CHANGED, &note)
        .map_err(|e| e.to_string())?; // emit 失败转成命令错误
    Ok(note)
}

要点：

  • 命令想要 AppHandle，直接在参数里声明，Tauri 自动注入；
  • emit 的载荷任意可序列化类型；用 () 表示「只通知，不带数据」；
  • 事件名用模块内常量，禁止前后端各写一遍字符串。

前端订阅（写在 composable 的 onMounted 中）：

ts
import { invoke } from "@tauri-apps/api/core";
import { listen, type UnlistenFn } from "@tauri-apps/api/event";

let unlisten: UnlistenFn | null = null;

await invoke("list_notes"); // 先拉一次全量
unlisten = await listen("notes://changed", () => {
  void refresh(); // 之后每次变更都重新同步
});

onUnmounted(() => unlisten?.()); // 组件销毁必须取消，否则重复订阅

这样数据流向就是一个闭环：

前端 invoke(create_note) → Rust 修改 State → emit changed
        ▲                                        │
        └────────── listen → refresh ◄───────────┘

3.5 反向通道：前端 emit，Rust listen ​

Rust 端在 setup 中挂监听 ​

rust
use tauri::Listener;

.setup(|app| {
    let handle = app.handle().clone(); // 闭包要 'static，需自己持有句柄
    app.listen("app://ping", move |event| {
        let payload = event.payload(); // 前端载荷的原始字符串
        if let Err(e) = handle.emit("app://pong", payload) {
            eprintln!("回送 pong 失败：{e}");
        }
    });
    Ok(())
})

⚠️ 两个 v2 细节

  1. 闭包里要用 AppHandle，必须在 listen 前 app.handle().clone()， 不能直接引用 setup 参数 app（生命周期不匹配，编译不过）；
  2. 忘记 use tauri::Listener 会报 no method named listen。

前端先发后听 ​

ts
import { emit, listen } from "@tauri-apps/api/event";

const stop = await listen<string>("app://pong", (event) => {
  console.log("收到 pong：", event.payload);
});
setTimeout(stop, 5000); // 一次性监听的简单写法

await emit("app://ping", { from: "EventLab", at: Date.now() });

🦀 钳钳的悄悄话

先挂监听再 emit，顺序不能反——事件不会等你订阅。 如果 Rust 可能在应用启动瞬间就推事件，前端监听要尽早注册。

3.6 事件命名与载荷约定 ​

教程采用 领域://动作 的命名风格，好处是一眼知道来源、避免和 Tauri 内部事件冲突：

事件名方向载荷
notes://changedRust → 前端Note 或 ()
app://ping前端 → Rust任意 JSON
app://pongRust → 前端原样字符串

载荷也请保持「可版本化」：字段只增不删、加可选字段比改语义安全。第 8 章的更新清单本身也遵循同样的思路。

3.7 乐观更新与防抖保存 ​

编辑器每敲一个字就 invoke 一次？不可行：IPC 往返 + Rust 广播 + 列表刷新，输入会卡顿，事件日志还会被刷爆。

本章的解法分两层：

ts
function applyUpdate(patch) {
  // ① 乐观更新：本地立即改，输入零延迟
  Object.assign(note, patch, { updatedAt: new Date().toISOString() });

  // ② 防抖持久化：停顿 500ms 才真正 invoke
  clearTimeout(saveTimer);
  saveTimer = setTimeout(() => invoke("update_note", snapshot), 500);
}

权衡要清楚：乐观更新意味着「保存中崩溃会丢最后 500ms 的内容」。对笔记场景完全可接受； 如果是金融表单，就应改为显式「保存」按钮 + 保存中禁用输入。没有银弹，只有取舍。
