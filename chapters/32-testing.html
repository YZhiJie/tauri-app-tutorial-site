第 32 章 · 测试金字塔与 E2E ​

钳钳：「测试不是越多越好，而是每一层只负责它最擅长的事。金字塔歪了，跑得再久也不安心。」

本章学习目标 ​

  • 用「成本 / 反馈速度 / 可信度」重新理解测试金字塔
  • 分清单元测试、集成测试、组件测试、E2E 各自该验证什么
  • 用 Vitest + jsdom 为前端纯函数、组件与 composable 写测试
  • 用 Playwright 在浏览器 mock 模式下跑主链路 E2E
  • 认识原生 E2E 的平台限制，并为 CI 设计分层策略
  • 掌握 flaky 测试的排查顺序：等待状态，而不是等待时间

32.1 金字塔不是按数量分的 ​

常见的错误理解是「单元测试要占 70%，E2E 占 10%」。真正决定比例的，是三种成本：

层级单次耗时失败定位能发现的问题
单元测试毫秒直接指向函数边界条件、算法错误
集成测试十毫秒~秒指向模块边界序列化、数据库 SQL、公开 API 变更
组件测试百毫秒指向组件输入 → 事件、条件渲染
E2E秒~分钟指向用户流程装配错误、路由、真实交互断链

越往下越慢、越难定位，但越接近「用户真的能用」。所以策略是：能在下层测的，绝不放到上层。

本章给项目补齐三层：Rust 集成测试、前端单元/组件测试、浏览器 E2E。原生 E2E 只讲边界，不强行落地——原因在 32.7。

32.3 Rust：单元与集成分开写 ​

单元测试放在模块内部，能访问私有函数：

rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn crlf_and_cr_become_lf() {
        assert_eq!(normalize_newlines("a\r\nb\rc").as_ref(), "a\nb\nc");
    }
}

集成测试放在 tests/ 目录，只能看到 pub 接口，相当于「另一个 crate 怎么用你」：

rust
use aninotes::text::{count_words, normalize_newlines, safe_file_name};

#[test]
fn safe_file_name_blocks_path_traversal() {
    assert_eq!(safe_file_name("../../etc/passwd", "fallback"), "etc_passwd");
}

这条断言比单元测试更有价值：它同时锁住了「函数是公开的」和「路径穿越被挡住」。如果哪天有人把 pub 改成 pub(crate)，集成测试会在编译期失败。

不要为覆盖率而写重复测试：同一个分支在单元层测过，就不必在集成层再测一遍。集成层只关心「跨模块协作」和「对外契约」。

32.4 前端单元测试：先测纯函数 ​

Vitest 直接复用 Vite 的配置与别名，不需要第二套构建：

ts
// vite.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  // ...
  test: {
    environment: "jsdom",
    include: ["src/**/*.test.ts"],
  },
});

见 [vite.config.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/vite.config.ts#L17-L23)。

include 只收 src 下的测试，避免把 Playwright 的 e2e/ 用例混进 jsdom。

纯函数测试最便宜，先写它：

ts
it("中英文混排按「中文逐字、英文按词」计数", async () => {
  const stats = await noteStats("你好 Rust");
  expect(stats).toEqual({ chars: 6, words: 3, lines: 1 });
});

noteStats 在浏览器里走 mock 分支（isTauri() 为 false），所以这条测试同时锁住了 mock 与 Rust 的同一套统计规则。

提示：浏览器 mock 不是「测试替身」，而是应用在没有原生运行时也要能工作的降级路径。它的行为必须和 Rust 一致，否则设计稿预览会骗人。

32.5 组件测试：只测输入与输出 ​

NoteSidebar 是纯展示 + 事件上抛，测试不需要真实 IPC：

ts
const wrapper = mount(NoteSidebar, {
  props: { notes, activeId: "n-1", keyword: "" },
});

await wrapper.findAll(".list li")[1]?.trigger("click");
expect(wrapper.emitted("select")?.[0]).toEqual(["n-2"]);

见 [NoteSidebar.test.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/notes/NoteSidebar.test.ts#L16-L44)。

三条原则：

  1. 断言用户可见的结果（文本、列表数量），不断言内部 ref 名；
  2. 测 emit 的载荷，因为它是组件与父组件的契约；
  3. 不测 CSS。样式回归交给截图或视觉测试，jsdom 里没有真实排版。

32.6 composable 测试：挂一个最小宿主 ​

useNotes 依赖 onMounted，不能直接调用。用一个宿主组件把它挂起来：

ts
const Harness = defineComponent({
  setup() {
    return useNotes();
  },
  template: "<div>{{ notes.length }}</div>",
});

const wrapper = mount(Harness);
const vm = wrapper.vm as unknown as UnwrapRef<ReturnType<typeof useNotes>>;

见 [useNotes.test.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/composables/useNotes.test.ts#L8-L24)。

UnwrapRef 很重要：模板里 Vue 会自动解包 ref / computed，类型也必须解包，否则 vm.notes 在 TS 里仍然是 Ref<Note[]>，.length 根本不存在。

测试覆盖的链路：

ts
await vm.createNote();          // 新建插入首位并选中
vm.applyUpdate({ title: "改过的标题" }); // 只改当前笔记
vm.setKeyword("待办");          // 立即过滤可见列表

setKeyword 在 mock 分支下不等待 300ms 防抖也能立即生效——因为 visibleNotes 直接读了 keyword。如果换成真实 Tauri 环境，这条断言就要改成等待 searchResults，这是「测试要跟着实现语义走」的典型例子。

32.7 浏览器 E2E：Playwright 拉起自己的服务器 ​

E2E 配置的核心是 webServer：Playwright 负责启动、等待就绪、测试结束关闭。

ts
export default defineConfig({
  testDir: "./e2e",
  use: { baseURL: "http://127.0.0.1:4173" },
  webServer: {
    command: "pnpm exec vite --host 127.0.0.1 --port 4173 --strictPort",
    url: "http://127.0.0.1:4173",
    reuseExistingServer: true,
    timeout: 120_000,
  },
});

见 [playwright.config.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/playwright.config.ts#L8-L26)。

两个坑都踩过：

  • 必须显式 --host 127.0.0.1：Vite 默认监听 localhost，某些系统上它解析到 IPv6，而 Playwright 用 IPv4 轮询，结果一直等到超时。
  • 端口不要复用 1420：那是 tauri dev 的端口，本地同时开两个进程会互相打架。

E2E 用例只写用户动作：

ts
await page.goto("/");
await expect(page.locator(".sidebar .list li")).toHaveCount(2);

await page.getByTitle("新建笔记").click();
await expect(page.locator(".sidebar .list li.active .title")).toHaveText("无标题笔记");

await page.getByPlaceholder("给笔记起个标题…").fill("今天的动漫笔记");
await expect(page.locator(".sidebar .list li.active .title")).toHaveText("今天的动漫笔记");

见 [notes.spec.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/e2e/notes.spec.ts#L15-L48)。

定位器优先顺序：getByRole / getByPlaceholder / getByTitle > locator(".class") > locator("div > div:nth-child(2)")。最后一种会在改布局时碎一地。

32.8 原生 E2E 的真实边界 ​

Tauri 的原生 E2E 依赖 WebDriver：

平台WebDriver现状
Windowstauri-driver + msedgedriver可用
Linuxtauri-driver + WebKitWebDriver可用
macOS无官方 WebDriver 支持只能靠单元/集成 + 人工冒烟

这不是配置问题，是平台能力问题。所以本章没有把原生 E2E 塞进 CI，而是明确分工：

  • 每次 PR：Rust 测试 + Vitest + 浏览器 E2E，三到五分钟内完成；
  • nightly：Linux/Windows 上跑 tauri-driver，覆盖真实窗口与 IPC；
  • 发布前：三平台人工冒烟清单（打开、导入、导出、托盘、快捷键）。

警告：不要用「在浏览器里点一遍」冒充原生 E2E。浏览器模式没有 IPC、没有文件系统、没有托盘，装配错误它一个都发现不了。

32.9 CI 分层：快反馈在前，慢验证在后 ​

yaml
# frontend job
- name: 类型检查 + 构建
  run: pnpm build

- name: 单元测试
  run: pnpm test

# e2e job
- name: 安装 Chromium
  run: pnpm exec playwright install --with-deps chromium

- name: 浏览器 E2E
  run: pnpm test:e2e

见 [ci.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/ci.yml#L85-L122)。

排序的理由：构建和单元测试几十秒就能给出结论；E2E 要装浏览器、拉服务器，慢一个数量级。把它们放在独立的 job，还能并行执行——单元失败时不必等 E2E 跑完。

E2E 失败时保留 trace 与截图（配置里的 trace: "retain-on-failure"），CI 上传 artifact，本地用 pnpm exec playwright show-trace 回放。

32.10 flaky 测试：先怀疑等待，再怀疑代码 ​

E2E 最常见的失败不是功能坏了，而是「动作太快」。

症状错误做法正确做法
点击时元素还没出现waitForTimeout(1000)await expect(locator).toBeVisible()
断言数量对不上多睡一会儿等待「数量变化」这个状态
偶发点击没反应重试三次检查元素是否被遮挡、是否稳定
本地过、CI 挂提高超时检查字体/动画/网络差异

Playwright 的 expect(locator) 自带轮询，天然比 waitForTimeout 稳。固定 sleep 只是在掩盖竞态。

另一个常见来源是测试间共享状态：每个用例都从「两条种子笔记」开始，就不要在前一个用例里新建三条。Playwright 默认每个 test 一个全新 page，但开发服务器是共享的——mock 数据只存在页面内存里，所以天然隔离。

32.11 常见报错速查 ​

现象原因解决
Timed out waiting ... from config.webServerVite 只监听 localhost / 端口被占显式 --host 127.0.0.1，换独立端口
is already used ... reuseExistingServer本地残留 vite 进程关掉旧进程，或设 reuseExistingServer: true
点击一直卡在「waiting for stable」元素在动画 / 布局持续变化等状态稳定，或检查是否有持续动画
Cannot find module 'jsdom'没装测试环境pnpm add -D jsdom
Ref<Note[]> 上不存在 length测试里没解包类型用 UnwrapRef<ReturnType<...>>
cargo test 找不到集成测试文件不在 tests/ 根目录移到 src-tauri/tests/*.rs
CI 上 Chromium 启动失败缺系统依赖playwright install --with-deps chromium
端口 1420 被占用和 tauri dev 同时跑E2E 改用 4173

32.12 小结与课后练习 ​

本章你已完成：补齐 Rust 集成测试；接入 Vitest + jsdom，为纯函数、组件与 composable 写了 12 条测试；用 Playwright 跑通「新建 → 编辑 → 搜索」主链路；把单元与 E2E 拆成独立 CI job；写清原生 E2E 的平台边界与 flaky 治理顺序。应用升级到 v0.31.0。

课后练习：

  1. 给 NoteEditor 写组件测试：输入标题后应 emit update，删除按钮应 emit delete。
  2. 用 Playwright 增加一条「空搜索恢复全量」的独立用例，确认两条用例互不影响。
  3. 在 Linux 或 Windows 上按 Tauri 官方文档接入 tauri-driver，跑一条「启动应用 → 新建笔记」的原生 E2E，并记录它比浏览器 E2E 慢多少。
  4. 故意把 notes.spec.ts 里的 await expect 换成 waitForTimeout(100)，观察它在慢机器上如何偶发失败。
