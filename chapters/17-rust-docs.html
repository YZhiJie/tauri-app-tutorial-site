第 17 章 · Rust 文档工程：rustdoc、文档注释与 doctest ​

钳钳：「代码是写给编译器看的，文档是写给未来的自己看的。Rust 最妙的地方是——这两件事可以只做一次。」

本章学习目标 ​

  • 理解 ///（条目文档）与 //!（模块文档）的区别与使用场景
  • 用 cargo doc 生成可浏览的 API 文档，用 intra-doc link 建立文档间引用
  • 写出能被 cargo test --doc 执行的 doctest，并知道 no_run / compile_fail 的用途
  • 理解 为什么 doctest 需要 lib target，并把纯逻辑代码拆进 src/lib.rs
  • 把散落两处的文本规则收敛到 text.rs，做到「规则一份、测试一套」

17.1 文档不是注释，是可执行的契约 ​

先看一个常见误区：很多人把文档写成「解释这行代码在做什么」的注释。但 Rust 的文档注释会被 rustdoc 抽取成 HTML，还会被 cargo test 当成测试代码编译执行。

rust
/// 把 CRLF / CR 统一为 LF。
///
/// # 示例
///
/// ```
/// use aninotes::text::normalize_newlines;
/// assert_eq!(normalize_newlines("a\r\nb").as_ref(), "a\nb");
/// ```
pub fn normalize_newlines(input: &str) -> Cow<'_, str> {
    // ...
}

这段文档同时承担三个角色：

角色由谁消费
人类可读的说明cargo doc --open 生成的网页
可编译的示例cargo test --doc
接口约束的声明调用方（示例就是最诚实的用法说明）

示例一旦和实现脱节，doctest 会直接失败——文档过期这件事，在 Rust 里是能被 CI 抓住的。

17.2 /// 与 //!：写在哪里 ​

写法位置作用
///写在函数/结构体/枚举/字段上方描述「这个条目是什么」
//!写在模块文件顶部描述「这个模块整体是什么」

我们的 text.rs 顶部就是模块文档：

rust
//! text —— 文本归一化与文件名安全化（第 17 章，第 18 章升级为 Cow）
//!
//! 这一组函数原先散落在 system/mod.rs 与 notes/commands.rs 里……

main.rs、error.rs 里那些原有的 //! 注释现在有了正式身份：它们就是 crate 级文档。运行 cargo doc 后，打开首页看到的第一屏就是这些内容。

一个实用的文档结构约定（本项目全程采用）：

rust
/// 一句话说明「它解决什么问题」
///
/// # 示例
/// ```
/// // 可直接运行的最小例子
/// ```
///
/// # Panics / # Errors / # Safety
/// 只在真的会 panic、返回 Err、或含 unsafe 时才写

# Panics、# Errors、# Safety 是 rustdoc 约定俗成的小节标题，不是语法要求，但 IDE 与读者都认这套。

17.3 关键一步：doctest 需要 lib target ​

第 1 章起，AniNotes 一直是「只有 src/main.rs 的二进制 crate」。这种结构有一个隐藏限制：

doctest 需要把示例当作独立 crate 编译，并通过 extern crate 你的库 链接进来。二进制 crate 没有对外符号，无法被链接，所以 bin-only 项目的 doctest 不会被运行。

验证一下：在只有 bin 的旧项目里写 /// ``` ... ``` ，cargo test --doc 会告诉你没有可测试目标。

解决方案是把「纯逻辑」拆进库目标：

app/src-tauri/src/
├── lib.rs        ← 新增：库入口，`pub mod text;`
├── text.rs       ← 新增：纯逻辑 + doctest
├── main.rs       ← 二进制入口，`pub use aninotes::text;`
└── notes/ ...

lib.rs：

rust
//! AniNotes 库目标（第 17 章）
//!
//! 为什么二进制项目要拆出一个 lib.rs：
//! 1. doctest 只能运行在「可被外部 crate 链接」的库目标上；
//! 2. 纯逻辑工具不依赖 Tauri，可以被单元测试、文档测试直接复用；
//! 3. main.rs 通过 `pub use aninotes::text;` 把库模块挂回自己的模块树。

pub mod text;

main.rs 只加一行：

rust
pub use aninotes::text;

这样业务代码里 crate::text::safe_file_name(...) 照旧可用——pub use 在 crate 根创建了一个名为 text 的绑定。

🦀 钳钳的悄悄话

「同一份源码会不会编译两遍？」不会。text.rs 只属于 lib target；bin target 通过 --extern aninotes 链接编译好的库。Cargo 的并行编译会复用同一份产物。

17.4 doctest 的进阶写法 ​

隐藏准备代码 ​

示例里有些行只是搭环境，不想让读者看到，可以用 # 开头隐藏（渲染时不可见，编译时生效）：

rust
/// ```
/// # let note = make_note();
/// assert_eq!(note.summary(4).len() > 0, true);
/// ```

no_run：只编译不执行 ​

涉及网络、磁盘、GUI 的示例不适合在测试机里真跑：

rust
/// ```no_run
/// let dir = std::path::Path::new("/tmp/notes");
/// std::fs::create_dir_all(dir).unwrap();
/// ```

compile_fail：把「不能编译」也变成测试 ​

rust
/// ```compile_fail
/// let s: &str = String::from("x"); // 类型不匹配，必须编译失败
/// ```

should_panic ​

rust
/// ```should_panic
/// let v: Vec<i32> = Vec::new();
/// v[0]; // 越界 panic
/// ```

这四种标注让文档示例覆盖「正常路径、不可运行路径、反例、panic 路径」，比只写一段漂亮代码有用得多。

17.5 实战：把两处重复规则收敛成 text.rs ​

第 5 章的导入逻辑里有：

rust
let content = raw.replace("\r\n", "\n").replace('\r', "\n");

第 12 章的导出逻辑里有：

rust
let safe: String = note.title.chars()
    .map(|c| if c.is_alphanumeric() || c == '-' || c == '_' { c } else { '_' })
    .collect();

这是同一个知识点的两个碎片：换行归一化、文件名白名单。它们分别长在两个模块里，规则一旦要改（比如增加对 \u{2028} 的处理），很容易只改一处。

第 17 章把它们搬进 [text.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/text.rs)：

rust
use std::borrow::Cow;

pub fn normalize_newlines(input: &str) -> Cow<'_, str> {
    if input.contains('\r') {
        // 先处理 \r\n（顺序不能反：先删 \r 会把 CRLF 拆成两个 LF）
        Cow::Owned(input.replace("\r\n", "\n").replace('\r', "\n"))
    } else {
        Cow::Borrowed(input)
    }
}

pub fn count_words(input: &str) -> usize {
    input.chars().filter(|c| !c.is_whitespace()).count()
}

pub fn safe_file_name(title: &str, fallback: &str) -> String {
    let cleaned: String = title
        .chars()
        .map(|c| if c.is_alphanumeric() || c == '-' || c == '_' { c } else { '_' })
        .collect();

    let trimmed = cleaned.trim_matches('_');
    if trimmed.is_empty() { fallback.to_string() } else { trimmed.to_string() }
}

调用点随之变短：

rust
// system/mod.rs：导入
let content = crate::text::normalize_newlines(&raw).into_owned();

// notes/commands.rs：导出文件名
let file_name = format!("{}.{}", safe_file_name(&note.title, &note.id), ext);

为什么 count_words 不是按空格切词 ​

中文没有空格，split_whitespace().count() 对「今天天气很好」会返回 1。也不能用 len()——那是 UTF-8 字节数，一个汉字占 3 字节。正确姿势是按字符过滤空白：

rust
input.chars().filter(|c| !c.is_whitespace()).count()

word_count 命令也切到这套规则，字数统计与文档示例从此只有一个定义。

17.6 生成与浏览：cargo doc ​

bash
cd app/src-tauri
cargo doc --no-deps --open
  • --no-deps：只文档化自己的 crate，不把几百个依赖的文档一起生成（速度快一个数量级）；
  • --open：生成后用浏览器打开 target/doc/aninotes/index.html；
  • 私有条目默认不出现，需要时用 --document-private-items。

想让「公开项漏写文档」变成编译错误，在 lib.rs 顶部加：

rust
#![deny(missing_docs)]

本项目的作法更温和：只对 lib 里的公开工具要求文档，Tauri 命令靠代码注释即可——门禁的严格程度要匹配项目阶段。

导入文档链接（intra-doc link）让文档之间可以互相跳转：

rust
/// 返回 [`Cow`]，没有 `\r` 时直接借用原串。
///
/// 参见 [`safe_file_name`] 与 [`count_words`]。

cargo doc 会把 [Cow] 链接到标准库，把 [safe_file_name] 链接到同 crate 的函数。写错路径会得到 warning，这也是文档层的类型检查。

17.7 常见报错速查 ​

现象原因解决
cargo test --doc 显示 0 个测试项目只有 bin target，示例没有被当作 crate 编译拆出 lib.rs，把被测逻辑放进库目标
doctest 报 unresolved import aninotes::text包名与 crate 名不一致，或忘了 pub mod text;检查 Cargo.toml 的 name 与 lib.rs 的导出
doctest 里的 # 行把代码弄乱# 后面的空格被当成代码缩进隐藏行写成 # let x = ...;，# 后必须有一个空格
cargo doc 报 broken intra-doc link链接路径写错，或条目是私有的用完整路径 crate::text::safe_file_name，或加 --document-private-items
文档示例能跑，但复制到项目里编译失败示例缺 use，靠 doctest 的隐式 prelude示例里显式写 use，保证可复制粘贴
normalize_newlines 对 \r\n 产生两个换行替换顺序反了：先替换 \r 再替换 \r\n必须先 \r\n -> \n，再 \r -> \n

17.8 小结与课后练习 ​

本章你已完成：拆分 lib target 让 doctest 可运行；为 text 模块补齐模块文档、函数文档与三个可执行示例；把导入/导出的重复规则收敛成一份实现；掌握 no_run / compile_fail / should_panic 四种 doctest 标注。应用升级到 v0.16.0。

课后练习：

  1. 给 safe_file_name 增加一个 compile_fail 示例：直接把 &str 赋给 String，观察编译器如何解释类型不匹配。
  2. 在 lib.rs 打开 #![deny(missing_docs)]，运行 cargo doc，把报出的缺失文档逐个补上——体会「文档门禁」的强度。
  3. 用 cargo doc --document-private-items 对比输出，找出哪些内部函数其实值得补一段说明。
