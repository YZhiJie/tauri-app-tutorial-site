第 39 章 · Tauri 内部原理：tao、wry 与事件循环 ​

小塔：「窗口是壳，WebView 是画布，事件循环才是让两者动起来的心脏。」

本章学习目标 ​

  • 分清 Tauri、tao、wry 三层的职责边界，知道遇到问题该往哪一层找
  • 理解事件循环为什么必须占据主线程，以及命令、事件、异步任务各自跑在哪里
  • 用 on_window_event 统计窗口事件，验证事件循环确实在工作
  • 解释逻辑像素、物理像素与 scaleFactor 的换算关系
  • 区分 inner_size / outer_size、装饰边与显示器信息
  • 写出一个只读、可反复调用的运行时探针，并知道它能定位哪几类问题

39.1 三层结构：谁负责什么 ​

用 cargo tree 看依赖会看到一长串 crate，但真正需要记住的只有三层：

层代表 crate职责出问题时看哪里
应用框架tauri配置、命令、插件、状态、权限命令没注册、权限被拒、状态取不到
窗口与事件循环tao创建窗口、菜单、托盘，驱动平台事件循环窗口不显示、事件不触发、主线程卡死
WebView 嵌入wry把 WKWebView / WebView2 / WebKitGTK 嵌进窗口白屏、缩放异常、WebView 版本差异
粘合层tauri-runtime-wry把 tao 的窗口和 wry 的 WebView 组装成 Tauri 的运行时需要读源码确认具体行为时

tauri 本身不直接操作原生窗口，它通过 Runtime trait 描述「我想要一个窗口 / 一个 WebView」。桌面端这个 trait 的实现就是 tauri-runtime-wry。这也是为什么同一份代码能编到 Android / iOS：换的是 Runtime 实现，业务层不变。

提示：不要在业务代码里直接依赖 tao / wry。它们属于运行时实现细节，Tauri 没有承诺跨大版本稳定；需要的能力优先找 tauri::window / tauri::webview 的公开 API。

39.2 事件循环：一切从 run() 开始 ​

main.rs 的最后一行是：

rust
.run(tauri::generate_context!())
.expect("启动 AniNotes 时发生错误");

run 不会立刻返回。它做三件事：

  1. 解析配置、创建窗口与 WebView；
  2. 进入平台事件循环（macOS 的 NSApplication run loop、Windows 的消息泵、Linux 的 GTK/glib loop）；
  3. 循环取出事件，分发给窗口回调、WebView 回调与 Tauri 的命令分发器。

可以用伪代码概括：

text
run():
  初始化平台应用
  创建窗口 + WebView（必须在主线程）
  loop {
    event = 等待下一个平台事件()      // 鼠标、键盘、窗口尺寸、DPI 变化…
    match event {
      WindowEvent(e) => 交给 on_window_event 回调,
      WebviewEvent(e) => 交给 WebView 回调,
      IpcRequest(r)   => 交给命令分发器,
    }
  }

两个直接推论：

  • 窗口和 WebView 只能在主线程创建。在异步命令里直接 WebviewWindowBuilder::new(...) 会触发平台层的线程断言失败（或直接崩溃）。需要动态建窗时，用 AppHandle::run_on_main_thread 把闭包投递回主线程。
  • 事件回调不能慢。回调运行在事件循环上，里面每多阻塞 10ms，整个应用的输入响应就迟 10ms。计数、打日志、改一个原子变量都可以；读数据库、发网络请求、等锁都不行。

39.3 命令跑在哪里 ​

很多人以为「Rust 后端 = 后台线程」，其实要分三种情况：

命令类型执行位置适合做什么
同步 fn主线程（事件循环内）极短的纯计算、读一个托管状态
异步 async fnTauri 的 async runtime 线程池I/O、数据库、网络
spawn_blocking 包裹的同步代码阻塞线程池文件读写、CPU 密集计算

第 11 章把 word_count 改成 async + spawn_blocking，正是为了避免全库统计卡住事件循环。判断标准很简单：这段代码如果跑 100ms，用户会不会觉得窗口卡了？ 会，就不能留在同步命令里。

警告：同步命令里 std::thread::sleep、同步文件遍历、等待 Mutex 都是事件循环杀手。调试时表现为「窗口能显示但点什么都没反应」——因为循环正停在你的命令里。

39.4 窗口事件从哪来 ​

tao 把平台事件翻译成统一的 WindowEvent。常用的几个：

事件触发时机常见用途
Resized(size)客户区尺寸变化保存窗口尺寸、重排布局
Moved(position)窗口位置变化记住上次位置、多屏吸附
Focused(bool)获得 / 失去焦点暂停轮询、收起浮层
ScaleFactorChanged { .. }DPI 变化、拖到另一块屏重新加载高分屏资源
CloseRequested { .. }用户点关闭拦截为「最小化到托盘」
ThemeChanged(theme)系统明暗主题切换同步 CSS 变量

本章的探针只统计前四类，因为它们能直接回答「事件循环是否在送货」：

rust
pub struct WindowEventCounters {
    resized: AtomicU64,
    moved: AtomicU64,
    focused: AtomicU64,
    scale_changed: AtomicU64,
}

pub fn record(&self, event: &tauri::WindowEvent) {
    let slot = match event {
        WindowEvent::Resized(_) => &self.resized,
        WindowEvent::Moved(_) => &self.moved,
        WindowEvent::Focused(_) => &self.focused,
        WindowEvent::ScaleFactorChanged { .. } => &self.scale_changed,
        _ => return,
    };
    slot.fetch_add(1, Ordering::Relaxed);
}

见 [runtime_probe.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/runtime_probe.rs#L34-L66)。

为什么用 AtomicU64 而不是 Mutex<u32>：

  1. 回调在事件循环线程上，锁竞争会直接变成 UI 卡顿；
  2. Ordering::Relaxed 足够——我们只关心最终计数，不关心两个事件谁先被读到；
  3. 计数溢出不值得报错，收窄到 u32 时饱和即可（Specta 也不允许把 u64 直接导出到 TypeScript）。

39.5 计数器为什么托管在 Builder 阶段 ​

setup 里 app.manage(...) 是常见写法，但对窗口事件计数来说太晚了。窗口在 setup 之前就已经创建，第一波 Resized / Focused 可能在状态托管完成前到达。正确顺序是：

rust
let mut builder = tauri::Builder::default()
    .manage(perf::StartupTimeline::default())
    .manage(runtime_probe::WindowEventCounters::default())
    .on_window_event(|window, event| {
        if let Some(counters) = window.try_state::<runtime_probe::WindowEventCounters>() {
            counters.record(event);
        }
    });

见 [main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L88-L99)。

两个细节：

  • on_window_event 是应用级回调，会收到所有窗口的事件。本项目还有「快速记一笔」小窗，它的移动与焦点事件也会累加进来。做真实统计时可以把窗口 label 一起记下，按窗口分组。
  • 用 try_state 而不是 state。前者返回 Option，状态尚未就绪时安静跳过；后者会 panic，让一个早期事件变成启动崩溃。

39.6 逻辑像素、物理像素与缩放 ​

这是桌面端最容易出错的一组概念：

概念单位来源用途
逻辑像素与设备无关的 CSS 像素布局、设计稿写 CSS、设窗口逻辑尺寸
物理像素真实屏幕像素inner_size() 等 API截图、渲染精度、WebView 视口
缩放因子无单位scale_factor()两者换算：physical = logical × factor

在 2 倍屏上，一个 1200×800 的客户区对应 2400×1600 物理像素。若把物理尺寸直接当 CSS 尺寸用，界面会「莫名其妙地小一半」；反之把 CSS 尺寸当物理尺寸，截图会模糊。

inner_size 与 outer_size 也常被混淆：

  • inner_size 是客户区，不含标题栏和边框，WebView 实际可用的区域；
  • outer_size 是整个窗口，含装饰边。两者之差就是标题栏高度与边框宽度。

macOS 上差异随窗口是否全屏、是否使用自定义标题栏而变，所以不要写死「标题栏 28px」这类常量，直接相减。

39.7 探针的 DTO 与命令 ​

命令本身是只读的：

rust
#[tauri::command]
#[specta::specta]
pub fn runtime_probe(
    window: WebviewWindow,
    counters: State<'_, WindowEventCounters>,
) -> RuntimeProbe {
    RuntimeProbe {
        webview_version: tauri::webview_version().ok(),
        scale_factor: window.scale_factor().unwrap_or(1.0),
        inner_size: size_info(window.inner_size()),
        outer_size: size_info(window.outer_size()),
        is_maximized: window.is_maximized().unwrap_or(false),
        is_decorated: window.is_decorated().unwrap_or(true),
        monitor: monitor_info(&window),
        events: counters.snapshot(),
        // …
    }
}

见 [runtime_probe.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/runtime_probe.rs#L150-L168)。

三个设计取舍：

  1. 所有几何 API 都降级。inner_size() 返回 Result，个别平台/窗口状态下会失败；探针失败不应让「关于」弹窗报错，统一退回 0 或默认值。
  2. webview_version 用 Option。取不到就明确写 None，前端展示「未知」，而不是编一个版本号。
  3. 不修改窗口。探针不移动、不缩放、不改主题，因此可以反复点击、可以放进诊断日志。

第 31 章的 collect_commands! 会自动把 RuntimeProbe、SizeInfo、MonitorInfo、WindowEventCounts 写进 TypeScript 绑定，前端不需要手抄类型。

39.9 用探针定位四类问题 ​

现象先看哪个字段判断
界面模糊 / 过小scaleFactor 与 innerSize物理/逻辑像素是否被混用
窗口尺寸不符预期innerSize vs outerSize差值是否等于装饰边；是否被最大化
拖动窗口后没有反应events.moved / events.resized计数不涨说明事件循环没收到事件
多显示器下布局错乱monitor.scaleFactor窗口是否跨到了另一块屏

使用顺序建议：先点探针看事件计数，再拖一下窗口，再点一次。两次计数之差就是这一段交互期间事件循环送货的数量。若移动窗口 5 秒而 moved 一直是 0，问题就不在你的布局代码，而在事件循环或窗口属性（例如窗口被设成了不可移动）。

提示：探针只读，不会干扰问题复现。排查「卡顿」时也可以先点一次探针记录基线，再执行可疑操作，最后对比事件计数与进程运行时长。

39.10 什么时候该读源码 ​

公开 API 能回答 90% 的问题，剩下 10% 需要读源码。建议的阅读顺序：

  1. tauri::window / tauri::webview 的文档与签名——先确认「有没有这个能力」；
  2. tauri-runtime-wry 里的实现——确认「这个能力在各平台具体怎么做的」；
  3. tao / wry 对应平台模块——只有怀疑是平台差异时才下探到这一层。

几个值得记住的事实：

  • tauri::webview_version() 来自 wry，在不同系统上返回不同内核版本（WKWebView / WebView2 / WebKitGTK），不要用它判断功能支持，能力检测应走 CSS.supports 或特性开关。
  • #[cfg(desktop)] 不是装饰。托盘、全局快捷键、多窗口这些 API 在移动端根本不存在；第 35 章已用 cfg 把桌面专属代码整段裁掉。
  • 移动端只有一个 WebView，窗口尺寸通常等于屏幕尺寸，scaleFactor 由系统给定。探针在移动端仍可运行，但「移动窗口」这类事件不会出现。

39.11 常见报错速查 ​

报错 / 现象原因处理
cannot find 'dpi' in 'tauri'把 tauri::dpi::PhysicalSize 当成公开路径改用 tauri::PhysicalSize / tauri::PhysicalPosition
window must be created on the main thread在 async 命令或子线程里直接建窗用 app.run_on_main_thread(...) 投递回主线程
窗口显示但点击无响应同步命令阻塞了事件循环改成 async，重活放 spawn_blocking
try_state 总是 None状态托管晚于事件回调，或类型不匹配把 .manage(...) 提前到 Builder 阶段
事件回调里死锁在回调中等待命令持有的锁回调只做计数 / 发消息，不做阻塞操作
高分屏截图模糊用了逻辑尺寸当物理尺寸乘 scaleFactor，或用 inner_size() 的物理值
移动端编译失败桌面专属 API 没加 cfg按第 35 章拆 #[cfg(desktop)]

39.12 小结 ​

本章把 Tauri 的运行时拆成三层来看：

  • tao 管窗口与事件循环，wry 管 WebView，tauri 管配置、命令、插件与权限；
  • 事件循环必须在主线程，回调和同步命令都不能慢；I/O 与重计算交给 async runtime 或阻塞线程池；
  • 窗口几何是「物理像素 + 缩放因子」的组合，inner 与 outer 的差值来自装饰边；
  • 只读探针可以低成本地回答「事件循环还在工作吗」「窗口处于什么状态」；
  • 计数状态要在 Builder 阶段托管，并用 try_state 容忍早期事件。

下一章我们会继续向下，看 Tauri 的自定义协议与 IPC 底层：请求如何从 WebView 走到 Rust，响应又如何回到页面。

课后练习 ​

  1. 给 WindowEventCounters 增加窗口 label 维度，只统计 main 窗口的事件，并在探针里分别展示。
  2. 为 RuntimeProbe 增加 theme 字段，监听 ThemeChanged，验证系统明暗切换时事件确实到达。
  3. 把窗口拖到另一块缩放不同的显示器上，对比前后 monitor.scaleFactor 与 events.scaleChanged，解释布局为什么需要重新计算。
