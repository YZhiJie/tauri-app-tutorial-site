第 24 章 · 架构收口：多窗口、状态分层与测试 ​

钳钳：「一个窗口能把事做完，两个窗口能让事做得顺手。架构的终点不是更多代码，而是每块代码都知道自己该待在哪。」

本章学习目标 ​

  • 用 WebviewWindowBuilder 按需创建窗口，并保证同 label 单例
  • 让多个窗口共享同一份后端状态，理解 Tauri 状态是进程级而非窗口级
  • 用窗口 label 做「一个前端产物、多种界面」的轻量路由
  • 梳理 AniNotes 的完整分层：入口 / 域 / 数据 / 基础设施
  • 用 cargo test 建立单元测试 + doctest 的回归网，知道下一步该补什么

24.1 为什么要第二个窗口 ​

主窗口是「工作台」：搜索、列表、编辑器、关于弹窗，信息密度高。但真实使用场景里，有一类操作需要快：

正在看网页/写文档，突然想到一句话，想立刻记下来，不想切换窗口、找输入框、等列表加载。

于是有了「快速记一笔」：托盘菜单一点，弹出 420×300 的小窗，只有标题、正文、保存。保存后关窗，主窗口通过事件自动刷新。

这带来三个架构问题：

  1. 窗口怎么创建、怎么保证只有一个？
  2. 新窗口的数据从哪来？
  3. 同一份前端代码怎么渲染两种界面？

24.2 创建窗口：单例 + 按需 ​

[main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs)：

rust
fn open_quick_capture(app: &tauri::AppHandle) {
    if let Some(window) = app.get_webview_window("quick-capture") {
        let _ = window.show();
        let _ = window.set_focus();
        return; // 已存在：只唤起，不重复创建
    }

    if let Err(e) = WebviewWindowBuilder::new(
        app,
        "quick-capture",
        WebviewUrl::App("index.html".into()),
    )
    .title("快速记一笔 · AniNotes")
    .inner_size(420.0, 300.0)
    .min_inner_size(360.0, 240.0)
    .always_on_top(true)
    .resizable(true)
    .build()
    {
        tracing::warn!("创建快速记录窗口失败：{e}");
    }
}

托盘菜单加一项：

rust
let capture_item = MenuItem::with_id(app, "tray-capture", "快速记一笔", true, None::<&str>)?;

.on_menu_event(|app, event| match event.id.as_ref() {
    "tray-show" => toggle_main_window(app),
    "tray-capture" => open_quick_capture(app),
    "tray-quit" => app.exit(0),
    _ => {}
})

细节：

  • get_webview_window(label) 是单例检查：窗口被关闭后 label 释放，下次会重新创建；
  • WebviewUrl::App("index.html") 指向打包后的前端入口，开发期自动映射到 Vite；
  • always_on_top(true) 让记录窗不被主窗口遮挡；
  • 创建失败只记录日志，不 panic——托盘点击不应该让应用崩溃。

24.3 权限：新窗口也要进 capability ​

Tauri v2 的权限按窗口生效。capabilities/default.json 的 windows 字段必须包含新 label：

json
{
  "identifier": "default",
  "windows": ["main", "quick-capture"],
  "permissions": ["core:default", "dialog:default", "..."]
}

漏掉的症状很典型：窗口能显示，但 invoke 报 not allowed on window "quick-capture"。新增窗口时先改 capability，再写前端逻辑。

24.4 共享状态：新窗口不需要新数据库 ​

快速记录窗口调用的 create_note 命令，与主窗口完全一样：

ts
await invoke("create_note", { title, content });

它不需要自己的 NotesDb，因为 Tauri 的状态是进程级的：

rust
app.manage(db);
app.manage(WordCountCache::default());

任何窗口的命令通过 State<'_, NotesDb> 拿到的都是同一个连接池；写操作广播 notes://changed，主窗口的 useNotes 监听后自动刷新。

text
        ┌──────────── main 窗口 ────────────┐
        │  Vue: useNotes（监听 changed）      │
        └──────────────┬────────────────────┘
                       │ invoke
        ┌──────────────▼────────────────────┐
        │        进程级状态（app.manage）     │
        │  NotesDb（SQLite 连接池）           │
        │  WordCountCache（Arc<RwLock>）      │
        │  LogGuard（日志守卫）               │
        └──────────────▲────────────────────┘
                       │ invoke
        ┌──────────────┴────────────────────┐
        │  quick-capture 窗口：仅表单          │
        └───────────────────────────────────┘

24.5 一个前端产物，两种界面 ​

App.vue 用窗口 label 做轻量路由：

ts
const isQuickCapture = ref(false);

onMounted(() => {
  try {
    isQuickCapture.value = getCurrentWebviewWindow().label === "quick-capture";
  } catch {
    // 纯浏览器预览没有 Tauri 窗口对象
  }
  if (!isQuickCapture.value) void silentCheckAndPrompt();
});
vue
<template>
  <QuickCapture v-if="isQuickCapture" />
  <div v-else class="app-shell"> ...完整工作台... </div>
</template>

为什么不给快速记录单独建一个 HTML 入口？

  • 构建配置、依赖、样式全部要维护两份；
  • 共享组件（通知、错误提示）无法复用；
  • 打包体积不会因为多一个入口而变小（代码本来就在同一个 bundle）。

用 label 分流，代价只是 App.vue 顶部一个 ref，收益是零额外构建配置。规模再大（比如 5+ 窗口）时，才值得引入真正的前端路由。

24.6 状态分层：谁该管什么 ​

AniNotes 到第 24 章形成了五层：

层位置职责依赖方向
入口层main.rs插件、命令注册、setup、窗口/托盘依赖所有域
命令层notes/commands.rs、system/mod.rs参数校验、状态编排、事件广播依赖域内业务
业务/数据层notes/db.rsSQL 规则、事务、索引依赖 model/error
模型层notes/model.rsNote、事件常量依赖 serde
基础设施text.rs、cache.rs、export.rs、error.rs、hardware.rs无业务状态、可单测依赖 std/少量 crate

依赖只能向下：模型不知道数据库，数据库不知道 Tauri 命令，命令不知道窗口。这条纪律让每一层都能被单独测试——cargo test 里 12 个测试没有启动一次 Tauri。

24.7 测试：从「能跑」到「敢改」 ​

当前测试分布：

位置类型覆盖
text.rs单元 + doctest换行归一化、字数、文件名白名单
cache.rs单元命中/失效、克隆共享
export.rs单元Markdown / JSON 渲染
hardware.rs单元PID/CPU 合理性 smoke test

运行：

bash
cd app/src-tauri
cargo test --workspace

输出会分三段：lib 单元测试、bin 单元测试、doctest。一个健康的项目应该三层都有。

还缺什么 ​

  1. 数据库集成测试：用 SqlitePool::connect("sqlite::memory:") 跑建表 + 增删改查 + FTS 搜索；
  2. IPC 契约测试：用 tauri::test::mock_builder 构造无窗口应用，直接调命令；
  3. 前端组件测试：Vitest + @vue/test-utils 测 useNotes 的防抖与错误分支。

测试不是越多越好，而是越靠近边界越值钱：序列化格式、SQL 规则、文件命名这些「错了会静默」的地方优先覆盖。

24.8 架构债务清单（诚实版） ​

一个成熟项目不该假装没有妥协。当前明确留下的债务：

项现状建议
Note.id 仍是裸 String无格式校验需要对外 API 时引入 NoteId newtype（第 18 章）
缓存粒度是全库任一写操作全量失效数据量上万后改按 id 缓存
导出进度按完成顺序与列表顺序不同若 UI 需要稳定顺序，改为 join_next_with_id
快速记录窗口无草稿关窗即丢加 tauri-plugin-store 或临时文件
更新检查无重试网络失败静默加指数退避与「稍后提醒」
无崩溃上报只有本地日志按第 16 章指南接 Sentry

写下来的债务才是可管理的债务；没写下来的会变成「历史遗留问题」。

24.9 系列回望：从窗口到架构 ​

text
基础篇   1 环境 → 2 命令 → 3 事件 → 4 文件 → 5 系统 API → 6 跨平台 → 7 打包 → 8 更新
进阶篇   9 调试 → 10 最佳实践
精通篇   11 Rust 核心 → 12 IPC → 13 系统集成 → 14 SQLite → 15 插件
         16 发布工程 → 17 文档 → 18 所有权 → 19 Trait
         20 智能指针 → 21 并发 → 22 宏 → 23 FFI → 24 架构收口

回头看，AniNotes 的复杂度不是线性堆上去的，而是每一章解决一个真实问题：

  • 数据从 JSON 到 SQLite，是因为搜索需要索引；
  • 错误从 String 到 AppError，是因为前端要按类型处理；
  • 导出从 for 到 Exporter + JoinSet，是因为格式要扩展、批量要提速；
  • 缓存、宏、FFI、多窗口，都是「重复出现三次以上」才引入的抽象。

这正是工程判断力的来源：知道什么时候该抽象，也知道什么时候不该。

24.10 常见报错速查 ​

现象原因解决
新窗口 invoke 报 not allowedcapability 的 windows 没包含新 label加入 "quick-capture" 并重启 dev
快速窗口白屏WebviewUrl::App 路径写错 / dist 未构建用 index.html，先 pnpm build 或走 devUrl
关窗再开报 label 已存在旧窗口 hide 而非 close用 close()，或在创建前检查并复用
主窗口不刷新新窗口写操作没广播 changed统一走 broadcast_notes_changed!
cargo test 找不到 doctest逻辑在 bin 而非 lib参照第 17 章把纯逻辑放进 lib target
多窗口同时写数据库偶发锁等待SQLite 写锁粒度为库级保持单连接池 + 短事务，避免长事务

24.11 小结与课后练习 ​

本章你已完成：按需创建单例的快速记录窗口；用 capability 授权新窗口；让多窗口共享进程级状态；用 label 做前端轻量分流；梳理五层架构与依赖方向；建立 12 项测试的回归网并列出架构债务。应用升级到 v0.23.0。

课后练习：

  1. 给快速记录窗口加全局快捷键（如 CmdOrControl+Shift+N），按下即弹出并聚焦。
  2. 用 tauri::test::mock_builder 写一个命令级集成测试：调用 create_note 后断言 list_notes 能查到。
  3. 从债务清单里挑一项落地（推荐「快速记录草稿」），并为它补一条测试。
