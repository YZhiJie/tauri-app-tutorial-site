第 42 章 · 架构治理：workspace、模块边界与 API 版本策略 ​

小塔：「架构不是画出来的图，是每次提交都被检查的规则。」

本章学习目标 ​

  • 理解 workspace 在「一仓多 crate」中的收益、代价与依赖方向约束
  • 用分层目录把业务域、系统能力、框架入口隔离开
  • 把架构规则写成会失败的测试（fitness function），而不是口头约定
  • 制定 IPC API 版本策略：哪些变更升版、哪些属于加性变更
  • 用 contract_info + 前端版本闸门识别前后端构建代际错位
  • 设计命令弃用流程，并治理依赖、MSRV 与锁版本

42.1 治理解决的是「变化的方向」 ​

功能会一直加，代码会一直改。架构治理要回答的不是「现在长什么样」，而是：

  1. 谁能依赖谁——防止依赖成环，保住拆分与测试的可能；
  2. 什么变化是兼容的——防止前后端来自不同代际时静默出错；
  3. 规则由谁执行——文档会过期，只有 CI 里会红的测试不会。

本章不引入新的业务功能，只做三件事：给 workspace 与模块边界加可执行约束，给 IPC 契约加版本号，给前后端加一次启动自检。

42.2 workspace：一仓多 crate 的收益与代价 ​

Cargo.toml 里声明了三个成员：

toml
[workspace]
members = ["plugins/note-stats", "macros/aninotes-macros"]

见 [Cargo.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/Cargo.toml#L27-L28)。

收益代价
共享 Cargo.lock，依赖版本只有一个真相任一成员改依赖，全 workspace 重新解析
共享 target/，依赖只编译一次单个 crate 的构建不再是完全独立
cargo test --workspace 一次跑全部测试变慢，需要靠 -p 收窄日常反馈
本地插件与过程宏随主应用一起演进成员彼此可见，容易写出不该有的依赖

本项目三个成员的角色：

成员类型允许依赖禁止依赖
aninotes（主 crate）bin + lib两个本地成员—
plugins/note-statsTauri 插件库tauri 插件 APIaninotes 主 crate
macros/aninotes-macros过程宏库proc-macro 生态一切运行时业务代码

警告：插件反向依赖主 crate 会形成循环依赖，Cargo 会直接拒绝解析。更隐蔽的是「主 crate 的内部类型被插件顺手 import」——一旦主 crate 重构，插件就得跟着改，插件就失去了独立演进的意义。插件只应依赖公开的 tauri 接口。

42.3 模块分层：从 model 到 commands ​

笔记域的内部结构在第 3~20 章逐步稳定下来：

text
src/notes/
├── model.rs      数据结构 + 事件常量（无框架依赖）
├── db.rs         SQLite / FTS5，业务规则与事务边界
├── storage.rs    旧版 JSON 存储，仅保留迁移用途
├── export.rs     导出格式 trait（第 19 章）
├── cache.rs      全库字数缓存（第 20 章）
├── stream.rs     Channel 分批推送（第 12 章）
├── commands.rs   对外命令：参数校验 + 编排 + 广播
└── mod.rs        域出口，re-export 公开项

见 [mod.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/mod.rs#L16-L31)。

依赖方向必须是单向的：

text
main.rs / system / platform
        │  调用
        ▼
     commands.rs  ──►  cache / stream / export
        │
        ▼
      db.rs  ──►  model.rs
        │
        ▼
    storage.rs（仅迁移）

三条实践规则：

  1. model 是词汇表：只放数据结构与常量，不 use tauri、不碰数据库。它被所有层引用，任何框架依赖都会被放大成编译瓶颈。
  2. db 是业务真相：查询、事务、约束都在这里。命令层不写 SQL，才能在未来换存储实现时只改一个文件。
  3. commands 是薄壳：参数校验、调用领域方法、广播事件。它越薄，业务越容易被单元测试覆盖。

提示：mod.rs 的 re-export 是「域出口」。外部只写 use crate::notes::NotesDb，不关心内部拆了几个文件；将来把 db.rs 拆成 db/mod.rs 也不会影响调用方。

42.4 把架构写成会失败的测试 ​

新建 tests/architecture.rs，用静态扫描固化五条规则：

#规则失败意味着
1每个 #[tauri::command] 必须有 #[specta::specta]命令不会进契约绑定，前端只能手写类型
2notes/model.rs 不出现 tauri模型层被框架污染，脱离 WebView 无法测试
3notes/ 不引用 crate::system / vault / plugin_sandbox领域反向依赖外层，依赖图开始成环
4notes/commands.rs 不出现 sqlxSQL 泄漏到命令层，换存储要全文件重写
5业务代码不出现 println! / eprintln!发布后没有日志，排障时无迹可寻

规则 1 的实现核心是「属性必须相邻」：

rust
if line.trim() != "#[tauri::command]" {
    continue;
}
let exported = lines
    .iter()
    .skip(index + 1)
    .take(2)
    .any(|next| next.trim() == "#[specta::specta]");

见 [architecture.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/tests/architecture.rs#L51-L74)。

它是文本级扫描，不追求语义精确——这正是它的价值：零依赖、毫秒级、任何平台都能跑，能拦住 90% 的「顺手破坏」。代价是可能误报：

  • 注释里出现 println!( 也会命中（本项目注释刻意只写 println! 不带括号）；
  • 属性写在同一行会漏检（团队约定一行一个属性）。

提示：规则误报时先改代码，再考虑改规则。把规则改松很容易，但松一次就会松第二次，最后测试变成摆设。

42.5 API 版本策略：加性 vs 破坏性 ​

第 31 章让 Rust 命令签名自动生成 TypeScript，解决了「类型不同步」。但它解决不了「前后端来自不同构建」：

  • 用户升级了安装包，WebView 里仍是旧前端缓存（极端情况下）；
  • 灰度期间，更新包与旧前端混合运行；
  • 回滚后端但没回滚前端。

因此需要一份契约主版本：

rust
pub const IPC_API_VERSION: u32 = 1;

见 [contract.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/contract.rs#L26-L26)。

什么变更升版、什么不升：

变更是否升 IPC_API_VERSION理由
新增命令否旧前端不会调用它，行为不变
返回结构新增可选字段否旧前端忽略未知字段
新增必填参数是旧前端不传，调用直接失败
删除 / 重命名命令是旧前端调用会报「命令不存在」
修改参数或返回类型是反序列化形态改变
把可选字段改为必填是语义收紧，旧数据可能不满足

一句话：旧客户端还能正常跑，就是加性变更；否则就是破坏性变更。 判断标准不看代码改了多少行，只看「上一版前端是否仍可用」。

42.6 contract_info：把版本变成可查询的数据 ​

rust
pub struct ContractInfo {
    pub api_version: u32,
    pub backend_version: String,
    pub deprecated_commands: Vec<String>,
}

见 [contract.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/contract.rs#L37-L45)。

三个字段各有分工：

  • api_version：判断能否互通；
  • backend_version：定位「是哪一个构建」；
  • deprecated_commands：迁移提示的数据源。

命令本身只有一个内存取值：

rust
#[tauri::command]
#[specta::specta]
pub fn contract_info() -> ContractInfo {
    ContractInfo {
        api_version: IPC_API_VERSION,
        backend_version: env!("CARGO_PKG_VERSION").to_owned(),
        deprecated_commands: DEPRECATED_COMMANDS.iter().map(|n| (*n).to_owned()).collect(),
    }
}

见 [contract.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/contract.rs#L52-L61)。

注册后，第 31 章的契约测试自动把 ContractInfo 与 contractInfo 写进 [ipc-bindings.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/ipc-bindings.ts#L162)。

提示：为什么不把 api_version 塞进 build_info？两者生命周期不同。构建身份属于打包管线，契约版本属于架构治理；混在一起会让「只想看 commit」的调用方被迫理解版本策略。

42.7 前端闸门：只告警，不白屏 ​

前端持有自己的期望版本：

ts
export const EXPECTED_IPC_API_VERSION = 1;

见 [contract.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/contract.ts#L15-L15)。

两个常量分别随各自的产物走，天然可能不一致。比较逻辑是纯函数：

ts
export function evaluateContract(info: ContractInfo): { ok: boolean; message: string } {
  if (info.apiVersion === EXPECTED_IPC_API_VERSION) {
    return { ok: true, message: `IPC 契约一致（v${info.apiVersion}）` };
  }
  return {
    ok: false,
    message:
      `IPC 契约版本不一致：前端期望 v${EXPECTED_IPC_API_VERSION}，` +
      `后端（v${info.backendVersion}）提供 v${info.apiVersion}。请重新构建前端或回退后端。`,
  };
}

见 [contract.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/contract.ts#L34-L44)。

启动时调用一次，失败只写日志：

ts
void loadContract()
  .then((info) => {
    const result = evaluateContract(info);
    if (!result.ok) console.error(result.message);
  })
  .catch((err) => console.warn("IPC 契约自检失败", err));

见 [main.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/main.ts#L14-L19)。

警告：不要把不一致做成 throw 或白屏。灰度阶段短暂错位是常态，而「契约告警」的优先级远低于「用户还能不能记笔记」。先记录、再提示、最后才是阻断——阻断只应出现在安全场景（例如加密库版本不兼容）。

「关于」弹窗同时展示版本与弃用数量：

vue
<li v-if="contract">
  <span>IPC 契约</span>
  <b>v{{ contract.apiVersion }} · {{ contract.deprecatedCommands.length }} 个弃用命令</b>
</li>

见 [AboutDialog.vue](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/components/system/AboutDialog.vue#L138-L141)。

42.8 弃用流程：先挂牌，再删除 ​

删除命令不能一步到位。标准三步：

text
1. 命令进入 DEPRECATED_COMMANDS（仍可调用，前端开始迁移）
2. 至少保留一个发布周期，观察调用日志
3. 前端不再调用后，删除命令并把 IPC_API_VERSION +1

DEPRECATED_COMMANDS 是唯一登记处：

rust
pub const DEPRECATED_COMMANDS: &[&str] = &[];

见 [contract.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/contract.rs#L32-L32)。

单元测试守住「无重复」：

rust
let unique: HashSet<_> = DEPRECATED_COMMANDS.iter().collect();
assert_eq!(unique.len(), DEPRECATED_COMMANDS.len());

见 [contract.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/contract.rs#L75-L79)。

当前列表为空，是刻意的：没有技术债就不要造技术债。等真的需要删命令时，流程已经就位。

42.9 依赖治理：锁版本、MSRV 与 deny ​

架构的另一半是「谁能进入这个仓库」。本项目已有三层约束：

约束位置拦住什么
rust-version = "1.77.2"Cargo.toml依赖偷偷抬高 MSRV，CI 与用户环境编译失败
specta = "=2.0.0-rc.26"Cargo.tomlrc 版本间的破坏性变更让构建随机失败
cargo-deny 白名单[deny.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/deny.toml)漏洞、未知许可证、未知源、通配符版本
Cargo.lock / pnpm-lock.yaml仓库根「我这里能跑」变成「哪里都能跑」

deny.toml 的四组检查值得记住：

toml
[advisories]
vulnerability = "deny"
unmaintained = "warn"
yanked = "deny"

[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause", ...]

[bans]
wildcards = "deny"
multiple-versions = "warn"

[sources]
unknown-registry = "deny"
unknown-git = "deny"

见 [deny.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/deny.toml#L13-L51)。

提示：multiple-versions = "warn" 是刻意的。升级期同一 crate 出现两个版本很常见，直接 deny 会逼着团队做无关紧要的版本对齐；等到发布前再统一。安全类问题则必须 deny。

42.10 什么时候该拆 ​

治理不是「越拆越好」。拆分的触发条件应该是可观察的：

信号动作
单个文件超过 600 行且包含两种以上职责按职责拆文件，不急着拆 crate
模块之间出现循环依赖先抽公共接口/模型，再谈拆分
某段逻辑要独立测试、且不依赖 Tauri抽成纯函数或独立 crate
插件需要被其他应用复用独立 crate + 明确公开 API
构建时间显著上升且改动集中在一个域评估拆 crate 的收益，而不是先拆

本项目的选择：只有插件与过程宏独立成 crate，业务域全部留在主 crate 的目录内。理由很实际——它们有独立的复用边界（note-stats 可给别的 Tauri 应用用，宏与业务无关），而业务域拆 crate 只会增加跨 crate 的 pub 管理成本。

42.11 治理反模式速查 ​

反模式表现后果
架构只写在文档里README 画了依赖图，代码里没人检查三个月后图与代码完全对不上
用 pub 解决一切所有模块、所有字段都公开任何重构都是破坏性变更
命令层写 SQLcommands.rs 里出现 sqlx::query换存储要重写全部命令
前后端版本「约定同步」没有常量、没有自检灰度时静默错位，排障靠猜
契约不一致直接白屏throw new Error("版本不一致")可用性问题被放大成事故
依赖版本用 *本地能跑、CI 随机失败构建不可复现
为未来提前拆 crate业务还没稳定就拆成五个包跨包改动成本 > 收益

42.12 小结与课后练习 ​

本章你已完成：梳理了 workspace 的成员与依赖方向；把五条模块边界规则写成会失败的集成测试；建立了 IPC API 版本策略与 contract_info 命令；前端在启动时自检并只告警；展示了弃用流程与依赖治理清单。应用升级到 v0.41.0。

课后练习：

  1. 把规则 1 扩展为「collect_commands! 里的每个命令都必须能在源码中找到定义」，并说明如何处理宏展开带来的误报。
  2. 给 ContractInfo 增加 min_frontend_version 字段，前端在版本过低时展示一条可关闭的提示条，而不是只写控制台。
  3. 设计一次真实的破坏性变更（例如把 list_notes 的返回改为分页结构），写出后端、绑定、前端、版本号与弃用登记的完整改动清单。
  4. 为 plugin_sandbox 增加一条边界测试：插件沙箱不得直接访问 NotesDb，只能通过传入的输入结构与输出结构交互。
  5. 给 CI 增加 cargo deny check 与架构测试的独立 job，要求任一失败都阻断合并，并说明为什么架构测试不该只在 Linux 上跑。
