第 26 章 · 大数据 IPC 与流式传输 ​

钳钳：「把一万条笔记塞进一个 JSON，就像把一整箱行李塞进地铁闸机——不是不行，是所有人都得等你。」

本章学习目标 ​

  • 理解一次性大响应的三重成本：序列化、跨边界传输、前端空等
  • 用 tauri::ipc::Channel 把大结果拆成小批次推送
  • 写出稳定分页（ORDER BY 第二排序键）与批大小上下限
  • 前端用 Channel 边收边渲染，并正确处理取消 / 窗口关闭
  • 知道什么时候该用命令返回、事件、Channel，以及如何测量收益

26.1 一次性返回一万条，会发生什么 ​

list_notes 现在的实现是「全量查询 + 全量返回」。笔记 500 条时没感觉，1 万条时同时发生三件事：

  1. Rust 侧序列化：把 Vec<Note> 转成一条超长 JSON 字符串；
  2. 跨边界传输：WebView 与 Rust 之间要整体搬运这条字符串；
  3. 前端空等：await invoke 在全部数据到达前不会 resolve，首屏一直是空的。

更糟的是内存峰值：Rust 里有一份 Vec，IPC 层有一份 JSON，前端解析后又有一份对象图。同一条数据在三个地方同时存在。

text
一次性返回：
Rust Vec ──► JSON 字符串 ──► 前端对象数组
   │              │                 │
   └──── 峰值内存 ≈ 3 份 ────────────┘
   用户等待：全程无进度，直到最后一条解析完

流式传输把这条链路切开：

text
分批返回：
Rust 查 100 条 ──► JSON ──► 前端渲染 ──► 释放
Rust 查下 100 条 ──► JSON ──► 前端追加 ──► 释放
                    ▲
              每批都能看到进度

26.2 三种通信形态，别选错 ​

Tauri 提供了多种前后端通信方式，适用场景不同：

形态API适合不适合
命令返回invoke 的返回值请求-响应、结果小、需要错误处理大结果、长任务
事件广播emit / listen一对多通知（如 notes://changed）需要精确回传调用方
ChannelChannel<T> 参数一对一流式结果、进度、日志广播给多个窗口

判断口诀：「这次调用的结果只有调用者关心，而且可能很大」→ Channel。

26.3 Rust 侧：一批一批地查 ​

新增 [stream.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/stream.rs)，核心结构只有三个字段：

rust
#[derive(Debug, Clone, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct NotesBatch {
    pub offset: usize,
    pub total: usize,
    pub notes: Vec<Note>,
}

offset + notes.len() 就是已发送条数，前端不需要自己累加。

命令签名里的 Channel 是一个普通参数：

rust
#[tauri::command]
pub async fn stream_notes(
    db: State<'_, NotesDb>,
    batch_size: Option<usize>,
    on_event: Channel<NotesBatch>,
) -> Result<usize, AppError> {
    let size = batch_size.unwrap_or(100).clamp(1, 1000);
    let total = db.count().await? as usize;
    let mut offset = 0usize;

    while offset < total {
        let notes = db.list_page(offset as i64, size as i64).await?;
        if notes.is_empty() { break; }

        let batch = NotesBatch { offset, total, notes };
        offset += batch.notes.len();

        if on_event.send(batch).is_err() {
            tracing::debug!(offset, "前端已断开 Channel，停止后续分页");
            break;
        }
    }
    Ok(offset)
}

三个细节决定了它是否可靠：

  1. clamp(1, 1000)：前端传 0 会死循环，传 1,000,000 会造出巨型消息。边界必须在后端强制，不能只信前端。
  2. send 失败即取消：窗口关闭或组件卸载后 Channel 被丢弃，send 返回错误。这不是异常，而是用户已经不需要后续数据了。
  3. 先取数再累加 offset：offset += batch.notes.len() 用的是实际返回条数，最后一页不满时进度依然准确。

数据库侧新增两个方法：

rust
pub async fn count(&self) -> Result<i64, AppError> { /* SELECT COUNT(*) */ }

pub async fn list_page(&self, offset: i64, limit: i64) -> Result<Vec<Note>, AppError> {
    sqlx::query_as::<_, NoteRow>(
        "SELECT id, title, content, updated_at, version FROM notes
         ORDER BY updated_at DESC, id ASC
         LIMIT ?1 OFFSET ?2",
    )
    // ...
}

第二个排序键 id ASC 不是可有可无的。只按 updated_at 排序时，同一毫秒写入的多条笔记顺序不稳定，分页会出现「第 1 页和第 2 页都出现同一条」。加上唯一键做 tie-breaker，顺序才是确定的。

26.4 前端：Channel 的用法 ​

[stream.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/stream.ts) 把细节包成一个小函数：

ts
import { Channel, invoke } from "@tauri-apps/api/core";

const channel = new Channel<NotesBatch>();
let received = 0;

channel.onmessage = (batch) => {
  received += batch.notes.length;
  onBatch(batch);
};

await invoke("stream_notes", { batchSize, onEvent: channel });
return received;

注意参数名：Rust 的 on_event 在 JS 侧写 onEvent。Tauri v2 默认把命令参数转为 camelCase，写错会得到「missing required key onEvent」。

onmessage 回调运行在 WebView 主线程。不要在回调里做重活：如果每批都触发一次同步布局或深拷贝，流式传输的收益会被抵消。

26.5 批大小怎么选 ​

批大小没有唯一正确答案，但有可计算的区间：

批大小单批大致体积适合风险
10几 KB移动端、弱设备、首屏优先消息次数多，调度开销上升
100几十 KB桌面端默认基本无风险
1000几百 KB ~ 1 MB导入导出、后台任务单条消息偏大，UI 可能卡顿

经验规则：单批序列化后的 JSON 控制在 1MB 以内，超过就减半。可以用第 25 章的时间线，在前端记录「第一批到达时间」与「最后一批到达时间」：

ts
const t0 = performance.now();
let firstBatchAt = 0;

await streamNotes({
  batchSize: 100,
  onBatch: (batch) => {
    if (!firstBatchAt) firstBatchAt = performance.now() - t0;
    // 追加渲染...
  },
});

如果 firstBatchAt 很大，问题在查询而不是传输；如果第一批很快但最后一批很慢，问题在总数据量或前端渲染。

26.6 背压：Channel 不是无限水管 ​

Channel 的 send 是「投递」而不是「等待前端处理完」。前端渲染慢时，消息会在 IPC 层排队，内存继续上涨。

三种应对方式，按复杂度排序：

  1. 减小批大小：最省事，牺牲消息次数换内存平稳；
  2. 节流渲染：onmessage 只把数据推进队列，用 requestAnimationFrame 合并成一次渲染；
  3. 显式确认：前端处理完一批后再 invoke("ack_batch")，后端收到确认才发下一批（协议复杂度最高，通常不需要）。

对笔记应用，方案 1 + 2 足够。真正需要方案 3 的场景是「不可丢的日志流」或「带顺序约束的协同编辑」。

取消也要说清楚：前端 AbortSignal 只是停止处理，后端要到下一次 send 失败才知道。如果希望立刻停止查询，需要额外的取消命令（例如 cancel_stream(task_id)），这属于第 38 章「运行时扩展」的协议设计范畴。

26.7 渲染侧：别把一万条塞进响应式数组 ​

即使传输是流式的，前端如果每批都 notes.value.push(...batch.notes)，Vue 仍会为每个对象建立响应式代理，1 万条就是 1 万个代理，滚动时持续 diff。

两个务实做法：

做法效果
用 shallowRef 持有数组，整批替换引用避免深层代理，配合虚拟列表
只保留可视区附近的数据（虚拟滚动）DOM 节点数量恒定

教程应用本身数据量小，不必上虚拟列表；但要把这条原则写进设计文档：流式传输解决「到达」问题，虚拟化解决「渲染」问题，两者不能互相替代。

26.8 常见报错速查 ​

现象原因解决
missing required key onEvent前端参数名没转 camelCase写 onEvent，不是 on_event
命令一直不 resolve循环条件写错 / total 为 0先 count，空库直接返回 0
分页出现重复或漏条排序缺少唯一 tie-breakerORDER BY updated_at DESC, id ASC
窗口关闭后 Rust 报错刷屏把 send 失败当致命错误视为取消，break 即可
前端越收越卡每批都 push 进深响应式数组shallowRef + 批量替换 / 虚拟列表
最后一批进度不到 100%用固定 batch_size 累加 offset用实际 notes.len() 累加
