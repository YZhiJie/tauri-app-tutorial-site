第 25 章 · 性能基线与启动剖析 ​

小塔：「用户不会夸你代码优雅，但一定记得你那 3 秒白屏。先把启动时间量出来，再谈优化。」

本章学习目标 ​

  • 说清「启动」到底包含哪几段，避免把首帧慢误判成 Rust 慢
  • 在应用里落地一条真实可用的启动时间线（Rust 标记 + 前端 Navigation Timing）
  • 用命令取回快照，建立可重复的冷启动 / 热启动测量协议
  • 配置 profiling 编译档，用采样工具定位真正的热点
  • 给体积、内存、首帧建立基线表，并列出下一步的优化优先级

25.1 「启动慢」是一句没有信息量的话 ​

用户说「启动慢」，可能是四种完全不同的情况：

阶段典型耗时慢的表现
进程加载几十毫秒双击后图标跳动很久才出窗口
后端初始化100ms ~ 1s窗口出现了，但一直是白屏
前端资源加载50ms ~ 500ms白屏后突然一次性出现整页
首帧渲染几十毫秒内容出现后字体/布局再闪一下

不做分段，任何优化都是猜。AniNotes 的做法是在代码里埋时间线：每个关键节点记一个相对进程起点的毫秒数，同时记录与上一节点的差值。

text
进程起点 ──► setup 进入 ──► SQLite 就绪 ──► 托盘就绪 ──► 前端首帧
   0ms           ~180ms          ~210ms         ~230ms        ~420ms
                 delta 180        delta 30       delta 20      delta 190

这张表最有价值的一列不是 at_ms，而是 delta_ms——它直接告诉你「下一刀该切哪里」。

25.2 Rust 侧：一个不引入依赖的时间线 ​

新增 [perf.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/perf.rs)。核心只有三样东西：一个全局起点、一个受互斥锁保护的阶段数组、一个快照结构。

rust
static PROCESS_START: OnceLock<Instant> = OnceLock::new();

pub fn mark_process_start() {
    PROCESS_START.get_or_init(Instant::now);
}

pub struct StartupTimeline {
    stages: Mutex<Vec<StartupStage>>,
    frontend: Mutex<Option<FrontendTiming>>,
}

为什么用 OnceLock<Instant> 而不是 lazy_static：

  • 标准库自带，零依赖；
  • get_or_init 天然幂等，热重载或多入口调用都只记录第一次；
  • 起点一旦写入就不可变，符合「进程启动只发生一次」的事实。

mark 的实现只有一行关键逻辑：差值来自上一阶段，而不是固定间隔。

rust
pub fn mark(&self, name: &str) {
    let at_ms = since_process_start();
    let Ok(mut stages) = self.stages.lock() else { return };
    let delta_ms = stages.last().map_or(at_ms, |prev| at_ms - prev.at_ms);
    stages.push(StartupStage {
        name: name.to_owned(),
        at_ms: at_ms.round(),
        delta_ms: delta_ms.round(),
    });
}

注意 let Ok(...) else { return }：性能采集是尽力而为，锁中毒时宁可少一条数据，也不能让启动失败。

25.3 把标记插进真实生命周期 ​

[main.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/main.rs#L44-L110) 在 main() 第一行启动计时，在 setup 中打三个点：

rust
fn main() {
    perf::mark_process_start();

    tauri::Builder::default()
        // ...
        .manage(perf::StartupTimeline::default())
        .setup(|app| {
            let timeline = app.state::<perf::StartupTimeline>();
            timeline.mark("setup_enter");

            init_logging(app.handle());

            let db = tauri::async_runtime::block_on(NotesDb::open(app.handle()))?;
            app.manage(db);
            timeline.mark("sqlite_ready");

            // ... 托盘构建 ...
            timeline.mark("tray_ready");
            tracing::info!(
                uptime_ms = timeline.snapshot().process_uptime_ms,
                "后端初始化完成"
            );
            Ok(())
        })
        .run(tauri::generate_context!())
}

三个设计决定值得说明：

  1. 状态在 setup 之前托管。如果在 setup 里才 app.manage，前端极早的 invoke 可能撞上「状态尚未注册」而失败。
  2. 只标记有意义的边界。每个函数都打点会污染时间线，10 个以内的粗粒度阶段足够定位问题。
  3. setup_enter 包含窗口创建。Tauri 会先按配置创建窗口，再进入 setup；所以这个 delta 往往包含 tao/wry 的初始化成本。

25.4 前端侧：Navigation Timing 是免费的性能数据 ​

浏览器已经替你测了导航各阶段，没必要用 Date.now() 手搓。前端在首帧后上报：

ts
requestAnimationFrame(() => {
  const nav = performance.getEntriesByType("navigation")[0] as
    | PerformanceNavigationTiming
    | undefined;
  void invoke("report_frontend_ready", {
    timing: {
      domReadyMs: nav?.domContentLoadedEventEnd ?? performance.now(),
      firstPaintMs: performance.now(),
      navigationMs: nav?.duration ?? performance.now(),
    },
  }).catch(() => { /* 采集失败不影响使用 */ });
});

三个字段的含义：

字段来源能回答的问题
domReadyMsdomContentLoadedEventEndHTML 与同步脚本多久解析完
firstPaintMsrequestAnimationFrame 时刻用户第一次真正看到内容是什么时候
navigationMsduration从导航开始到 load 的总耗时

为什么放在 requestAnimationFrame 里：onMounted 只代表组件挂载完成，浏览器可能还没绘制。等到下一帧再上报，采集点才落在「确实画过一帧」之后。

上报失败只吞掉，不弹提示——性能采集永远不能影响主流程。

25.5 取回快照：开发期的「体检报告」 ​

Tauri 命令已注册，开发时在 WebView 控制台执行：

js
const snap = await window.__TAURI__.core.invoke("perf_snapshot");
console.table(snap.stages);
console.log("峰值内存 MB:", snap.peakMemoryMb, "平台:", snap.platform);

一个真实快照大致长这样（数值随机器变化，结构才是重点）：

json
{
  "processUptimeMs": 412,
  "stages": [
    { "name": "setup_enter",  "atMs": 168, "deltaMs": 168 },
    { "name": "sqlite_ready", "atMs": 196, "deltaMs": 28  },
    { "name": "tray_ready",   "atMs": 214, "deltaMs": 18  }
  ],
  "frontend": { "domReadyMs": 62, "firstPaintMs": 240, "navigationMs": 388 },
  "peakMemoryMb": 86.4,
  "platform": "macos"
}

读法：

  • setup_enter 占 168ms → 大头在运行时与窗口创建，属于框架成本；
  • sqlite_ready 28ms → 建表与迁移正常，若超过 100ms 要查磁盘或迁移逻辑；
  • 前端 firstPaintMs 240ms 与进程总时长 412ms 有重叠 → 前后端是并行的，不能简单相加。

25.6 测量协议：不然数字没有可比性 ​

同一台机器上，冷启动和热启动能差 3 倍。比较优化前后必须固定条件：

项冷启动热启动
系统缓存重启或清理文件缓存后首次连续启动第 2 次以后
用途用户第一次打开日常反复开关
采样次数5 次取中位数10 次取中位数
记录内容时间线 + 峰值内存时间线 + 首帧

macOS 上可重复冷启动的粗暴办法：退出应用后执行 sudo purge 清理缓存（需要管理员权限，仅用于测量）。更稳的做法是只比较同一条件下的相对变化，不追求绝对值。

一条纪律：一次只改一个变量。同时改依赖版本、读取逻辑和图片格式，测出来的数字无法归因。

25.7 用采样工具找热点 ​

时间线告诉你「哪一段慢」，采样工具告诉你「这一段里哪一行慢」。

[Cargo.toml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/Cargo.toml#L89-L97) 新增了剖析档：

toml
[profile.profiling]
inherits = "release"
debug = true        # 保留符号，火焰图才能显示函数名
strip = false
panic = "unwind"    # abort 会让采样器拿不到完整栈

构建带符号的发布版：

bash
cd app/src-tauri
cargo build --profile profiling

三平台常用工具：

平台工具命令 / 操作
macOSInstruments（Time Profiler）open -a Instruments，附加到进程
macOS / Linuxsamplysamply record target/profiling/aninotes
Linuxperfperf record -g ./aninotes
通用cargo-flamegraphcargo flamegraph --profile profiling

看火焰图时只问一个问题：最宽的叶子函数是不是我的代码？ 如果最宽的是 malloc、objc_msgSend 或 sqlx 内部，优化方向是「少调用」而不是「改实现」。

25.8 体积与内存基线 ​

启动时间不是唯一指标。桌面应用还要看安装包大小与常驻内存：

指标采集方式AniNotes 参考值
安装包（macOS dmg）ls -lh target/release/bundle/dmg/*.dmg约 8~15 MB
可执行文件ls -lh target/release/aninotes约 6~12 MB
峰值内存perf_snapshot().peakMemoryMb开发期 80~150 MB
空闲 CPU活动监视器 / top -pid接近 0%

参考值只用于「量级判断」：如果安装包突然从 10MB 变成 60MB，说明混进了不该打包的资源；如果空闲 CPU 持续 5%，说明有轮询或渲染循环没停。

peak_memory_mb 在 Unix 上通过 getrusage 读取，没有引入新依赖：

rust
#[cfg(unix)]
fn peak_memory_mb() -> Option<f64> {
    let mut usage: libc::rusage = unsafe { std::mem::zeroed() };
    let ok = unsafe { libc::getrusage(libc::RUSAGE_SELF, &mut usage) };
    if ok != 0 { return None; }
    let raw = usage.ru_maxrss as f64;
    #[cfg(target_os = "macos")]
    let mb = raw / (1024.0 * 1024.0);   // macOS 是字节
    #[cfg(not(target_os = "macos"))]
    let mb = raw / 1024.0;              // Linux 是 KB
    Some((mb * 10.0).round() / 10.0)
}

这段代码故意展示一个常见坑：ru_maxrss 的单位在不同平台不一致。不处理会在 Mac 上得到「80GB 内存」这种荒谬数字。

25.9 优化优先级：先摘低垂的果子 ​

按「收益 / 风险」排序，AniNotes 的清单是：

优先级项预期收益风险
P0延迟加载非首屏资源（教程大图、导出模块）首帧 -50~150ms低
P0数据库初始化移到异步任务，窗口先显示骨架白屏 -30~80ms中
P1日志文件改按大小 + 天数双重滚动磁盘与启动更稳低
P1首屏只查最近 50 条，搜索再走 FTS列表渲染更快低
P2release 档继续压体积（opt-level="z" 试验）包体 -5~10%需回归
P2预编译 SQL / 连接池预热首次查询 -10ms低

不要先做的：把 Vue 换成更小的框架、重写 IPC、上 SSR。这些改动大、收益不确定，在没有基线的情况下属于赌博。

现象原因解决

25.11 小结与课后练习 ​

本章你已完成：为 AniNotes 加了零依赖的启动时间线；在 main / setup / 数据库 / 托盘 / 前端首帧五个位置打点；用 Navigation Timing 采集浏览器侧数据；提供 perf_snapshot 快照命令；配置带符号的 profiling 编译档；写下冷/热启动测量协议与优化优先级。应用升级到 v0.24.0。

课后练习：

  1. 把「窗口可见」也纳入时间线：在 setup 里监听主窗口的 Shown 事件并打点，观察它和 setup_enter 的差值。
  2. 在开发模式连续启动 5 次，把 setup_enter 的 delta 记到表格里，看看波动范围有多大。
  3. 故意在 setup 里加 std::thread::sleep(Duration::from_millis(300))，确认时间线能准确定位到这一段，然后删掉。
