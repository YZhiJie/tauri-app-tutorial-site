第 20 章 · 智能指针与内部可变性：Arc、RwLock 与缓存 ​

钳钳：「多个窗口想共用同一份数据，靠的不是复制，而是『大家手里都拿着同一个钥匙扣』。」

本章学习目标 ​

  • 分清 Box / Rc / Arc / RefCell / Mutex / RwLock 各自解决什么问题
  • 用 Arc<RwLock<Option<T>>> 实现进程内共享缓存
  • 理解 RwLock 的读写语义、毒化（poisoning）处理与锁粒度
  • 知道为什么「写操作失效」比「定时过期」更适合本地数据缓存
  • 把缓存托管进 Tauri 状态，让主窗口与快速记录窗口共享同一份

20.1 六种容器，一张表说清 ​

类型解决什么线程安全典型场景
Box<T>把值放到堆上，固定大小取决于 T递归类型、trait object
Rc<T>多所有者（引用计数）❌ 单线程GUI 单线程共享、树结构
Arc<T>多所有者（原子引用计数）✅跨线程/跨任务共享
Cell<T> / RefCell<T>编译期借用检查 → 运行期❌ 单线程内部可变性、观察者模式
Mutex<T>互斥锁，一次一个写者✅写多读少、状态机
RwLock<T>读写锁，多读或单写✅读多写少（缓存、配置）

一句话选型：跨线程用 Arc，单线程用 Rc；读多写少用 RwLock，其余用 Mutex。

20.2 问题：word_count 每次都扫全库 ​

第 11 章的 word_count：

rust
let snapshot = db.list().await?;
let total = spawn_blocking(move || snapshot.iter().map(|n| n.content.chars().count()).sum()).await?;

「关于」弹窗打开一次就查一次全库、遍历一次全部正文。笔记 1000 条时这只是一次卡顿；如果每敲几个字就刷新统计，就会变成持续的后台 CPU 消耗。

缓存需求很明确：

  • 计算结果是一个 usize，读多写少；
  • 任何增/删/改/导入之后，缓存必须立刻失效；
  • 主窗口和快速记录窗口都要看到同一份缓存。

20.3 设计：Arc<RwLock<Option<usize>>> ​

[notes/cache.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/cache.rs)：

rust
use std::sync::{Arc, RwLock, RwLockReadGuard, RwLockWriteGuard};

#[derive(Clone, Default)]
pub struct WordCountCache {
    inner: Arc<RwLock<Option<usize>>>,
}

impl WordCountCache {
    fn read(&self) -> RwLockReadGuard<'_, Option<usize>> {
        self.inner.read().unwrap_or_else(|poisoned| poisoned.into_inner())
    }

    fn write(&self) -> RwLockWriteGuard<'_, Option<usize>> {
        self.inner.write().unwrap_or_else(|poisoned| poisoned.into_inner())
    }

    pub fn get(&self) -> Option<usize> { *self.read() }
    pub fn store(&self, total: usize) { *self.write() = Some(total); }
    pub fn invalidate(&self) { *self.write() = None; }
}

三个设计点：

  1. Arc 让状态可克隆。命令里先 clone 一份，再 .await，避免把 State 守卫长期借出去；
  2. RwLock 而非 Mutex。get() 只读，多个窗口可以同时读；只有 store/invalidate 才需要独占；
  3. Option 表达「未计算」。None 不是错误，是「还没算或已失效」，语义比用 0 当哨兵清晰得多。

20.4 毒化（Poisoning）：锁也会「受伤」 ​

如果持锁线程 panic，RwLock 会被标记为 poisoned，后续 read()/write() 返回 Err。教科书做法是继续 unwrap 让错误扩散，但对缓存来说没必要：

rust
self.inner.read().unwrap_or_else(|poisoned| poisoned.into_inner())

缓存最坏的结果是「多算一遍」，不值得让整个应用崩溃。这是按场景选择失败策略，不是偷懒。

🦀 钳钳的悄悄话

MutexGuard 千万不要跨 .await 持有：它通常不是 Send，编译器会直接拒绝；更重要的是，持锁等待 I/O 会让所有读者一起排队。第 21 章的并发导出特意用「先取数、再放锁、后写盘」的顺序。

20.5 接入 word_count ​

rust
#[tauri::command]
pub async fn word_count(
    db: State<'_, NotesDb>,
    cache: State<'_, WordCountCache>,
) -> Result<usize, AppError> {
    if let Some(total) = cache.get() {
        return Ok(total);
    }

    let snapshot = db.list().await?;
    let total = spawn_blocking(move || {
        snapshot.iter().map(|n| crate::text::count_words(&n.content)).sum()
    })
    .await
    .map_err(|e| AppError::disk("字数统计任务被中断", e))?;

    cache.store(total);
    Ok(total)
}

注意 cache.get() 返回时读锁已经释放（get 内部 *guard 复制出 usize 后 guard 立即 drop），后面的 .await 不持有任何锁。

20.6 失效策略：写路径负责一致性 ​

缓存只在写操作成功后失效：

rust
// create_note / update_note / delete_note / import_note 都一样
let note = db.insert(title, content).await?;
cache.invalidate();
crate::broadcast_notes_changed!(app, &note);

顺序很重要：先写库成功，再失效缓存。如果先失效再写库失败，缓存会被无谓地清空；反过来则绝不会读到旧值。

为什么不用 TTL（定时过期）？

  • 本地数据库的写操作是确定的，事件驱动的失效是精确的；
  • TTL 会引入「过期窗口」：用户刚改完笔记，统计可能还是旧的；
  • TTL 还会造成「没人读也反复重算」的浪费。

一般规律：数据源能精确通知变更时，用失效；数据源无法通知（如远程 API）时，才用 TTL。

20.7 多窗口共享同一份缓存 ​

第 24 章会创建 quick-capture 窗口。它不新建数据库连接，也不新建缓存——所有窗口的命令都从 app.manage 里取同一份状态：

rust
app.manage(db);
app.manage(WordCountCache::default());

Tauri 的状态是进程级的，按类型索引。State<'_, WordCountCache> 在任何窗口的任何命令里拿到的都是同一个 Arc，因此：

  • 主窗口保存笔记 → 缓存失效；
  • 快速记录窗口打开「关于」→ 重新计算一次 → 写回同一份缓存；
  • 主窗口再查字数 → 直接命中。

20.8 测试：克隆共享与失效 ​

rust
#[test]
fn clones_share_the_same_cell() {
    let a = WordCountCache::default();
    let b = a.clone();
    a.store(7);
    assert_eq!(b.get(), Some(7));
}

#[test]
fn store_and_invalidate() {
    let cache = WordCountCache::default();
    assert_eq!(cache.get(), None);
    cache.store(42);
    assert_eq!(cache.get(), Some(42));
    cache.invalidate();
    assert_eq!(cache.get(), None);
}

第一个测试是 Arc 语义的「活体证明」：如果误用 Rc 且跨线程，会在编译期被拒绝；如果误把内部字段当值拷贝，两个实例就不会共享。

20.9 常见报错速查 ​

报错 / 现象原因解决
Rc<...> cannot be sent between threads safely用了单线程引用计数换成 Arc
future cannot be sent between threads safely跨 .await 持有 MutexGuard把 guard 作用域缩到 await 之前
应用偶发卡死同一线程重复 write()（RwLock 不可重入）避免递归加锁，缩小临界区
统计结果永远是旧值写路径漏了 invalidate()在 insert/update/delete/import 后统一失效
PoisonError 导致后续全挂持锁线程 panic 后仍 unwrap按场景 into_inner() 恢复
缓存命中率低把整个列表当缓存键，写一次就全失效缓存粒度改成「按笔记 id」或接受现状（数据量小）

20.10 小结与课后练习 ​

本章你已完成：用 Arc<RwLock<Option<usize>>> 实现全库字数缓存；在写路径精确失效；把缓存托管为进程级状态，为多窗口共享打底；处理锁毒化并理解跨 .await 持锁的风险。应用升级到 v0.19.0。

课后练习：

  1. 给缓存加一个 computed_at: Option<Instant>，在「关于」弹窗里显示「统计于 X 秒前」。
  2. 把缓存粒度改成 HashMap<String, usize>（按笔记 id），比较失效成本与命中率。
  3. 写一个多线程测试：8 个线程并发 store / get，用 std::thread::scope 验证不会死锁、最终值一致。
