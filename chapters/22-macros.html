第 22 章 · 宏与代码生成：macro_rules 与过程宏 ​

钳钳：「重复的活让魔法棒干。宏不是让你少打字，是让同一类错误只可能犯一次。」

本章学习目标 ​

  • 用 macro_rules! 写声明式宏，并理解 $crate 与卫生性（hygiene）
  • 区分声明式宏、派生宏、属性宏、函数式宏
  • 新建一个 proc-macro = true 的 workspace crate，用 syn + quote 生成代码
  • 把 AppError 的手写 Serialize 实现替换成 #[derive(IpcError)]
  • 用 cargo expand 检查宏展开结果，理解「宏只是编译期文本替换」

22.1 先消除一处四连重复 ​

create_note、update_note、delete_note、import_note 里都有一模一样的一行：

rust
app.emit(EVENT_NOTES_CHANGED, &note)?;

重复本身不是大问题，问题在于它携带了三个容易写错的细节：

  1. 事件名常量（写成字面量 "notes://changed" 也能编译，但会静默不匹配前端）；
  2. payload 形状（&Note / ()，前端监听得懂哪种）；
  3. 错误转换（tauri::Error → AppError）。

任何一处漏掉或写错，症状都是「前端不刷新」，而且不报错。适合用宏收敛。

22.2 macro_rules!：声明式宏 ​

[notes/commands.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/notes/commands.rs) 顶部：

rust
#[macro_export]
macro_rules! broadcast_notes_changed {
    ($app:expr, $payload:expr) => {
        $app.emit($crate::notes::EVENT_NOTES_CHANGED, $payload)
            .map_err($crate::error::AppError::from)?
    };
}

调用点：

rust
crate::broadcast_notes_changed!(app, &note);

四个要点：

机制作用
$app:expr捕获一个表达式；expr 后面只能跟 , / ; 等有限分隔符
$crate指向定义宏的 crate，避免调用方同名模块造成解析错误
#[macro_export]把宏导出到 crate 根，跨模块可用（crate::broadcast_notes_changed!）
?宏展开后的 ? 作用在调用处的函数返回值上

? 这一点常被忽略：宏不是函数，它展开进调用者的上下文，所以能直接使用调用者的 Result 返回类型。

卫生性（hygiene） ​

宏里引入的局部变量不会与调用方的变量冲突：

rust
macro_rules! with_temp {
    () => {{
        let temp = 1; // 这个 temp 对调用方不可见
        temp
    }};
}

但 $crate 这类路径必须显式写，否则宏被别的 crate 使用时找不到定义处的模块。

22.3 四种宏，别混为一谈 ​

类型写法例子本项目
声明式macro_rules!vec!、println!broadcast_notes_changed!
派生宏#[proc_macro_derive]#[derive(Serialize)]#[derive(IpcError)]
属性宏#[proc_macro_attribute]#[tauri::command]Tauri 内部使用
函数式宏#[proc_macro]sqlx::query!未使用

后三种属于过程宏，需要单独的 proc-macro crate，输入输出都是 TokenStream。

22.4 新建过程宏 crate ​

目录结构（与 plugins/note-stats 平级，纳入同一 workspace）：

text
app/src-tauri/
├── macros/
│   └── aninotes-macros/
│       ├── Cargo.toml
│       └── src/lib.rs
├── Cargo.toml
└── src/ ...

macros/aninotes-macros/Cargo.toml：

toml
[package]

[lib]

主 crate 的 Cargo.toml 两处改动：

toml
[workspace]
members = ["plugins/note-stats", "macros/aninotes-macros"]

[dependencies]
aninotes-macros = { path = "macros/aninotes-macros" }

🦀 钳钳的悄悄话

过程宏 crate 只能导出宏，不能导出普通函数/结构体给运行时使用。它的产物在编译期就被消费掉了，所以 proc-macro = true 与「普通库」是互斥的。

22.5 写 #[derive(IpcError)] ​

完整实现只有二十来行：

rust
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(IpcError)]
pub fn derive_ipc_error(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);
    let ident = input.ident;

    let expanded = quote! {
        impl ::serde::Serialize for #ident {
            fn serialize<S>(&self, serializer: S) -> ::std::result::Result<S::Ok, S::Error>
            where
                S: ::serde::Serializer,
            {
                serializer.serialize_str(&::std::string::ToString::to_string(self))
            }
        }
    };

    TokenStream::from(expanded)
}

逐段解释：

  1. parse_macro_input! 把 token 流解析成 DeriveInput（包含类型名、泛型、字段等）；
  2. input.ident 拿到类型名（这里是 AppError）；
  3. quote! 里的 #ident 会被替换成实际标识符；
  4. 生成代码里所有路径都用 ::serde::... 绝对路径，避免与调用方的同名模块冲突；
  5. 返回 TokenStream，编译器把它拼回源码继续类型检查。

使用侧（[error.rs](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/src/error.rs)）：

rust
use aninotes_macros::IpcError;
use thiserror::Error;

#[derive(Debug, Error, IpcError)]
pub enum AppError {
    #[error("未找到 id 为 {0} 的笔记")]
    NotFound(String),
    // ...
}

原来那段三十行的 impl Serialize for AppError 被删掉了，行为完全不变。

22.6 为什么这比手写 impl 好 ​

维度手写 impl派生宏
新增错误类型复制一段 impl，容易漏字段加一个 derive，零样板
序列化策略变更改 N 处改宏一处
一致性依赖开发者记性编译器保证所有变体同策略
可读性错误类型文件被样板淹没类型定义保持干净

代价也很真实：宏的调试比普通代码难。遇到问题时用：

bash
cargo expand --bin aninotes
cargo expand --bin aninotes error

cargo expand 会把宏展开成普通 Rust 代码，直接看到 impl Serialize 长什么样。它是宏开发的第一工具。

22.7 宏的边界：什么时候不该写宏 ​

  • 只有两处调用：直接写两行更清楚；
  • 逻辑需要断点调试：宏展开后的行号映射不直观；
  • 需要类型多态：优先 trait/泛型，宏是最后手段；
  • 错误信息可读性要求高：宏报错往往指向展开点，不指向定义点。

一句经验：宏用来消除「结构性重复」，不是消除「看起来相似的代码」。

22.8 常见报错速查 ​

现象原因解决
cannot find macro broadcast_notes_changed in this scope没加 #[macro_export]，或用 self:: 而非 crate::用 crate::broadcast_notes_changed!
宏展开后报 expected expression$x:expr 后跟了非法分隔符改成 $x:expr, 或调整模式
过程宏 crate 报 cannot find crate serde生成代码用了 serde:: 相对路径统一改 ::serde:: 绝对路径
#[derive(IpcError)] 报 trait Display 未实现类型没有 #[derive(Error)] 或手写 Display先保证 to_string() 可用
改了宏但行为没变增量编译缓存 / 没重新编译主 cratecargo clean -p aninotes-macros 后重试
宏在别的 crate 里找不到定义$crate 写成 crate定义侧用 $crate，调用侧用导出路径

22.9 小结与课后练习 ​

本章你已完成：用 macro_rules! 收敛事件广播（事件名、payload、错误转换一处定义）；新建 aninotes-macros 过程宏 crate 并纳入 workspace；用 syn + quote 实现 #[derive(IpcError)]，删掉手写 Serialize；掌握 cargo expand 的排查方式。应用升级到 v0.21.0。

课后练习：

  1. 给 broadcast_notes_changed! 增加一个可选分支，支持不传 payload（默认 ()）。
  2. 写第二个派生宏 #[derive(Timestamped)]，为结构体自动生成 fn touched_at(&self) -> String（提示：用 chrono::Local::now()）。
  3. 用 cargo expand 展开 AppError，把展开结果与手写版本逐行对比，确认语义一致。
