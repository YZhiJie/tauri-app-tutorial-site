第 34 章 · 发布通道、灰度与回滚 ​

钳钳：「发版不是一次按下按钮，而是一场有观众的演出——先让一小部分人看到，再决定要不要开灯。」

本章学习目标 ​

  • 用版本号的预发布段定义 stable / beta / nightly 三个通道
  • 在更新清单里增加 channel 与 rollout 字段，让发布策略随包一起下发
  • 用确定性哈希做稳定分桶，保证同一用户不会反复横跳
  • 用 rollout = 0 实现 kill switch，在出问题时立刻止血
  • 理解 semver 不可降级，并据此设计回滚路径
  • 用 prerelease 与 make_latest 让预发布版本不污染稳定端点

34.1 一次发布为什么会同时伤害所有人 ​

第 8 章搭好了自动更新：打 tag → 构建签名 → 客户端检查 → 下载安装。它解决的是「怎么把包送到用户手里」，但没有回答一个更重要的问题：如果这个包有问题呢？

全量发布的失败模式非常整齐：

  1. 新版本有启动崩溃，所有用户重启后一起黑屏；
  2. 更新端点被撤包，已经下载的用户仍会安装；
  3. 想回退，却发现客户端只接受更高的版本号。

发布工程的成熟度，不体现在「发得多快」，而体现在「出问题时能多快收住」。这一章补三件事：通道、灰度、回滚。

三者各管一段：

手段解决的问题生效时机
通道beta 用户先踩坑，稳定用户不被波及下载前（选端点）
灰度即使同一通道，也只放一部分人进来检查更新后、询问前
回滚已经放出去的错误版本如何止损发布新版本 / kill switch

34.2 版本号就是通道 ​

最省事的通道设计不是「构建时注入一个 CHANNEL 环境变量」，而是直接从 semver 读：

  • 0.33.0 → stable
  • 0.33.0-beta.3 → beta
  • 0.33.0-rc.1 → beta（发布候选也属于预发布）
  • 0.33.0-nightly.20261102 → nightly

见 [channel.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.ts#L16-L21)。

ts
export function releaseChannel(version: string): ReleaseChannel {
  const pre = version.split("-")[1]?.toLowerCase() ?? "";
  if (pre.startsWith("nightly")) return "nightly";
  if (pre.startsWith("beta") || pre.startsWith("rc")) return "beta";
  return "stable";
}

这样做的好处是只有一个事实来源。package.json、Cargo.toml、tauri.conf.json 里的版本号已经由构建流程同步，tag 名又必须与它一致，通道自然不会再出现「配置写 beta、版本号写 stable」的分裂。

提示：不要用 0.33.0+build.7 这种构建元数据表达通道。semver 规定 + 之后的部分不参与优先级比较，很多工具会直接忽略它，用来做通道判断并不稳妥。

34.3 清单里的策略字段 ​

Tauri 的更新清单本来只有 version、pub_date、platforms。插件会把不认识的字段原样保留在 update.rawJson 里，这正好可以用来携带发布策略。

第 34 章在 release.yml 生成清单时加入两个字段：

json
{
  "version": "0.33.0",
  "channel": "stable",
  "rollout": 20,
  "platforms": {
    "darwin-aarch64": { "signature": "…", "url": "…" }
  }
}

见 [release.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/release.yml#L129-L176)。

生成逻辑刻意与客户端保持同一套规则：

js
const pre = version.split("-")[1] ?? "";
const channel = pre.startsWith("nightly")
  ? "nightly"
  : pre.startsWith("beta") || pre.startsWith("rc")
    ? "beta"
    : "stable";

const rawRollout = process.env.ROLLOUT;
const rollout = rawRollout ? Number(rawRollout) : 100;

rollout 来自仓库的 Actions 变量 ROLLOUT_PERCENT：

取值含义
未设置 / 100全量发布
20约 20% 的安装收到更新
0暂停发布（kill switch）

变量而不是 secret 是刻意的：它不敏感，修改后立即生效，不需要重新构建，也不该被审计日志藏起来。

34.4 稳定分桶：同一用户不能反复横跳 ​

灰度最容易写错的地方，是每次检查都用随机数：

ts
// 反例
if (Math.random() * 100 < rollout) { /* 放行 */ }

后果是用户每启动一次应用，就可能看到一次更新提示，下一次又消失。更糟的是，用户点了「稍后」之后永远不知道下一次还会不会出现。

正确做法是把用户映射到固定桶位：

ts
export function rolloutBucket(seed: string): number {
  let hash = 0x811c9dc5;
  for (const char of seed) {
    hash ^= char.codePointAt(0) ?? 0;
    hash = Math.imul(hash, 0x01000193);
  }
  return (hash >>> 0) % 100;
}

见 [channel.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.ts#L29-L36)。

哈希种子不是用户 ID，而是本地生成的安装 ID：

ts
export function installId(storage: Storage = localStorage): string {
  const key = "aninotes.install-id";
  /* 首次 randomUUID，之后复用 */
}

见 [channel.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.ts#L52-L63)。

三个设计点：

  1. 不含用户信息：随机 UUID，卸载重装会换一个，符合隐私最小化；
  2. 持久化：存在 localStorage，升级前后保持一致；
  3. 同步可算：FNV-1a 只有几行，不依赖 crypto.subtle，浏览器预览与 Tauri 内表现一致。

放量时只改 rollout 的阈值，不换哈希函数，于是「已经进来的用户」不会退出去：

ts
export function inRollout(rollout: number | undefined, seed: string): boolean {
  if (rollout === undefined || rollout >= 100) return true;
  if (rollout <= 0) return false;
  return rolloutBucket(seed) < rollout;
}

见 [channel.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.ts#L45-L49)。

rollout = 20 放行的永远是桶位 0~19 的那批人；下一步调到 50，原来 20% 的人仍然在内，只是新增 20~49 桶位。这就是「单调放量」。

提示：rollout 的判定是 < rollout 而不是 <=。否则 rollout = 1 会放行 0 和 1 两个桶位，实际比例变成 2%，放量曲线就不精确了。

34.5 kill switch：出事了先关门 ​

rollout = 0 是一个特殊值，它让所有安装都跳过这次更新：

ts
if (!inRollout(rollout, installId())) {
  console.info(`[updater] 灰度未命中（rollout=${rollout ?? "全量"}），跳过 ${update.version}`);
  return false;
}

见 [updater.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/updater.ts#L74-L82)。

它和「删除 Release」的区别很关键：

  • 删 Release 只是让 URL 404，已经拿到清单的客户端可能还在下载；
  • rollout = 0 是清单级别的门，客户端在询问用户之前就退出，连下载都不会开始。

止血顺序建议固定成：

  1. 把 ROLLOUT_PERCENT 改成 0，重新生成清单（或直接替换 Release 里的 JSON）；
  2. 确认下载量与崩溃上报回落；
  3. 定位问题，发一个更高版本号修复；
  4. 修复版从 5% 开始重新放量。

第 1 步为什么不改代码重新构建？因为 kill switch 的意义就是不依赖构建成功。构建管线本身出问题时，你仍然需要能改清单。

34.6 客户端接入：静默过滤，不要打扰 ​

灰度未命中的处理原则只有一条：对用户完全不可见。

用户看到「有新版本，但你不能装」，只会困惑。因此过滤发生在 ask 之前：

ts
const rollout = readRollout(update.rawJson);
if (!inRollout(rollout, installId())) {
  console.info(`[updater] 灰度未命中（rollout=${rollout ?? "全量"}），跳过 ${update.version}`);
  return false;
}

const channel = releaseChannel(update.version);
const accepted = await ask(
  `发现新版本 v${update.version}（${channel} 通道）。\n${update.body ?? ""}\n\n是否立即下载并更新？`,
  { title: "AniNotes 软件更新", kind: "info" },
);

见 [updater.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/updater.ts#L78-L88)。

readRollout 做了类型收窄，避免清单里出现字符串 "20" 时静默失效：

ts
export function readRollout(rawJson: Record<string, unknown>): number | undefined {
  const value = rawJson.rollout;
  return typeof value === "number" && Number.isFinite(value) ? value : undefined;
}

见 [channel.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.ts#L66-L69)。

这部分逻辑不依赖 Tauri API，所以可以用纯单元测试覆盖。见 [channel.test.ts](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src/lib/channel.test.ts#L48-L67)，其中一条测试专门验证「20% 灰度的放行者桶位都小于 20」。

34.7 回滚：semver 不允许降级 ​

很多人第一次做回滚时会想：「把清单指回旧版本不就行了？」答案是不行。

Tauri updater 与 semver 的约定是只接受更高版本。如果客户端当前是 0.33.0，清单写成 0.32.0，检查更新会直接返回「已是最新」，不会降级。

因此回滚不是「退回旧包」，而是发一个更高版本号的旧代码：

场景错误做法正确做法
0.33.0 崩溃清单改回 0.32.0发 0.33.1，内容等同 0.32.0
灰度 20% 发现问题删除 Releaserollout = 0，再发修复版
签名泄露只换私钥换公私钥 + 发新版本，旧版本不再可更新

这条规则听起来笨，但它保证了「版本号单调递增」这个不变量。更新系统一旦允许降级，就会打开「攻击者把用户骗回有漏洞版本」的口子。

本章的实践约定：

  • 每次回滚都占用一个新的 patch 版本；
  • release notes 里明确写「本版本回滚了 0.33.0 的某改动」；
  • 不与正常功能发布混在一起，避免用户以为有新功能。

34.8 通道与 latest 指针 ​

GitHub Releases 有一个 latest 指针，稳定端点用的正是它：

json
"endpoints": [
  "https://github.com/your-github-name/aninotes/releases/latest/download/{{target}}-{{arch}}.json"
]

见 [tauri.conf.json](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/app/src-tauri/tauri.conf.json#L58-L63)。

如果 beta 版本也被标成 latest，稳定用户会在下一次检查时直接收到 beta——通道就形同虚设。因此发布工作流必须显式处理：

yaml
- name: Create GitHub Release
  uses: softprops/action-gh-release@v2
  with:
    prerelease: ${{ contains(github.ref_name, '-') }}
    make_latest: ${{ !contains(github.ref_name, '-') }}

见 [release.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/release.yml#L203-L209)。

判定规则很简单：tag 里有连字符就是预发布。v0.33.0 不含连字符，正常占 latest；v0.33.0-beta.3 含连字符，标为 prerelease 且不占 latest。

提示：beta 通道需要自己的端点。常见做法是给 beta 用户单独构建一份 tauri.beta.conf.json，把 endpoints 指向固定 tag（如 releases/download/beta-latest/...）。本章不引入第二个配置文件，先保证「预发布不会误伤稳定用户」这条底线。

34.9 签名链与权限最小化 ​

发布流程里的信任边界有三层，缺一层都不算完整：

层机制本章位置
传输HTTPSendpoints
完整性minisign 签名TAURI_SIGNING_PRIVATE_KEY
发布权限GitHub token 最小化permissions: contents: write

私钥只存在于 Actions secret 中，构建机用完即弃；客户端只内置公钥，验签失败直接拒绝安装。因此即使更新端点被劫持，攻击者也无法伪造一个能装上的包。

见 [release.yml](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/tauri-app-tutorial/.github/workflows/release.yml#L95-L99) 的签名注入，以及 release job 的权限声明。

新增的 concurrency 也是安全的一部分：同一个 tag 重复推送时，两轮构建同时写 Release 会造成产物与清单错配。取消旧的一轮，比事后查「为什么 JSON 里的签名对不上安装包」便宜得多。

34.10 一次完整的发布演练 ​

把本章的规则串起来，一个稳定版本的发布节奏是：

  1. 版本号升到 0.33.0，三处同步，本地门禁全过；
  2. 打 tag v0.33.0 并推送，触发 release.yml；
  3. 四套产物构建、签名，清单写入 channel: stable、rollout: 5；
  4. 观察一天：崩溃率、更新成功率、卸载量；
  5. 把 ROLLOUT_PERCENT 调到 50，重新生成清单并替换 Release 资源；
  6. 无异常后调到 100，此时全量；
  7. 若中途发现严重问题，调回 0，然后准备 0.33.1。

第 5、6 步不需要重新构建安装包，只改清单里的数字。这正是把 rollout 放进清单而不是写死在客户端的原因。

警告：不要在同一份清单上同时改 version 和 rollout。前者意味着换包，后者只是换策略；混在一起会让「到底是新包出问题还是放量出问题」无法区分。

34.11 常见报错速查 ​

现象原因解决
beta 版本推给了稳定用户预发布没标 prerelease，占了 latest加 prerelease: contains(ref, '-')
灰度用户反复收到/收不到提示用了随机数而不是稳定哈希用安装 ID + FNV-1a 分桶

34.12 小结与课后练习 ​

本章你已完成：用版本号定义 stable / beta / nightly；在更新清单中加入 channel 与 rollout；实现 FNV-1a 稳定分桶与 kill switch；在客户端静默过滤未命中的灰度；让预发布不占 latest 指针；明确了「回滚 = 发更高版本」的规则。应用升级到 v0.33.0。

课后练习：

  1. 把 rolloutBucket 换成 crypto.subtle.digest("SHA-256", ...)，说明为什么它不再是同步函数，以及这会如何影响 silentCheckAndPrompt 的调用链。
  2. 给 channel.ts 增加一个 describeRollout(rollout)，返回「全量 / 暂停 / 20%」这样的中文文案，并补一条测试。
  3. 设计 beta 通道的端点方案：写出 tauri.beta.conf.json 的关键字段，并说明它如何与 release.yml 的 tag 规则配合。
  4. 假设 0.33.0 在 5% 灰度时发现启动崩溃，写出完整的止血步骤与时间顺序，包括版本号、清单字段和 release notes。
  5. 思考：如果用户手动下载了旧版安装包覆盖安装，installId 会变化吗？这对灰度结果有什么影响？
