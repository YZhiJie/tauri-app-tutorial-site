第 16 章 · 发布工程化：结构化日志与 CI 质量门禁 ​

钳钳：「第 8 章我们学会了把应用打包发出去。但『能发布』和『敢维护』是两回事——出问题时有日志可查，每次提交有机器把关，这才叫工程化。」

本章学习目标 ​

  • 用 tracing 全家桶搭建「控制台 + 滚动文件」双输出日志
  • 理解 non_blocking 写入与 WorkerGuard 的寿命管理
  • 写一个三任务 CI 工作流（Rust / 前端 / 文档），把质量门禁自动化
  • 了解移动端与崩溃上报（Sentry）的接入路径（指南性质，不写代码）

16.1 为什么 eprintln! 不够用 ​

我们的代码里目前只有一处 eprintln!（ping/pong 回送失败时）。它在开发期完全够用，但发布后有两个死穴：

  1. 用户看不到：打包后的应用没有控制台，Windows 下我们甚至用 windows_subsystem = "windows" 关掉了控制台窗口——错误信息直接蒸发；
  2. 没有级别和去向：eprintln! 永远是「往 stderr 打一行字」，不能过滤级别、不能写文件、不能按模块区分。

用户反馈「应用打不开」时，没有日志的开发者只能猜。本章的日志方案：

tracing::info! / warn! / error!
        │
        ├── fmt::layer() ──────────────> 控制台（开发期）
        └── fmt::layer().with_writer(file) ──> ~/Library/Logs/.../aninotes.log.YYYY-MM-DD（发布后）

16.2 tracing 全家桶：三个 crate 的分工 ​

toml
# 第 16 章：结构化日志（控制台 + 日志目录滚动文件双输出）
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
tracing-appender = "0.2"
crate角色
tracing调用侧：info! warn! error! 宏，带结构化字段
tracing-subscriber订阅侧：fmt layer（格式化输出）、EnvFilter（级别过滤）、registry（组合器）
tracing-appender文件去向：按天滚动 + 后台线程写入

16.3 初始化：init_logging 逐行拆解 ​

main.rs 新增（setup 中最先调用）：

rust
/// 日志文件后台写入线程的守护：WorkerGuard 被 drop 写线程即停、缓冲丢失。
/// 托管进应用状态，保证与进程同寿命。字段从不被读取，存在就是为了「活着」。
struct LogGuard(#[allow(dead_code)] tracing_appender::non_blocking::WorkerGuard);

fn init_logging(app: &tauri::AppHandle) {
    use tracing_subscriber::{fmt, layer::SubscriberExt, util::SubscriberInitExt, EnvFilter};

    // 日志目录：各平台标准位置（如 macOS ~/Library/Logs/com.aninotes.app）
    let log_dir = app.path().app_log_dir().unwrap_or_else(|_| std::env::temp_dir());
    // 按天滚动：aninotes.log.2026-10-30 这样的文件名，避免单文件无限增大
    let file_appender = tracing_appender::rolling::daily(&log_dir, "aninotes.log");
    // non_blocking：写文件在后台线程完成，日志调用点零阻塞
    let (file_writer, guard) = tracing_appender::non_blocking(file_appender);
    app.manage(LogGuard(guard));

    // RUST_LOG 环境变量可覆盖默认级别（如 RUST_LOG=aninotes=debug）
    let filter =
        EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("aninotes=info"));
    let console_layer = fmt::layer(); // 开发期看控制台
    let file_layer = fmt::layer().with_ansi(false).with_writer(file_writer); // 文件不带颜色码

    tracing_subscriber::registry()
        .with(filter)
        .with(console_layer)
        .with(file_layer)
        .init();

    tracing::info!(dir = %log_dir.display(), "日志系统初始化完成");
}

四个要点：

  1. registry().with(...).with(...)：layer 是可组合的管道。filter 管「哪些日志能过」，两个 fmt layer 管「送到哪」；
  2. with_ansi(false)：ANSI 颜色码写进文件就是一堆乱码 ^[[32m，文件输出必须关掉；
  3. non_blocking + WorkerGuard：文件写入放到后台线程，日志调用点不会卡在磁盘 I/O 上——但代价是 guard 一旦 drop，缓冲里没写完的日志就丢了。所以把它托管进应用状态与进程同寿命；
  4. EnvFilter：默认 aninotes=info（只看自己 crate 的 info 以上）；排查问题时 RUST_LOG=aninotes=debug,sqlx=warn pnpm tauri dev，不用改一行代码。

顺手把唯一的 eprintln! 换成 tracing::warn!，再给数据库迁移加两条 info 日志（db.rs）：

rust
tracing::info!("首次启动：执行 JSON -> SQLite 迁移与种子初始化");
tracing::info!(count = legacy.len(), "旧版 JSON 笔记迁移入库");

注意第二条用了结构化字段：count = legacy.len() 在日志里是独立的 key=value，日后日志系统可以按字段检索，而不是在字符串里正则找数字。

16.4 CI：让机器当第一道评审 ​

新建 .github/workflows/ci.yml——push 到 main 与所有 PR 触发，三个任务并行：

yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  rust:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: app/src-tauri
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy
      - name: 安装系统依赖   # Tauri 在 Linux 上编译需要 WebKitGTK
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf
      - uses: actions/cache@v4   # 依赖缓存：锁文件不变时秒级命中
        with:
          path: |
            ~/.cargo/registry
            ~/.cargo/git
            app/src-tauri/target
          key: ${{ runner.os }}-cargo-${{ hashFiles('app/src-tauri/Cargo.lock') }}
          restore-keys: ${{ runner.os }}-cargo-
      - name: cargo check（含 note-stats 插件）
        run: cargo check --workspace
      - name: cargo clippy
        run: cargo clippy --workspace -- -D warnings

  frontend:
    # checkout -> pnpm -> node 22 -> pnpm install --frozen-lockfile -> pnpm build
    # build 脚本内含 vue-tsc --noEmit，类型错误直接失败

  docs:
    # checkout -> pnpm -> node 22 -> pnpm install --frozen-lockfile -> pnpm docs:build

（完整文件在仓库 .github/workflows/ci.yml，三个任务共用 pnpm 9.15.4 + Node 22 的约定，与 deploy.yml 保持一致。）

设计决策：

  • cargo check --workspace：--workspace 把 note-stats 插件一起检查——workspace 的意义在 CI 上体现出来了；
  • clippy -- -D warnings：把所有 lint 升级为错误。写这章时它真的抓到了三个问题（一个从未被读取的字段、两处文档列表缩进），当场修掉；
  • docs 也进 CI：文档站构建失败（死链、配置错误）应该在提交时暴露，而不是部署时；
  • 与 release.yml 分工：CI 管每次提交的质量，release 管打 tag 时的签名发布，互不重复。

在 GitHub 仓库 Settings → Branches 给 main 加保护规则，要求 ci 三个任务通过才能合并——门禁才算真正落地。

16.5 进阶指南：移动端与崩溃上报（不写代码） ​

移动端（iOS / Android） ​

Tauri v2 的移动端已进入稳定期，接入路径：

  1. pnpm tauri android init / pnpm tauri ios init 生成 gen/android、gen/apple 工程目录；
  2. 前置依赖：Android Studio（SDK + NDK）、Xcode；iOS 还需 Apple Developer 账号；
  3. pnpm tauri android dev / pnpm tauri ios dev 真机/模拟器调试；
  4. 代码适配点：#[cfg(mobile)] 条件编译裁剪桌面专属逻辑（托盘、全局快捷键在移动端没有意义）；CSP 与 capabilities 同样生效；
  5. 分发：Android 走 tauri android build --apk/--aab，iOS 走 Xcode Archive。

AniNotes 的数据层（SQLite）在移动端天然可用，但文件路径策略要改——移动端没有用户可浏览的文件系统，导入导出要走系统分享面板（tauri-plugin-share 等）。

崩溃上报（Sentry） ​

日志文件在用户能主动发给你时才有效；应用直接崩溃时，需要崩溃上报：

  1. Rust 侧：接 sentry crate 的 sentry::init，panic 自动捕获；
  2. 前端侧：@sentry/vue 捕获 JS 异常；
  3. Tauri 官方插件 tauri-plugin-sentry 提供打包好的集成；
  4. 隐私红线：崩溃堆栈可能包含用户路径/内容片段，接入时务必在隐私政策中声明，并提供关闭开关；自托管可用 Sentry 开源版或 GlitchTip。

这两项都不进本仓库代码——它们是「知道何时该上」的储备知识。

16.6 常见报错速查 ​

现象原因解决
日志文件里全是 ^[[32m 乱码文件 layer 没关 ANSI 颜色.with_ansi(false)
退出前最后几条日志丢失WorkerGuard 提前 drop，后台缓冲没写完guard 托管进应用状态（LogGuard 模式）
文件里一条日志都没有filter 级别过高，或 init 在日志调用之后才执行init_logging 放在 setup 最前；确认 EnvFilter 规则
CI 上 cargo check 报 glib/webkit 找不到Ubuntu runner 缺系统依赖装 libwebkit2gtk-4.1-dev 等（见 ci.yml）
CI 上 clippy 失败但本地通过本地没跑 clippy 或 Rust 版本不同本地 cargo clippy --workspace -- -D warnings 对齐
RUST_LOG=debug 设了但没 debug 日志EnvFilter 被代码里的默认值覆盖顺序搞反try_from_default_env 优先，兜底才用默认值

16.7 小结与课后练习 ​

本章你已完成：tracing 双输出日志（控制台 + 按天滚动文件、non_blocking + WorkerGuard 寿命管理、EnvFilter 级别过滤）；三任务 CI 工作流（cargo check / clippy / 前端构建 / 文档构建）。应用升级到 v0.15.0。

至此，精通篇的「工程化阶段」六章全部完成。回看这条路线：错误体系（11）→ 通信架构（12）→ 系统常驻（13）→ 数据引擎（14）→ 插件化（15）→ 工程化（16）——AniNotes 已经是一个架构清晰、可持续演进的桌面应用了。

但这还只是「会用」。从第 17 章开始，我们把视线转向 Rust 本身：文档测试、所有权建模、trait 抽象、智能指针、并发、宏、FFI，最后用多窗口与测试把架构收口——那才是「精通」的部分。

课后练习：

  1. 给 NotesDb 的写入操作（insert/update/delete）加 tracing::info!，带上笔记 id 字段，运行后去日志目录验证结构化字段的输出格式。
  2. 给 CI 加第四个任务 fmt：跑 cargo fmt --check，本地装 rustfmt 组件对齐。（提示：dtolnay/rust-toolchain 的 components 里加 rustfmt）
  3. 把日志层升级成 JSON 格式（fmt::layer().json()），体会「结构化日志」对机器检索的意义——想想为什么文件输出适合 JSON 而控制台不适合。
