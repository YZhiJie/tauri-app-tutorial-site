第 6 章 · 多端兼容性开发 ​

钳钳：「『能跑』和『表现一致』是两件事。本章系统梳理四个层次的差异，并给出每种差异的标准答案。」

本章学习目标 ​

  • 建立兼容性问题的分层认知（构建期 / 文件行为 / 窗口外观 / Web 渲染）
  • 熟练使用 Rust 条件编译组织平台专属代码
  • 掌握路径、换行符、编码三类最常踩的跨平台坑
  • 理解三大 WebView 的差异及 CI 构建矩阵思路

6.1 兼容性问题的四个层次 ​

写跨平台代码时，先判断问题属于哪一层，解决方案是固定的：

层次典型问题解决手段
① 构建期某平台才有原生 API / 依赖条件编译、平台专属模块
② 文件行为路径分隔符、大小写、换行符、文件锁Path/PathBuf、归一化策略
③ 窗口外观标题栏样式、DPI、窗口按钮位置tauri.conf 平台配置、条件编译
④ Web 渲染CSS/表单控件差异、WebKit 版本特性检测、渐进增强、降级方案

6.2 Rust 条件编译 ​

三种写法 ​

rust
// 1) 编译期「条件包含」整段代码（未命中平台的代码完全不存在）
#[cfg(target_os = "windows")]
fn only_on_windows() {}

// 2) cfg! 宏：运行时布尔值（两侧代码都会编译，适合分支逻辑）
if cfg!(target_os = "macos") {
    // ...
}

// 3) 组合条件
#[cfg(all(target_os = "linux", target_arch = "x86_64"))]
fn linux_x64_only() {}

常用检测条件：target_os（windows/macos/linux）、target_arch（x86_64/aarch64）、 target_family（unix/windows）、debug_assertions（区分 debug/release）。

推荐的模块组织：平台模块 + cfg 重导出 ​

平台代码一多，散落的 #[cfg] 会很难读。标准模式：

text
src/platform/
├── mod.rs        # 统一接口 + cfg 重导出
├── windows.rs    # Windows 实现
├── macos.rs      # macOS 实现
└── linux.rs      # Linux 实现
rust
// platform/mod.rs —— 调用方只看到一个函数名，不关心平台差异
#[cfg(target_os = "windows")]
#[path = "windows.rs"]
mod imp;

#[cfg(target_os = "macos")]
#[path = "macos.rs"]
mod imp;

#[cfg(target_os = "linux")]
#[path = "linux.rs"]
mod imp;

pub(crate) use imp::describe;

每个平台文件实现签名相同的 describe()。本章应用的 platform_tips 命令 采用的是更轻量的「函数内多段 cfg 块」——代码量小时它更直观； 规模一大就应迁移到上面的模块模式（这就是判断标准）。

🦀 钳钳的悄悄话

条件编译的最大陷阱是：你在某平台上永远编译不到另一段代码，错误会潜伏到 CI 才爆。 对策就是 6.9 的 CI 矩阵——让三个平台每次提交都编译一次。

6.3 运行时平台检测 ​

不想（或不能）用条件编译时：

rust
// Rust：编译期常量，无运行时开销
use std::env::consts::OS; // "windows" / "macos" / "linux"
ts
// 前端：第 5 章已用
import { platform } from "@tauri-apps/plugin-os";

选型：逻辑与原生能力绑定 → 条件编译；只是 UI 文案差异 → 运行时检测。

6.4 路径：永远不要自己拼分隔符 ​

❌ 错误写法：

rust
let path = format!("{base}/notes/{id}.json");     // Windows 上是错的

✅ 正确写法：PathBuf::join 自动选择分隔符，跨平台通用：

rust
let path = std::path::PathBuf::from(&base)
    .join("notes")
    .join(format!("{id}.json"));

JS 侧同理，使用 @tauri-apps/api/path 的 join()，不要手写 /。

三平台文件系统差异 ​

行为WindowsmacOSLinux
分隔符\（API 也接受 /）//
大小写不敏感（保留大小写）默认不敏感（APFS）敏感
非法文件名字符\ / : * ? " < > |/、冒号受限/

大小写差异的经典 bug：开发机 macOS 上 import.png 和 Import.png 看似同一个文件， 到 Linux CI 上直接找不到。文件名一律小写是最简单的防御。

数据目录继续使用第 4 章的 app_data_dir()，不要自己发明路径规则。

6.5 换行符：CRLF 与 LF ​

平台文本默认换行
Windows\r\n（CRLF）
macOS / Linux\n（LF）

如果不归一化，同一个文件在不同平台导入后：字数不同、文本比较永远不相等、 导出内容混入两种换行。本章应用在导入时统一归一化：

rust
let content = raw.replace("\r\n", "\n").replace('\r', "\n");

策略要明确：应用内部只使用 \n；在边界处（导入）归一化，导出时按需转换。 如果产品明确要求「导出的文件在记事本里也要一行不错」，可在导出分支按平台写 CRLF—— 但不要两头都转换，保持单向。

6.6 编码：统一 UTF-8 ​

  • Rust 的 String / str 天然是 UTF-8，read_to_string 会拒绝非 UTF-8 文件并给出错误；
  • Windows 用户可能拿到 GBK 编码的旧文件：要么在文档中说明「请另存为 UTF-8」， 要么引入编码检测库转换（属于进阶需求，别一开始就做）；
  • Windows 控制台默认 codepage 可能导致 println! 中文乱码，不影响应用本身； 调试时用 chcp 65001 切换 UTF-8（第 9 章有记录）。

6.7 WebView 渲染差异 ​

差异点WebView2 (Win)WKWebView (macOS)WebKitGTK (Linux)
内核对应新版 EdgeSafariWebKit（版本看发行版）
滚动条样式Win 风格，可自定义overlay 风格GTK 主题风格
原生表单（date/color）Win 原生弹层macOS 原生弹层各 GTK 主题，老旧版本样式差
字体渲染DirectWriteCore TextFreeType/fontconfig
新 CSS 特性跟进很快跟 Safari 版本取决于 WebKitGTK 版本，LTS 发行版可能落后

应对原则：

  1. 优先用成熟 CSS：自定义属性、grid/flex 三引擎都支持；避免为了炫技用实验特性；
  2. 对关键控件（如日期选择）准备「自绘组件」降级方案；
  3. Linux 上测旧版 WebKitGTK——最容易出渲染问题的平台；
  4. 不要根据 UA 做判断分支，用 CSS @supports 做特性检测。

6.8 窗口外观差异 ​

WindowsmacOSLinux
窗口控制按钮右上，图标风格左上「交通灯」位置随窗口管理器
标题栏系统风格可配 titleBarStyleGTK Header Bar
DPI 缩放系统 DPI系统 RetinaHiDPI 需正确配置

macOS 想做「无边框融合」效果时，可在窗口配置中使用（仅影响 macOS）：

json
{ "titleBarStyle": "Transparent", "hiddenTitle": true }

注意交通灯按钮需要内容区预留左侧空间，否则按钮会压住你的界面元素。 这属于外观定制，没需求不要加——保持默认是跨平台一致性最好的选择。

6.9 CI 构建矩阵 ​

三平台的「构建可行性」要分清（照抄命令前先判断）：

产物在哪构建
.msi/.exe (NSIS)Windows 主机 / windows-latest runner
.dmg/.appmacOS 主机（签名需 Apple 证书）
.deb/.AppImageLinux 主机（交叉编译通常不可行）

GitHub Actions 的矩阵思路（第 8 章会给出包含打包/更新清单的完整 workflow 文件）：

yaml
strategy:
  fail-fast: false
  matrix:
    include:
      - { platform: "windows-latest", args: "" }
      - { platform: "macos-latest",   args: "" }
      - { platform: "ubuntu-22.04",  args: "" }
runs-on: ${{ matrix.platform }}
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with: { node-version: 20 }
  # Rust 由 rustup 在 runner 中自带；Linux runner 需装 webkit2gtk-4.1 依赖
  - run: cd app && pnpm install --no-frozen-lockfile
  - run: cd app && pnpm tauri build

fail-fast: false：一个平台失败不要取消另外两个，一次看到全部问题。

6.10 兼容性自测清单 ​

每次涉及系统能力的改动，过一遍：

  • [ ] 条件编译的三个分支是否都在 CI 通过编译？
  • [ ] 有没有手写路径分隔符 / 手写 ~/？
  • [ ] 导入文本是否归一化了换行符？
  • [ ] 假设文件大小写不敏感是否已失效（Linux 测试）？
  • [ ] 关键 CSS 是否用 @supports / 避开实验属性？
  • [ ] 三平台数据目录中的数据是否一致？

6.12 小结与课后练习 ​

本章你已完成：四层兼容性认知、条件编译、路径/换行/编码标准答案、WebView 差异与 CI 矩阵。

课后练习：

  1. 按 6.2 新建 platform/ 模块，把 platform_tips 重构为三平台文件实现统一接口。
  2. 在导出命令中实现「平台感知换行」：Windows 导出 CRLF，其他平台导出 LF，并为这个行为补测试思路。
  3. 用 CSS @supports 给某个可能不兼容的样式写降级，在三平台（或三内核文档）验证。
